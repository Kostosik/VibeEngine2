# VibeEngine2 API Guide

Практическое руководство по использованию API VibeEngine2 при разработке игр на C#/.NET.

Архитектурное описание: [ENGINE.md](ENGINE.md).

## Часть I. Основы разработки игры

# 1. Основные принципы API

## 1.1. Граница между Engine и Game

VibeEngine2 предоставляет универсальные механизмы, на основе которых разрабатывается конкретная игра.

**Engine отвечает за механизмы, Game — за игровую логику.**

Engine предоставляет:
- ECS и системы выполнения игровой логики;
- симуляцию, физику и пространственные преобразования;
- графику, ввод, аудио и UI;
- загрузку ресурсов, сериализацию и сетевые механизмы;
- инструменты диагностики и отладки.

Игра определяет, как использовать эти возможности. Её собственные компоненты, системы, игровые правила и данные должны находиться в проекте игры, если они не представляют собой универсальный механизм движка.

Например, движок предоставляет возможность создавать сущности и добавлять им компоненты. Но то, что именно представляет сущность — персонажа, здание или производственную машину, — определяет игра.

## 1.2. Проекты, пространства имён и зависимости

API движка разделено на специализированные проекты, каждый из которых отвечает за определённую область функциональности.

При использовании API ориентируйся на публичные типы и их пространства имён. Имя проекта (`.csproj`), имя сборки и пространство имён не обязательно совпадают.

Игровой проект должен подключать необходимые проекты движка и использовать их публичные API. Не следует обращаться к внутренней реализации или конкретному backend без необходимости, если требуемая возможность доступна через общую абстракцию.

## 1.3. Как пользоваться руководством

Разделы этого руководства посвящены практическому использованию API в игровом коде.

Примеры показывают использование конкретных возможностей и не всегда содержат полную настройку приложения. Если пример зависит от уже созданного Runtime, ECS-мира, графического устройства или другого сервиса, это должно учитываться при его использовании.

Для понимания общей архитектуры движка смотри [ENGINE.md](ENGINE.md). Здесь основное внимание уделяется тому, как программист игры использует API на практике.

### 2. ECS
## Сущности и их жизненный цикл

Сущность (`EntityId`) — это идентификатор игрового объекта в ECS. Сама сущность не содержит игровую логику или данные: они представлены компонентами, которые будут рассмотрены далее.

Для работы с сущностями используется `Engine.ECS.World`.

### Создание сущности

```csharp
var world = new Engine.ECS.World();

var entity = world.CreateEntity();
```

Метод `CreateEntity()` создаёт сущность и возвращает её идентификатор (`EntityId`).

### Проверка существования

Перед выполнением операций с сущностью можно проверить, существует ли она в текущем мире:

```csharp
if (world.Exists(entity))
{
    // Сущность существует.
}
```

Проверка также позволяет обнаружить идентификатор сущности, которая уже была удалена.

### Удаление сущности

```csharp
var removed = world.DestroyEntity(entity);
```

`DestroyEntity()` возвращает `true`, если сущность была удалена, и `false`, если она не существовала.

При удалении сущности ECS автоматически удаляет все её компоненты. Дополнительно мир публикует событие `EntityDestroyed`.

### Важные правила

- `EntityId` — это идентификатор, а не самостоятельный игровой объект с поведением.
- После удаления сущности не следует продолжать использовать её старый идентификатор как действительный.
- Если сущность больше не существует, `DestroyEntity()` не выполняет повторное удаление и возвращает `false`.

Создание и удаление сущностей обычно выполняется игровым кодом в соответствии с правилами конкретной игры.
## Собственные компоненты игры

Компонент (`Component`) — это структура данных, прикреплённая к сущности. В VibeEngine2 игровые компоненты создаются непосредственно в проекте игры.

Компонент должен быть структурой (`struct`). Обычно он содержит данные, которые используются игровыми системами: здоровье, скорость, запас ресурсов, состояние производства и другие игровые характеристики.

### Объявление компонента

Например, создадим компонент для хранения здоровья игрового объекта:

```csharp
public struct Health
{
    public int Value;
}
```

Компонент не содержит игровой логики. Он хранит только значение здоровья, а правила его изменения определяет игровая система.

### Добавление компонента

Для добавления компонента используется метод `World.Add<T>()`:

```csharp
world.Add(
    entity,
    new Health
    {
        Value = 100
    });
```

После выполнения операции сущность получает компонент `Health` со значением здоровья `100`.

У одной сущности может быть несколько компонентов разных типов.

### Проверка наличия компонента

Перед обращением к компоненту можно проверить, прикреплён ли он к сущности:

```csharp
if (world.Has<Health>(entity))
{
    // Компонент Health существует.
}
```

Метод `Has<T>()` возвращает `true`, если сущность существует и содержит указанный компонент.

### Получение и изменение данных

Метод `World.Get<T>()` возвращает компонент по ссылке (`ref`). Благодаря этому можно изменять данные непосредственно в ECS, не добавляя компонент повторно.

```csharp
if (world.Has<Health>(entity))
{
    ref var health =
        ref world.Get<Health>(entity);

    health.Value -= 10;
}
```

В результате здоровье уменьшается на 10.

Обращение через `ref` позволяет изменять компонент непосредственно в хранилище ECS. Поэтому важно не терять `ref`, когда требуется изменить существующие данные.

### Удаление компонента

Чтобы удалить отдельный компонент, используй `World.Remove<T>()`:

```csharp
world.Remove<Health>(entity);
```

Удаление компонента не уничтожает саму сущность. Остальные компоненты сущности сохраняются.

### Основные правила

- Компоненты игры принадлежат игровому проекту, а не движку.
- Компоненты предназначены для хранения данных, а системы — для выполнения логики.
- Для получения компонента используй `Get<T>()`, а перед обращением при необходимости проверяй его наличие через `Has<T>()`.
- Для изменения существующего компонента используй `ref`, чтобы изменить данные непосредственно в ECS.

## Queries

Query позволяет перебирать сущности, которые содержат определённый компонент, не проверяя каждую сущность вручную.

Используй Query, когда необходимо обработать все подходящие игровые объекты: например, обновить здоровье, переместить объекты или рассчитать производство ресурсов.

### Чтение и изменение компонентов

Для обработки с возможностью изменения данных используется `World.Query<T>()`.

```csharp
foreach (var item in world.Query<Health>())
{
    var entity = item.Entity;

    ref var health = ref item.Component;

    health.Value -= 1;
}
```

В этом примере перебираются сущности с компонентом `Health`, и здоровье каждой из них уменьшается на единицу.

Каждый элемент Query предоставляет:

- `Entity` — идентификатор сущности;
- `Component` — ссылку на компонент, доступную для изменения.

Обращение через `ref` позволяет изменять данные непосредственно в ECS.

### Только чтение

Если данные не требуется изменять, используй `World.QueryReadOnly<T>()`.

```csharp
foreach (var item in world.QueryReadOnly<Health>())
{
    var entity = item.Entity;

    ref readonly var health = ref item.Component;

    // Использование health.Value без изменения компонента.
}
```

`QueryReadOnly<T>()` предоставляет компонент по ссылке только для чтения. Это подходящий вариант для логики, которой необходимо анализировать состояние игровых объектов, не изменяя его.

### Запрос по нескольким компонентам

Если системе необходимы сразу несколько компонентов одной сущности, можно использовать `Query<T1, T2>()` или `QueryReadOnly<T1, T2>()`.

Такие запросы возвращают только сущности, у которых присутствуют оба указанных компонента.

### Как выбрать Query

- `Query<T>()` — когда компонент нужно читать и изменять.
- `QueryReadOnly<T>()` — когда компонент используется только для чтения.
- Запросы по нескольким типам компонентов — когда обработка зависит от совместного наличия нескольких компонентов у одной сущности.

Queries удобны для массовой обработки данных и часто используются внутри игровых систем, которые будут рассмотрены в следующем разделе.

### 3. Игровые системы
## IUpdateSystem и IFixedUpdateSystem

Игровая система (`System`) — это класс, который выполняет определённую часть игровой логики. Например, система может обрабатывать движение, обновлять состояние объектов или рассчитывать производство ресурсов.

В VibeEngine2 есть два основных интерфейса для обновления игровых систем:

- `IUpdateSystem` — для обычного обновления.
- `IFixedUpdateSystem` — для логики, выполняемой на фиксированных шагах симуляции.

### Обычное обновление

Используй `IUpdateSystem`, когда логика должна выполняться при каждом обычном обновлении приложения.

```csharp
using Engine.Core.Systems;

public sealed class ExampleUpdateSystem : IUpdateSystem
{
    public void Update(SystemContext context)
    {
        var delta = context.Time.Delta;

        // Логика обычного обновления.
    }
}
```

Контекст `SystemContext` предоставляет информацию о времени:

- `context.Time.Delta` — длительность текущего обновления;
- `context.Time.Elapsed` — накопленное время;
- `context.Time.Tick` — текущий номер тика.

Длительность `Delta` можно получить в секундах через `context.Time.Delta.TotalSeconds`.

### Обновление фиксированным шагом

Используй `IFixedUpdateSystem`, когда логика должна выполняться на фиксированных шагах симуляции. Этот вариант подходит для физики и других вычислений, состояние которых необходимо обновлять с постоянной частотой.

```csharp
using Engine.Core.Systems;

public sealed class ExampleFixedSystem : IFixedUpdateSystem
{
    public void FixedUpdate(FixedSystemContext context)
    {
        var delta = context.Time.Delta;
        var tick = context.Time.Tick;

        // Логика фиксированного шага симуляции.
    }
}
```

`FixedSystemContext` предоставляет `SimulationTime`, содержащий:

- `context.Time.Delta` — длительность фиксированного шага в формате `Fixed32`;
- `context.Time.Tick` — номер текущего тика.

Фиксированный шаг позволяет отделить выполнение симуляции от частоты кадров. При этом сам по себе он не гарантирует детерминированность: она также зависит от выполняемой логики и используемых вычислений.

### Как выбрать интерфейс

Выбирай тип системы по характеру выполняемой работы.

Если логика должна реагировать на каждое обычное обновление, используй `IUpdateSystem`. Если она относится к состоянию симуляции и должна выполняться на фиксированных шагах, используй `IFixedUpdateSystem`.

Для логики, участвующей в детерминированной симуляции, особенно важно избегать зависимости результата от частоты кадров и недетерминированных внешних данных.


## Регистрация игровых систем

Чтобы движок выполнял игровую систему, её необходимо зарегистрировать в планировщике `runtime.Scheduler`.

При регистрации указывается экземпляр системы и фаза, в которой она должна выполняться.

Доступны две фазы:

- `SystemPhase.Update` — обычное обновление.
- `SystemPhase.FixedUpdate` — фиксированный шаг симуляции.

Выбранная фаза должна соответствовать интерфейсу, реализованному системой.

### Пример регистрации

Предположим, игра использует компонент для подсчёта количества тиков:

```csharp
public struct ProductionCounter
{
    public int Ticks;
}
```

Система увеличивает счётчик на каждом фиксированном шаге:

```csharp
using Engine.Core.Systems;
using Engine.ECS;

public sealed class ProductionTickSystem : IFixedUpdateSystem
{
    private readonly World _world;

    public ProductionTickSystem(World world)
    {
        ArgumentNullException.ThrowIfNull(world);
        _world = world;
    }

    public void FixedUpdate(FixedSystemContext context)
    {
        foreach (var item in _world.Query<ProductionCounter>())
        {
            ref var counter = ref item.Component;
            counter.Ticks++;
        }
    }
}
```

Здесь `World` — это ECS-мир, а `ProductionTickSystem` — игровая система, принадлежащая проекту игры.

Подключение к Runtime:

```csharp
var world = runtime.EcsWorld;

var entity = world.CreateEntity();

world.Add(
    entity,
    new ProductionCounter());

runtime.Scheduler.Add(
    new ProductionTickSystem(world),
    SystemPhase.FixedUpdate);

runtime.Initialize();
```

### Почему регистрация выполняется до Initialize()

Во время `runtime.Initialize()` движок строит план выполнения систем и проверяет их зависимости.

После построения плана регистрация новых систем и изменение порядка их выполнения недоступны. Поэтому игровые системы следует регистрировать до инициализации Runtime.

После инициализации система будет выполняться автоматически при обновлении соответствующей фазы Runtime. Вызовы обновления выполняются игровым циклом приложения.

### Важные правила

- Каждая система должна реализовывать интерфейс, соответствующий выбранной фазе.
- Один и тот же конкретный тип системы нельзя зарегистрировать повторно в одном планировщике.
- Система не начнёт выполняться только от создания её экземпляра: необходима регистрация и инициализация Runtime.

- ## Зависимости между системами

Иногда одной системе необходимо использовать результат работы другой. Например, система производства должна выполняться после системы движения, если расчёт производства зависит от обновлённого положения объектов.

Для задания порядка выполнения используется метод `.After<TSystem>()`.

### Пример

```csharp
var world = runtime.EcsWorld;

runtime.Scheduler.Add(
    new MovementSystem(world),
    SystemPhase.FixedUpdate);

runtime.Scheduler.Add(
    new ProductionTickSystem(world),
    SystemPhase.FixedUpdate)
    .After<MovementSystem>();
```

В этом примере `ProductionTickSystem` будет выполняться после `MovementSystem` в фазе `FixedUpdate`.

Зависимость не запускает другую систему вручную. Она сообщает планировщику, в каком порядке необходимо выполнять зарегистрированные системы.

### Правила зависимостей

- Обе системы должны быть зарегистрированы в одном `SystemScheduler`.
- Система, указанная в `.After<TSystem>()`, должна быть зарегистрирована.
- Обе системы должны принадлежать одной фазе выполнения.
- Циклические зависимости недопустимы, поскольку для них нельзя построить корректный порядок выполнения.

Если система зависит от результатов работы другой системы, указывай зависимость явно. Не полагайся на случайный или подразумеваемый порядок регистрации.

Также доступен метод `.Before<TSystem>()`, задающий обратное отношение: текущая система должна выполняться перед указанной системой.

Зависимости следует использовать только тогда, когда порядок действительно важен. Не нужно связывать все системы между собой без необходимости.

## Контексты обновления и время

При вызове системы движок передаёт ей контекст обновления. Через него система получает временные данные, необходимые для выполнения игровой логики.

Обычное и фиксированное обновления используют разные типы контекста.

### SystemContext

`SystemContext` передаётся в метод `Update()` и содержит `TimeSnapshot`:

```csharp
public void Update(SystemContext context)
{
    var delta = context.Time.Delta;
    var elapsed = context.Time.Elapsed;
    var tick = context.Time.Tick;

    // Логика обычного обновления.
}
```

Основные значения:

- `Delta` — длительность текущего обновления.
- `Elapsed` — накопленное время с начала работы игрового цикла.
- `Tick` — номер текущего тика симуляции.

`Delta` имеет тип `Duration`. Для получения длительности в секундах можно использовать `context.Time.Delta.TotalSeconds`.

### FixedSystemContext

`FixedSystemContext` передаётся в метод `FixedUpdate()` и содержит `SimulationTime`:

```csharp
public void FixedUpdate(FixedSystemContext context)
{
    var delta = context.Time.Delta;
    var tick = context.Time.Tick;

    // Логика фиксированного шага.
}
```

Основные значения:

- `Delta` — длительность фиксированного шага, представленная типом `Fixed32`.
- `Tick` — номер текущего тика симуляции.

Фиксированная длительность шага определяется настройкой `SimulationRate` и не зависит от длительности отдельного кадра.

### Как правильно использовать время

При реализации игровых систем учитывай назначение каждого контекста.

- Для логики обычного обновления используй `SystemContext`.
- Для логики, которая должна выполняться с постоянным шагом симуляции, используй `FixedSystemContext`.
- Не считай, что один кадр приложения всегда соответствует одному тику симуляции: за кадр может произойти несколько фиксированных обновлений или ни одного.

Для детерминированной игровой логики важно опираться на фиксированный шаг и избегать зависимости результата вычислений от частоты кадров.

## Фазы выполнения и игровой цикл

`SystemPhase` определяет, на каком этапе симуляции планировщик выполняет зарегистрированную систему.

В VibeEngine2 доступны две фазы:

- `SystemPhase.Update` — обычное обновление.
- `SystemPhase.FixedUpdate` — фиксированный шаг симуляции.

При регистрации фаза указывается явно:

```csharp
runtime.Scheduler.Add(
    new InterfaceUpdateSystem(),
    SystemPhase.Update);

runtime.Scheduler.Add(
    new WorldSimulationSystem(),
    SystemPhase.FixedUpdate);
```

Тип системы должен соответствовать выбранной фазе: первая система реализует `IUpdateSystem`, вторая — `IFixedUpdateSystem`.

### Как фазы связаны с игровым циклом

Игровой цикл (`GameLoop`) управляет последовательностью обновлений приложения. В типичном цикле VibeEngine2:

1. Выполняется обычное обновление приложения.
2. Выполняется ноль или несколько фиксированных шагов симуляции, в зависимости от накопленного времени.
3. Приложение выполняет рендеринг.

Таким образом, за один кадр может произойти несколько вызовов `FixedUpdate()` или ни одного.

Runtime не заменяет игровой цикл. Приложение связывает этапы своего жизненного цикла с соответствующими методами Runtime, а Runtime передаёт обновления планировщику систем.

### Что нужно учитывать

- Не используй `Update` как замену фиксированному шагу для логики, которой необходима постоянная частота симуляции.
- Не предполагай, что обычное обновление и фиксированный шаг вызываются одинаковое количество раз.
- Фаза `FixedUpdate` сама по себе не гарантирует детерминированность: для неё также важны детерминированные вычисления и порядок выполнения зависимых систем.

Выбирай фазу исходя из требований игровой логики, а не только из того, насколько часто требуется обновлять объект.

### 4. Simulation

## Назначение Simulation

`Simulation` объединяет механизмы выполнения игровой логики и управляет последовательностью основных операций симуляции.

В VibeEngine2 она связывает три основных механизма:

- **Systems** — выполнение зарегистрированных игровых систем.
- **Commands** — обработка игровых команд.
- **Events** — доставка событий подписчикам.

Получить доступ к симуляции через Runtime можно следующим образом:

```csharp
var simulation = runtime.Simulation;
```

### Как выполняется симуляция

На обычном обновлении (`Update`) Simulation выполняет системы фазы `SystemPhase.Update`, а затем обрабатывает ожидающие события.

На фиксированном шаге (`FixedUpdate`) последовательность другая:

1. Обрабатываются ожидающие команды.
2. Выполняются системы фазы `SystemPhase.FixedUpdate`.
3. Обрабатываются ожидающие события.

Таким образом, игровые команды могут изменять состояние до выполнения систем фиксированного шага, а события позволяют уведомлять другие части игры о произошедших изменениях.

### Ответственность игровой логики

Simulation предоставляет механизм выполнения, но не определяет содержание игровых действий.

Игра самостоятельно реализует:
- игровые команды и их обработчики;
- события и подписчиков;
- системы, изменяющие игровое состояние;
- правила, определяющие, когда и почему выполняется то или иное действие.

Это позволяет использовать одну и ту же инфраструктуру симуляции для разных игр, не добавляя игровые правила в Engine.

### Важные правила

- Перед выполнением обновлений Simulation необходимо инициализировать.
- Системы регистрируются до инициализации, поскольку во время неё строится план выполнения.
- Для игровой логики, требующей

## Фиксированные шаги симуляции

Фиксированный шаг определяет, как часто движок выполняет логику, относящуюся к состоянию симуляции.

В VibeEngine2 частота задаётся через `SimulationRate` — количество тиков симуляции в секунду.

### Настройка частоты

Частоту можно задать через `EngineRuntimeOptions` при создании Runtime:

```csharp
using Engine.Core.Time;
using Engine.Runtime;

var options = new EngineRuntimeOptions
{
    SimulationRate = new SimulationRate(30)
};
```

В этом примере симуляция настроена на 30 тиков в секунду.

По умолчанию используется частота **20 тиков в секунду**.

`SimulationRate` предоставляет два основных значения:

- `TicksPerSecond` — количество тиков в секунду.
- `TickDuration` — длительность одного тика в формате `Duration`.

Например, при частоте 30 тиков в секунду один фиксированный шаг длится приблизительно 33,3 миллисекунды.

### Частота симуляции и частота кадров

Частота тиков не равна частоте кадров (`FPS`).

Игровой цикл приложения использует накопленное время, чтобы определить, сколько фиксированных шагов нужно выполнить. Поэтому за один кадр может произойти несколько шагов симуляции или ни одного.

Это позволяет выполнять игровую логику с постоянной частотой независимо от частоты обновления изображения.

При настройке игрового цикла используй ту же частоту, что и у Runtime:

```csharp
var gameLoop = new GameLoop(
    application,
    runtime.SimulationRate);
```

Здесь `application` — объект игрового приложения, реализующий `IApplication`.

### Как выбирать частоту

Выбирай частоту, исходя из требований игры и характера симуляции.

Более высокая частота означает более частое обновление состояния, но также увеличивает объём вычислений. Более низкая частота снижает частоту вычислений, но может быть недостаточной для некоторых игровых механик.

Фиксированный шаг особенно полезен для физики, движения и других вычислений, которым нужна стабильная временная база.

Важно: фиксированная частота сама по себе не гарантирует детерминированность. Для этого также необходимо контролировать порядок выполнения систем, используемые вычисления и изменение состояния игры.

## Игровые команды

Команда (`ICommand`) представляет действие, которое необходимо передать на обработку симуляции.

Команды полезны, когда игровое действие должно выполняться в определённый момент симуляции, а не непосредственно в обработчике пользовательского ввода.

Например, нажатие кнопки игроком может сформировать команду на покупку предмета или изменение игрового состояния.

### Создание собственной команды

Команды определяются в проекте игры и реализуют `ICommand`.

```csharp
using Engine.Core.Commands;
using Engine.ECS.Entities;

public sealed record AddCreditsCommand(
    EntityId Entity,
    int Amount) : ICommand;
```

В этом примере команда содержит идентификатор сущности и количество начисляемых игровых очков. Само значение `Credits` — понятие игры, а `ICommand` — механизм движка.

### Обработчик команды

Для выполнения команды реализуй `ICommandHandler<TCommand>`.

```csharp
using Engine.Core.Commands;
using Engine.ECS;
using Engine.ECS.Entities;

public struct Credits
{
    public int Value;
}

public sealed class AddCreditsHandler :
    ICommandHandler<AddCreditsCommand>
{
    private readonly World _world;

    public AddCreditsHandler(World world)
    {
        ArgumentNullException.ThrowIfNull(world);
        _world = world;
    }

    public void Handle(AddCreditsCommand command)
    {
        if (!_world.Exists(command.Entity) ||
            !_world.Has<Credits>(command.Entity))
        {
            return;
        }

        ref var credits =
            ref _world.Get<Credits>(command.Entity);

        credits.Value += command.Amount;
    }
}
```

Обработчик определяет, что именно означает команда и как она изменяет игровое состояние.

### Регистрация и отправка команды

Зарегистрируй обработчик до инициализации Runtime:

```csharp
var world = runtime.EcsWorld;

var entity = world.CreateEntity();

world.Add(
    entity,
    new Credits());

var commandSubscription =
    runtime.Simulation.CommandDispatcher.Register(
        new AddCreditsHandler(world));

runtime.Initialize();
```

Объект `commandSubscription` необходимо сохранять, пока обработчик должен работать. Его освобождение через `Dispose()` отменяет регистрацию обработчика.

Отправить команду можно следующим образом:

```csharp
runtime.Simulation.Submit(
    new AddCreditsCommand(entity, 25));
```

`Submit()` помещает команду в очередь симуляции. Команда будет обработана на следующем фиксированном шаге до выполнения систем `FixedUpdate`.

### Важные правила

- Каждому используемому типу команды нужен зарегистрированный обработчик.
- Для одного конкретного типа команды регистрируется только один обработчик.
- `Submit()` вызывается после инициализации Simulation.
- Если для команды не зарегистрирован обработчик, её обработка завершается ошибкой.
- Проверяй актуальность сущности и наличие необходимых компонентов внутри обработчика, если команда зависит от состояния ECS.

Команды позволяют отделить момент возникновения игрового действия от момента изменения состояния симуляции.

## События

События (`IEvent`) позволяют одной части игры сообщить другим частям о произошедшем событии, не вызывая их напрямую.

Например, система производства может сообщить о завершении производства, а другие системы — обновить статистику, воспроизвести звук или показать уведомление.

Для работы с событиями используется `EventBus`, доступный через `runtime.Events`.

### Создание собственного события

События определяются в проекте игры и реализуют `IEvent`.

```csharp
using Engine.Core.Events;
using Engine.ECS.Entities;

public sealed record ProductionCompletedEvent(
    EntityId Entity,
    int Amount) : IEvent;
```

Событие содержит данные о завершившемся производстве. Его смысл определяется игрой, а `EventBus` предоставляет механизм доставки подписчикам.

### Подписка на событие

Чтобы получать события определённого типа, используй `Subscribe<TEvent>()`.

```csharp
var subscription =
    runtime.Events.Subscribe<ProductionCompletedEvent>(
        productionEvent =>
        {
            Console.WriteLine(
                $"Production completed: {productionEvent.Amount}");
        });
```

Обработчик будет вызван при обработке опубликованного события соответствующего типа.

Подписка возвращает `EventSubscription`. Сохраняй её, пока обработчик должен получать события. При завершении работы с подпиской вызови `Dispose()`:

```csharp
subscription.Dispose();
```

### Публикация события

Для публикации используется `Publish()`:

```csharp
runtime.Events.Publish(
    new ProductionCompletedEvent(entity, 10));
```

Вызов `Publish()` помещает событие в очередь. Обработчики не вызываются непосредственно в момент публикации.

Simulation обрабатывает ожидающие события после выполнения систем обычного обновления и после выполнения систем фиксированного шага.

### События и команды

Команды и события решают разные задачи.

- **Команда** передаёт действие, которое необходимо выполнить. Например, построить объект или потратить ресурсы.
- **Событие** сообщает о произошедшем факте. Например, объект построен или производство завершено.

Такое разделение помогает уменьшить связанность игровой логики: система может публиковать событие, не зная, какие именно части игры отреагируют на него.

### Важные правила

Пользовательские события должны реализовывать IEvent.

Публикация события и вызов его обработчиков происходят в разные моменты.

Подписка должна оставаться активной до момента, когда обработчику больше не требуется получать события.

При обработке события учитывай, что состояние игры могло измениться с момента его публикации.

## Детерминированное состояние

Детерминированное состояние — это данные, которые участвуют в вычислении хеша состояния симуляции. Такой хеш можно использовать для сравнения состояния игры между запусками или участниками сетевой симуляции и для обнаружения рассинхронизации.

Для подключения собственных игровых данных используется интерфейс `IDeterministicState`.

### Реализация собственного состояния

Например, игра может хранить количество кредитов и текущий уровень:

```csharp
using Engine.Core.Determinism;

public sealed class GameState : IDeterministicState
{
    public int Credits { get; set; }

    public int Level { get; set; }

    public void AddToHash(
        ref DeterministicStateHasher hasher)
    {
        hasher.AddInt32(Credits);
        hasher.AddInt32(Level);
    }
}
```

Метод `AddToHash()` определяет, какие данные объекта участвуют в вычислении хеша. Для каждого поля необходимо использовать подходящий метод `DeterministicStateHasher`.

Порядок добавления данных должен оставаться стабильным: одинаковое состояние при одинаковом порядке добавления должно приводить к одинаковому результату хеширования.

### Регистрация состояния

Зарегистрируй собственное состояние до инициализации Runtime:

```csharp
var gameState = new GameState
{
    Credits = 100,
    Level = 1
};

runtime.Simulation.RegisterDeterministicState(
    gameState);

runtime.Initialize();
```

Runtime автоматически включает в детерминированное состояние ECS-мир, пространственный мир и настройки физики. Дополнительные данные игры необходимо регистрировать самостоятельно.

После инициализации регистрировать новое детерминированное состояние нельзя.

### Получение хеша

После инициализации симуляции можно получить хеш её текущего состояния:

```csharp
var hash = runtime.GetStateHash();

Console.WriteLine(hash.Value);
```

`GetStateHash()` учитывает все зарегистрированные реализации `IDeterministicState`, включая собственное состояние игры.

Если игровое состояние изменяется, значение хеша может измениться.

### Важные правила

- Регистрируй все данные, влияющие на результат симуляции, если они не включены в другие зарегистрированные состояния.
- Не включай данные, не влияющие на симуляцию, например положение элементов интерфейса или оформление окна.
- Обеспечивай одинаковый порядок регистрации состояний и одинаковый порядок добавления полей при хешировании.
- Не используй хеш как замену сохранению игры: он позволяет сравнивать состояние, но не восстанавливает его.

Сам по себе хеш не гарантирует детерминированность. Он помогает обнаруживать расхождения, но не исправляет их.

## Хеширование состояния симуляции

Хеширование позволяет получить компактное числовое представление текущего детерминированного состояния симуляции.

В VibeEngine2 для этого используется `DeterministicStateHash`. Runtime вычисляет хеш на основе зарегистрированных реализаций `IDeterministicState`.

### Получение хеша

После инициализации Runtime можно получить хеш текущего состояния:

```csharp
var hash = runtime.GetStateHash();

Console.WriteLine(
    $"State hash: {hash.Value:X16}");
```

`hash.Value` содержит числовое значение хеша типа `ulong`. В примере оно выводится в шестнадцатеричном формате.

Хеш отражает состояние на момент вызова `GetStateHash()`. Если влияющие на него данные изменились, хеш может измениться.

### Сравнение состояний

Хеши можно сравнивать, чтобы проверить, совпадает ли состояние симуляции в двух контрольных точках:

```csharp
var firstHash = runtime.GetStateHash();

// Выполнение игровой логики и изменение состояния.

var secondHash = runtime.GetStateHash();

if (firstHash != secondHash)
{
    // Детерминированное состояние изменилось.
}
```

Изменение хеша само по себе не означает ошибку: игровое состояние закономерно меняется по мере выполнения симуляции.

Для обнаружения рассинхронизации сравнивай хеши в соответствующих точках выполнения, например на одном и том же тике у двух участников сетевой симуляции.

### Что необходимо учитывать

- Хеширование доступно после инициализации симуляции.
- В результат входят только данные, учтённые зарегистрированными реализациями `IDeterministicState`.
- Совпадение хешей не является математическим доказательством полного равенства состояний: разные состояния теоретически могут иметь одинаковый хеш.
- Хеш не содержит данных, необходимых для восстановления игры, и не заменяет сохранение состояния.

Хеширование — это диагностический механизм, помогающий сравнивать состояние симуляции и выявлять потенциальную рассинхронизацию. Оно не делает игровую логику детерминированной автоматически.

### 5. Интеграция Runtime и игровой цикл
## EngineRuntime и его назначение

`EngineRuntime` объединяет основные подсистемы движка в одном окружении, с которым работает игровое приложение.

Он создаёт ECS-мир, пространственный мир, симуляцию, планировщик систем, физику и runtime скриптов, а также регистрирует необходимые встроенные системы.

### Доступ к подсистемам

После создания Runtime игровые системы и приложение могут обращаться к его подсистемам через публичные свойства:

```csharp
var ecsWorld = runtime.EcsWorld;
var world = runtime.World;

var simulation = runtime.Simulation;
var scheduler = runtime.Scheduler;

var physics = runtime.Physics;
var scripts = runtime.Scripts;
```

Эти свойства предоставляют доступ к существующим экземплярам подсистем Runtime. Не нужно создавать отдельный ECS-мир или планировщик только для того, чтобы использовать игровые системы вместе со встроенными системами движка.

### Что делает Runtime, а что — приложение

`EngineRuntime` отвечает за объединение runtime-механизмов движка и предоставляет API для их использования.

Само игровое приложение определяет:

- какие игровые компоненты, системы и правила использовать;
- как организовать пользовательский ввод и игровое поведение;
- как связать Runtime с жизненным циклом приложения;
- как организовать отрисовку конкретной игры.

Runtime не заменяет игровое приложение и не запускает собственный игровой цикл. Он предоставляет методы обновления, которые приложение вызывает в нужные моменты.

Такое разделение позволяет использовать одну runtime-инфраструктуру для разных игр, не помещая их специфическую логику внутрь движка.

## Подключение сервисов

`EngineRuntimeServices` передаёт Runtime сервисы, которые создаются и обслуживаются приложением.

Это позволяет Runtime использовать графику, ввод, камеру, аудио и Content, не создавая самостоятельно конкретные реализации этих подсистем.

### Создание EngineRuntimeServices

Для обычного приложения необходимо передать пять сервисов:

```csharp
using Engine.Runtime;

var services = new EngineRuntimeServices(
    graphics,
    input,
    camera,
    audio,
    content);
```

Здесь:

- `graphics` — объект, реализующий `IGraphicsDevice`;
- `input` — объект, реализующий `IInput`;
- `camera` — экземпляр `Camera2D`;
- `audio` — объект, реализующий `IAudioManager`;
- `content` — объект, реализующий `IContentManager`.

Все эти объекты должны быть созданы приложением до создания `EngineRuntimeServices`.

При необходимости можно дополнительно передать `InputActionMap` — карту игровых действий ввода.

### Передача сервисов в Runtime

Созданный контейнер сервисов передаётся в конструктор `EngineRuntime`:

```csharp
var options = new EngineRuntimeOptions();

using var runtime = new EngineRuntime(
    options,
    services);
```

Runtime использует переданные экземпляры, а не создаёт их повторно.

### Владение сервисами

Передача сервиса в `EngineRuntimeServices` не означает передачи владения им в Runtime.

Приложение отвечает за время жизни переданных сервисов и освобождение ресурсов, которыми оно владеет. `EngineRuntime.Dispose()` освобождает принадлежащие Runtime объекты, но не вызывает `Dispose()` у переданных сервисов.

Поэтому при организации завершения работы приложения важно соблюдать порядок освобождения ресурсов и не уничтожать сервисы, пока Runtime ещё использует их.

### Важное замечание

Для обычного приложения с включённым tooling передавай полностью настроенный `EngineRuntimeServices`. Конструктор `EngineRuntime(options)` без сервисов не подходит для стандартного режима с включённым tooling: при создании Runtime требуется доступ к графическому сервису.

Конкретные реализации сервисов и их backend выбираются на уровне приложения, а не внутри игровой логики.

## Инициализация, обновление и завершение работы

`EngineRuntime` предоставляет методы для управления жизненным циклом runtime-части движка:

- `Initialize()` — инициализирует симуляцию и строит план выполнения систем.
- `Update(SystemContext context)` — выполняет обычное обновление.
- `FixedUpdate(FixedSystemContext context)` — выполняет фиксированный шаг симуляции.
- `Shutdown()` — завершает работу симуляции.
- `Dispose()` — освобождает ресурсы, которыми владеет Runtime.

### Инициализация

До вызова `Initialize()` необходимо зарегистрировать собственные игровые системы и подключить другие данные, регистрация которых требует неинициализированной симуляции.

```csharp
var runtime = new EngineRuntime(
    options,
    services);

// Регистрация игровых систем и состояния.
// ...

runtime.Initialize();
```

После инициализации планировщик построен. Добавлять новые системы в него уже нельзя.

### Обновление

Runtime не запускает игровой цикл самостоятельно. Приложение должно вызывать его методы в соответствии с этапами своего игрового цикла.

Обычное обновление передаёт контекст `SystemContext`:

```csharp
runtime.Update(
    new SystemContext(timeSnapshot));
```

Фиксированный шаг передаёт контекст `FixedSystemContext`:

```csharp
runtime.FixedUpdate(
    new FixedSystemContext(simulationTime));
```

Здесь `timeSnapshot` и `simulationTime` — временные данные, полученные от игрового цикла приложения.

В стандартной архитектуре VibeEngine2 за управление временем отвечает `GameLoop`. Он вызывает методы приложения, передавая временные данные. Приложение связывает эти вызовы с соответствующими методами Runtime.

### Связь с IApplication

`EngineRuntime` не реализует `IApplication`. Поэтому приложение должно выступать связующим звеном между игровым циклом и Runtime.

Минимальный пример:

```csharp
using Engine.Core.Application;
using Engine.Core.Systems;
using Engine.Core.Time;
using Engine.Runtime;

public sealed class RuntimeApplication : IApplication
{
    private readonly EngineRuntime _runtime;

    public RuntimeApplication(EngineRuntime runtime)
    {
        _runtime = runtime;
    }

    public void Initialize()
    {
        _runtime.Initialize();
    }

    public void Update(TimeSnapshot time)
    {
        _runtime.Update(
            new SystemContext(time));
    }

    public void FixedUpdate(SimulationTime time)
    {
        _runtime.FixedUpdate(
            new FixedSystemContext(time));
    }

    public void Render(double interpolationAlpha)
    {
        // Здесь приложение выполняет отрисовку игры.
    }

    public void Shutdown()
    {
        _runtime.Shutdown();
    }
}
```

Этот класс показывает связь жизненного цикла. В реальном проекте он может быть частью существующей архитектуры приложения или его состояний — создавать отдельный класс исключительно ради этого примера необязательно.

### Завершение работы и освобождение ресурсов

После завершения игрового цикла симуляцию необходимо корректно остановить. Затем следует освободить Runtime:

```csharp
using var runtime = new EngineRuntime(
    options,
    services);
```

`Dispose()` автоматически завершает симуляцию, если она была инициализирована и ещё не остановлена. При этом `Dispose()` можно использовать как дополнительную гарантию освобождения ресурсов, даже если завершение работы пошло не по обычному сценарию.

Runtime освобождает собственные ресурсы, ECS-мир, пространственный мир и ресурсы скриптов. Переданные через `EngineRuntimeServices` сервисы остаются ответственностью приложения.

**Основное правило:** игровой цикл определяет, когда выполнять обновления и рендеринг; Runtime выполняет соответствующую работу движка. Эти две ответственности не следует смешивать.

## Ответственность игрового приложения и движка

При разработке игры важно разделять ответственность движка, игрового кода и приложения, которое связывает их между собой.

### Engine

Engine предоставляет универсальные механизмы, которые могут использовать разные игры:

- ECS и планировщик систем;
- симуляцию и фиксированные шаги;
- физику и пространственные преобразования;
- графические, аудио- и input-абстракции;
- загрузку ресурсов и инструменты диагностики.

Engine не определяет правила конкретной игры.

### Game

Игровой проект определяет содержание игры и способы использования API движка.

К Game относятся:

- собственные компоненты и системы;
- игровые команды и события;
- правила взаимодействия объектов;
- игровые состояния и условия победы или поражения;
- обработка игровых действий и специфические механики.

Например, движок предоставляет ECS и физику, а игра решает, какие объекты столкнутся, какой эффект это окажет на игровой процесс и какие правила должны применяться.

### Application

Приложение связывает игровые механизмы с окружением, в котором запускается игра.

Оно отвечает за задачи уровня приложения:

- создание окна и конкретных backend-реализаций;
- подготовку сервисов и передачу их в `EngineRuntimeServices`;
- подключение Runtime к игровому циклу;
- организацию отрисовки и представления игры;
- управление жизненным циклом и освобождение принадлежащих приложению ресурсов.

В существующей архитектуре `GameLoop` работает с `IApplication`, а приложение связывает его вызовы с `EngineRuntime`. Сам `EngineRuntime` не реализует `IApplication` и не запускает игровой цикл самостоятельно.

### Общая схема

```text
Application
    ├── GameLoop
    ├── EngineRuntime
    └── Game
         ├── Components
         ├── Systems
         ├── Commands
         └── Game Rules
```

Это логическая схема ответственности, а не требование создавать именно такие классы или структуру каталогов в каждом проекте.

**Основное правило:** движок предоставляет механизмы, игра определяет игровое поведение, а приложение организует их совместную работу.

### 6. World и Chunks
## Назначение World и отличие от EcsWorld

VibeEngine2 разделяет хранение ECS-данных и управление пространственным миром.

`runtime.EcsWorld` предоставляет ECS: сущности, компоненты и запросы для работы с ними.

`runtime.World` предоставляет пространственную инфраструктуру: чанки, их содержимое, координаты и пространственный индекс сущностей.

Оба механизма связаны между собой. Пространственный мир использует тот же экземпляр ECS-мира, который доступен через `runtime.EcsWorld`.

### Доступ к мирам

```csharp
var ecsWorld = runtime.EcsWorld;
var world = runtime.World;
```

Используй `EcsWorld`, когда необходимо создавать сущности, добавлять компоненты или обрабатывать их через ECS.

Используй `World`, когда необходимо работать с чанками, преобразовывать координаты или получать сущности по их пространственному расположению.

### Основные свойства пространственного мира

```csharp
var chunkSize = world.ChunkSize;
var chunkCount = world.ChunkCount;
```

- `ChunkSize` — размеры чанка в единицах его сетки.
- `ChunkCount` — количество загруженных чанков.

Размер чанка задаётся при создании Runtime через `EngineRuntimeOptions`. По умолчанию используется размер `32 × 32`.

### Пространственное размещение сущностей

Для создания ECS-сущности с пространственной позицией можно использовать `world.SpatialEntities`:

```csharp
using Engine.Worlds.Spatial;

var entity = world.SpatialEntities.CreateEntity(
    new WorldPosition(10, 20));
```

Этот метод создаёт сущность в ECS-мире, назначает ей компонент пространственной позиции и регистрирует её в пространственном индексе.

Таким образом, ECS отвечает за данные сущности, а пространственный мир обеспечивает механизмы её пространственного размещения и поиска.

Важно не путать `WorldPosition` с `Transform2D`: первая задаёт целочисленные координаты пространственной сетки, а второй тип предназначен для пространственных преобразований. Они решают разные задачи и не заменяют друг друга.

## Создание и получение чанков

Чанк (`Chunk`) — это область пространственного мира с заданными размерами и собственным хранилищем тайлов.

Для работы с чанками используется `runtime.World`. Позиция чанка задаётся структурой `ChunkPosition`, содержащей целочисленные координаты X и Y.

### Создание чанка

Для создания нового чанка используется `CreateChunk()`:

```csharp
using Engine.Worlds.Spatial;

var world = runtime.World;

var position = new ChunkPosition(0, 0);

var chunk = world.CreateChunk(position);
```

Метод создаёт чанк с размерами, заданными в настройках пространственного мира, и регистрирует его в `World`.

Если чанк с такой позицией уже зарегистрирован, метод выбрасывает `InvalidOperationException`.

### Получение загруженного чанка

Если чанк может отсутствовать, используй `TryGetChunk()`:

```csharp
if (world.TryGetChunk(
        position,
        out var chunk))
{
    // Чанк загружен и доступен.
}
```

Метод возвращает `true`, если чанк зарегистрирован и загружен. В противном случае возвращает `false`.

### Получение или создание

Если необходимо получить существующий загруженный чанк или создать новый, используй `GetOrCreateChunk()`:

```csharp
var chunk = world.GetOrCreateChunk(position);
```

Метод возвращает существующий загруженный чанк либо создаёт его, если указанная позиция ещё не зарегистрирована.

**Важно:** если чанк уже зарегистрирован, но находится в состоянии `Unloaded`, `GetOrCreateChunk()` выбрасывает `InvalidOperationException`. Этот метод не загружает данные из хранилища автоматически.

### Получение данных чанка

У загруженного чанка доступно хранилище тайлов:

```csharp
var tiles = chunk.Tiles;

var tile = tiles.Get(
    new LocalPosition(0, 0));

tiles.Set(
    new LocalPosition(0, 0),
    tile);
```

`LocalPosition` задаёт координаты внутри чанка. Допустимые координаты начинаются с нуля и ограничены размерами чанка.

### Разница между отсутствующим и выгруженным чанком

В пространственном мире важно различать два состояния:

- **Чанк отсутствует в реестре.** Для указанной позиции нет зарегистрированной записи.
- **Чанк зарегистрирован, но выгружен.** Запись существует, однако данные чанка не находятся в загруженном объекте `Chunk`.

Эти состояния требуют разной обработки. Отсутствующий чанк можно создать через `CreateChunk()` или `GetOrCreateChunk()`. Для зарегистрированного выгруженного чанка нужно использовать соответствующий механизм загрузки, а не пытаться создать его повторно.

Не путай выгрузку чанка с удалением: выгрузка освобождает загруженные данные, сохраняя запись и состояние чанка, тогда как удаление убирает чанк из реестра.

## Координаты мира и чанков

Пространственный мир VibeEngine2 использует три типа координат:

- `WorldPosition` — целочисленная позиция в пространственной сетке мира.
- `ChunkPosition` — координаты чанка в сетке чанков.
- `LocalPosition` — координаты внутри отдельного чанка.

Все три типа находятся в пространстве имён `Engine.Worlds.Spatial`.

### Преобразование координат

Для преобразования между координатами используются методы `World`:

- `GetChunkPosition(WorldPosition)` — определяет чанк, которому принадлежит позиция мира.
- `GetLocalPosition(WorldPosition)` — определяет локальную позицию внутри этого чанка.
- `ToWorldPosition(ChunkPosition, LocalPosition)` — восстанавливает позицию мира по координатам чанка и локальной позиции.

Пример для чанков размером `32 × 32`:

```csharp
using Engine.Worlds.Spatial;

var world = runtime.World;

var position = new WorldPosition(70, 35);

var chunkPosition =
    world.GetChunkPosition(position);

var localPosition =
    world.GetLocalPosition(position);
```

Для этого примера результат будет следующим:

```text
WorldPosition: (70, 35)
ChunkPosition: (2, 1)
LocalPosition: (6, 3)
```

Чтобы получить исходную позицию обратно:

```csharp
var restoredPosition =
    world.ToWorldPosition(
        chunkPosition,
        localPosition);
```

`restoredPosition` будет равен исходному `position`.

### Работа с отрицательными координатами

Пространственный мир поддерживает отрицательные координаты. При определении чанка используется деление с округлением вниз, а не обычное целочисленное деление с округлением к нулю.

Например, при размере чанка `32 × 32`:

```text
WorldPosition: (-1, 0)
ChunkPosition: (-1, 0)
LocalPosition: (31, 0)
```

Таким образом, позиция `-1` принадлежит чанку `-1`, а локальная координата внутри этого чанка равна `31`.

Это особенно важно для миров, в которых игровые объекты могут располагаться по обе стороны от начала координат.

### Ограничения локальных координат

Локальная позиция должна находиться внутри границ чанка. При размере `32 × 32` допустимый диапазон по каждой оси — от `0` до `31` включительно.

Метод `ToWorldPosition()` проверяет локальные координаты и выбрасывает `ArgumentOutOfRangeException`, если они выходят за границы чанка.

**Важно:** эти координаты относятся к целочисленной пространственной сетке. Они не заменяют `Transform2D`, который используется для пространственных преобразований игровых объектов.

## Работа с игровым пространством

`World` предоставляет дополнительные механизмы для работы с пространственной структурой мира: поиска соседних чанков и получения сущностей, зарегистрированных в пространственном индексе определённого чанка.

### Получение соседнего чанка

Для поиска соседнего загруженного чанка используй `TryGetNeighbor()`:

```csharp
using Engine.Worlds.Spatial;

var position = new ChunkPosition(0, 0);

if (world.TryGetNeighbor(
        position,
        1,
        0,
        out var neighbor))
{
    // Соседний загруженный чанк доступен.
}
```

Параметры `offsetX` и `offsetY` задают смещение относительно исходного чанка.

Например:

- `(1, 0)` — справа;
- `(-1, 0)` — слева;
- `(0, 1)` — сверху по оси Y;
- `(0, -1)` — снизу по оси Y;
- `(1, 1)` — по диагонали.

Метод возвращает `true`, если в вычисленной позиции есть доступный загруженный чанк. Он не создаёт и не загружает соседние чанки автоматически.

### Поиск сущностей в чанке

Для получения сущностей, зарегистрированных в пространственном индексе определённого чанка и имеющих необходимый компонент, используй `World.Query<T>()`.

```csharp
foreach (var item in world.Query<Health>(
             new ChunkPosition(0, 0)))
{
    var entity = item.Entity;

    ref var health = ref item.Component;

    // Обработка сущности и её здоровья.
}
```

В отличие от `EcsWorld.Query<T>()`, который ищет сущности по наличию компонента во всём ECS-мире, пространственный запрос дополнительно ограничивает выборку сущностями из указанного чанка.

Для корректного поиска сущность должна быть зарегистрирована в пространственном индексе. Для этого используй `world.SpatialEntities`, например `CreateEntity()` или `SetPosition()`.

### Важные различия

- `TryGetNeighbor()` проверяет наличие загруженного чанка.
- `World.Query<T>()` использует пространственный индекс и наличие компонента, а не проверяет только существование объекта `Chunk`.
- Обычный ECS-запрос и пространственный запрос решают разные задачи: первый работает с компонентами, второй дополнительно учитывает пространственное размещение сущностей.

Пространственные запросы полезны для локальной обработки игровых объектов, когда нет необходимости перебирать все сущности мира.

### 7. Transform и Hierarchy
## Пространственные преобразования

Пространственное преобразование (`Transform`) описывает положение, поворот и масштаб объекта в двумерном пространстве.

В VibeEngine2 структура `Transform2D` содержит три свойства:

- `Position` — положение объекта, представленное типом `Vector2`.
- `Rotation` — угол поворота в радианах.
- `Scale` — масштаб по осям X и Y.

`Transform2D` — это структура данных, а не готовая ECS-система или компонент. Она описывает преобразование, а игровой код определяет, где хранить его и как использовать.

### Создание преобразования

```csharp
using Engine.Core.Math;
using Engine.Transform;

var transform = new Transform2D(
    new Vector2(100.0f, 50.0f));
```

При создании через этот конструктор задаётся позиция, поворот устанавливается в `0`, а масштаб — в `(1, 1)`.

### Изменение свойств

```csharp
transform.Position =
    new Vector2(200.0f, 100.0f);

transform.Rotation = MathF.PI / 2.0f;

transform.Scale =
    new Vector2(2.0f, 2.0f);
```

В результате объект получает новую позицию, поворот на 90 градусов и удвоенный масштаб по обеим осям.

Для получения преобразования без смещения, поворота и изменения масштаба можно использовать `Transform2D.Identity`.

### Операции с преобразованиями

Для вычислений предусмотрен `TransformOperations2D`.

Например, чтобы преобразовать точку из локальных координат объекта в координаты его преобразования, используй `TransformPoint()`:

```csharp
var point = TransformOperations2D.TransformPoint(
    transform,
    new Vector2(10.0f, 0.0f));
```

Метод учитывает масштаб и поворот точки, а затем прибавляет позицию преобразования.

Для объединения родительского и локального преобразований предусмотрен метод `Combine()`. Его использование будет рассмотрено в подразделе о Local и World Transform.

### Важное замечание

Наличие `Transform2D` само по себе не перемещает сущность в игре и не изменяет её отображение. Это данные и операции над ними. Чтобы преобразование влияло на игровое поведение или отрисовку, соответствующая система должна использовать его.

## Local и World Transform

В иерархии объектов преобразование может задавать положение относительно родителя или положение непосредственно в мировом пространстве.

В VibeEngine2 для этого используются два ECS-компонента:

- `LocalTransform2D` — локальные позиция, поворот и масштаб объекта.
- `WorldTransform2D` — итоговые позиция, поворот и масштаб объекта в мировом пространстве.

Оба компонента находятся в пространстве имён `Engine.ECS.Components` и используют фиксированную арифметику через `FixedTransform2D`.

### Локальное преобразование

`LocalTransform2D` описывает преобразование относительно родителя. Если у объекта нет родителя, его локальное преобразование становится мировым.

```csharp
using Engine.Core.Math;
using Engine.ECS;
using Engine.ECS.Components;
using Engine.Transform;

var world = new World();

var entity = world.CreateEntity();

world.Add(
    entity,
    new WorldTransform2D(
        FixedVector2.Zero));

world.Add(
    entity,
    new LocalTransform2D(
        new FixedTransform2D(
            new FixedVector2(
                Fixed32.FromInt(10),
                Fixed32.FromInt(20)))));
```

Здесь создаётся сущность с локальной позицией `(10, 20)`. Компонент `WorldTransform2D` также добавлен, поскольку система иерархии использует его для записи итогового преобразования.

### Связь с родителем

Для задания родителя используется `TransformParent2D`. Он хранит `EntityId` родительской сущности.

```csharp
var parent = world.CreateEntity();
var child = world.CreateEntity();

world.Add(
    parent,
    new WorldTransform2D(
        FixedVector2.Zero));

world.Add(
    parent,
    new LocalTransform2D(
        new FixedTransform2D(
            new FixedVector2(
                Fixed32.FromInt(10),
                Fixed32.FromInt(20)))));

world.Add(
    child,
    new WorldTransform2D(
        FixedVector2.Zero));

world.Add(
    child,
    new LocalTransform2D(
        new FixedTransform2D(
            new FixedVector2(
                Fixed32.FromInt(3),
                Fixed32.FromInt(4)))));

world.Add(
    child,
    new TransformParent2D(parent));
```

В этом примере локальная позиция дочернего объекта равна `(3, 4)`, а родитель имеет локальную позицию `(10, 20)`.

После вычисления иерархии мировая позиция дочернего объекта станет `(13, 24)`.

При наличии родителя также учитываются его поворот и масштаб.

### Вычисление иерархии

За вычисление итоговых преобразований отвечает `TransformHierarchySystem`. Это система фазы `FixedUpdate`, которая обрабатывает локальные преобразования и записывает результаты в `WorldTransform2D`.

В текущей реализации её необходимо зарегистрировать в планировщике до инициализации Runtime:

```csharp
using Engine.Core.Systems;
using Engine.ECS.Systems;

runtime.Scheduler.Add(
    new TransformHierarchySystem(
        runtime.EcsWorld),
    SystemPhase.FixedUpdate);
```

После регистрации и вызова `runtime.Initialize()` система будет пересчитывать преобразования на фиксированных шагах симуляции.

### Обязательные компоненты и ошибки

Для сущности, которую обрабатывает `TransformHierarchySystem`, необходимы `LocalTransform2D` и `WorldTransform2D`.

Если у сущности есть `TransformParent2D`, но нет `LocalTransform2D`, иерархия считается некорректной. Также ошибка возникает, если родитель отсутствует или не имеет `WorldTransform2D`.

Циклические ссылки между родителями также недопустимы.

**Важно:** добавление компонентов само по себе не вычисляет иерархию. Чтобы получить актуальный мировой результат, необходимо выполнить `TransformHierarchySystem`.

## Позиция, поворот и масштаб

Компоненты `LocalTransform2D` и `WorldTransform2D` предоставляют свойства `Position`, `Rotation` и `Scale`.

В отличие от обычного `Transform2D`, ECS-компоненты используют фиксированную арифметику:

- `Position` — тип `FixedVector2`.
- `Rotation` — тип `Fixed32`, угол в радианах.
- `Scale` — тип `FixedVector2`.

Это позволяет использовать фиксированную арифметику для пространственных данных симуляции.

### Изменение локального преобразования

Для изменения существующего компонента используй `World.Get<T>()` с `ref`:

```csharp
using Engine.Core.Math;
using Engine.ECS.Components;

ref var transform =
    ref runtime.EcsWorld.Get<LocalTransform2D>(entity);

transform.Position =
    new FixedVector2(
        Fixed32.FromInt(10),
        Fixed32.FromInt(20));

transform.Rotation =
    Fixed32.HalfPi;

transform.Scale =
    new FixedVector2(
        Fixed32.FromInt(2),
        Fixed32.One);
```

В этом примере локальная позиция устанавливается в `(10, 20)`, поворот — в 90 градусов, масштаб — в `(2, 1)`.

`Fixed32.HalfPi` представляет приближённое значение угла \(\pi/2\) радиан. Для перевода целых значений в `Fixed32` используется `Fixed32.FromInt()`, а для дробных — `Fixed32.FromFloat()`.

### Локальное и мировое преобразования

Если сущность участвует в иерархии, изменяй `LocalTransform2D`, чтобы задать её положение относительно родителя.

`WorldTransform2D` хранит итоговое преобразование в мировом пространстве. Для сущностей, которые обрабатываются `TransformHierarchySystem`, его значения вычисляются системой на фиксированном шаге симуляции.

Поэтому ручное изменение `WorldTransform2D` у такой сущности не заменяет изменение локального преобразования: при следующем обновлении иерархии значение может быть пересчитано.

### Масштаб и поворот

Масштаб задаётся отдельно для осей X и Y. Значение `FixedVector2.One` соответствует масштабу `(1, 1)`, то есть отсутствию изменения размера.

Поворот задаётся в радианах. В `Fixed32` доступны константы `Zero`, `HalfPi`, `Pi` и `TwoPi`.

**Важно:** само изменение Transform не гарантирует изменения изображения на экране. Соответствующие системы должны использовать мировое преобразование при расчёте положения игровых объектов или их отрисовке.

## Использование Transform в ECS

Для использования трансформаций в ECS добавь сущности компоненты `LocalTransform2D` и `WorldTransform2D`. Первая хранит локальное преобразование, а вторая — вычисленное положение в мировом пространстве.

`EngineRuntime` автоматически создаёт и регистрирует `TransformHierarchySystem` в фазе `FixedUpdate` до `PhysicsSystem2D`. При обычном использовании Runtime не нужно регистрировать эту систему повторно. Если приложение использует собственный `SystemScheduler` без `EngineRuntime`, оно отвечает за регистрацию и порядок выполнения системы самостоятельно.

```csharp
using Engine.Core.Math;
using Engine.Core.Systems;
using Engine.ECS.Components;
using Engine.ECS.Systems;
using Engine.Physics;

var ecs = runtime.EcsWorld;

// Создаём родительскую сущность.
var parent = ecs.CreateEntity();

ecs.Add(
    parent,
    new LocalTransform2D
    {
        Position = new FixedVector2(
            Fixed32.FromInt(10),
            Fixed32.Zero)
    });

ecs.Add(parent, new WorldTransform2D());

// Создаём дочернюю сущность.
var child = ecs.CreateEntity();

ecs.Add(
    child,
    new LocalTransform2D
    {
        Position = new FixedVector2(
            Fixed32.FromInt(3),
            Fixed32.Zero)
    });

ecs.Add(child, new WorldTransform2D());
ecs.Add(child, new TransformParent2D(parent));

// Регистрируем до runtime.Initialize().
runtime.Scheduler
    .Add(
        new TransformHierarchySystem(ecs),
        SystemPhase.FixedUpdate)
    .Before<PhysicsSystem2D>();
```

После выполнения `TransformHierarchySystem` на фиксированном шаге мировая координата дочерней сущности по X будет равна `13`: позиция родителя `10` плюс локальное смещение дочерней сущности `3`.

### Важные правила

- Для сущностей, обрабатываемых `TransformHierarchySystem`, `LocalTransform2D` служит источником локального преобразования, а `WorldTransform2D` пересчитывается системой.
- Изменения локального преобразования учитываются при следующем выполнении системы.
- Не изменяй вручную `WorldTransform2D`, ожидая, что изменение сохранится: система может перезаписать его при следующем фиксированном шаге.
- Системы, которым нужны уже вычисленные мировые координаты, должны выполняться после `TransformHierarchySystem`.

### 8. Physics
## Физическое тело и коллайдер

За физическую симуляцию отвечает `PhysicsSystem2D`. Он автоматически регистрируется в `EngineRuntime` и выполняется на фиксированных шагах симуляции.

Основные компоненты:

- `PhysicsBody2D` — тип тела, скорость, масса, силы и другие физические параметры.
- `Collider2D` — форма для обнаружения столкновений и настройки взаимодействия.
- `WorldTransform2D` — мировая позиция и поворот, которые изменяет физическая система.

### Типы физических тел

`PhysicsBodyType` определяет поведение тела:

- `Static` — неподвижное тело.
- `Dynamic` — тело, на которое действуют гравитация и силы.
- `Kinematic` — тело, движение которого задаётся скоростью, без автоматического применения гравитации и сил.

### Создание физического объекта

Например, создадим динамическое тело с круглым коллайдером:

```csharp
using Engine.Core.Math;
using Engine.ECS.Components;
using Engine.Physics.Components;
using Engine.Physics.Shapes;

// Настраиваем гравитацию.
runtime.PhysicsSettings.Gravity =
    new FixedVector2(
        Fixed32.Zero,
        Fixed32.FromFloat(-9.81f));

// Создаём сущность.
var entity =
    runtime.EcsWorld.CreateEntity();

// Добавляем мировой трансформ.
runtime.EcsWorld.Add(
    entity,
    new WorldTransform2D());

// Добавляем динамическое тело массой 1.
runtime.EcsWorld.Add(
    entity,
    PhysicsBody2D.Dynamic(
        Fixed32.One));

// Добавляем круглый коллайдер радиусом 1.
runtime.EcsWorld.Add(
    entity,
    new Collider2D(
        new CircleShape2D(
            Fixed32.One)));
```

После инициализации Runtime динамическое тело будет ускоряться под действием гравитации. При столкновении с другими подходящими физическими телами система сможет разрешать столкновения.

В примере гравитация направлена вдоль отрицательной оси Y. Направление и величина гравитации задаются настройками игры.

### Важные правила

- Для обработки физикой сущность должна иметь `WorldTransform2D` и `PhysicsBody2D`.
- Для обнаружения столкновений необходим также `Collider2D`.
- Коллайдер задаёт геометрию взаимодействия, а не графическое изображение объекта.
- Физика изменяет `WorldTransform2D`. Если одновременно использовать `TransformHierarchySystem`, нужно учитывать порядок систем: иерархия может перезаписать мировую трансформацию из `LocalTransform2D`.

## Скорость и силы

`PhysicsBody2D` позволяет управлять движением двумя основными способами: задавать скорость напрямую или прикладывать силу.

### Прямое изменение скорости

Свойство `Velocity` хранит линейную скорость тела. Для динамического тела скорость изменяется физической симуляцией под действием гравитации и сил.

```csharp
using Engine.Core.Math;
using Engine.Physics.Components;

ref var body =
    ref runtime.EcsWorld.Get<PhysicsBody2D>(entity);

body.WakeUp();

body.Velocity =
    new FixedVector2(
        Fixed32.FromInt(2),
        Fixed32.Zero);
```

В этом примере телу задаётся горизонтальная скорость `2`. Вызов `WakeUp()` нужен, чтобы разблокировать динамическое тело, если физика перевела его в спящее состояние.

### Применение силы

Метод `AddForce()` добавляет силу, которая влияет на ускорение динамического тела:

```csharp
body.AddForce(
    new FixedVector2(
        Fixed32.FromInt(10),
        Fixed32.Zero));
```

Ускорение от силы зависит от массы тела. Для динамического тела действует соотношение \(a = F / m\), к которому добавляется ускорение от гравитации.

Физическая система сбрасывает накопленные силы после обработки фиксированного шага. Поэтому, если сила должна действовать постоянно, её нужно прикладывать на каждом фиксированном шаге.

### Где применять силы

Для постоянного воздействия, например тяги двигателя или силы управления персонажем, используй игровую систему с `IFixedUpdateSystem` и прикладывай силу до выполнения `PhysicsSystem2D`.

```csharp
runtime.Scheduler
    .Add(
        new PlayerForceSystem(runtime.EcsWorld),
        SystemPhase.FixedUpdate)
    .Before<PhysicsSystem2D>();
```

`PlayerForceSystem` здесь — пример пользовательской игровой системы, которую необходимо реализовать в проекте игры.

### Важные правила

- `Velocity` задаёт скорость напрямую, а `AddForce()` влияет на ускорение.
- Ненулевая сила автоматически пробуждает спящее тело.
- Для постоянной силы повторяй `AddForce()` на каждом фиксированном шаге.
- Не прикладывай игровые силы из обычного кадрового `Update`, если от частоты кадров зависит то, как часто сила добавляется.

## Коллайдеры, триггеры и фильтрация столкновений

`Collider2D` определяет форму физического объекта и правила взаимодействия с другими коллайдерами.

### Триггеры

Триггер позволяет обнаруживать пересечение объектов без разрешения физического столкновения. Для этого установи `IsTrigger`:

```csharp
using Engine.ECS.Components;
using Engine.Physics.Components;

ref var collider =
    ref runtime.EcsWorld.Get<Collider2D>(entity);

collider.IsTrigger = true;
```

Физическая система продолжает обнаруживать пересечения триггера и публиковать события контакта.

### Обработка событий контакта

`PhysicsContactEvent` содержит тип контакта, его фазу и идентификаторы взаимодействующих сущностей через `Manifold.Pair`.

```csharp
using Engine.Physics.Collision;

var subscription =
    runtime.Events.Subscribe<PhysicsContactEvent>(
        contact =>
        {
            if (contact.Type != PhysicsContactType.Trigger ||
                contact.Phase != PhysicsContactPhase.Enter)
            {
                return;
            }

            var first =
                contact.Manifold.Pair.First;

            var second =
                contact.Manifold.Pair.Second;

            // Игровая логика при входе в триггер.
        });
```

Основные значения:

- `PhysicsContactType.Collision` — физическое столкновение.
- `PhysicsContactType.Trigger` — пересечение триггера.
- `PhysicsContactPhase.Enter` — контакт начался.
- `PhysicsContactPhase.Stay` — контакт продолжается.
- `PhysicsContactPhase.Exit` — контакт завершился.

События ставятся в очередь и обрабатываются при диспетчеризации событий симуляции. Храни подписку в течение нужного периода работы игровой логики и освобождай её через `Dispose()`, когда обработчик больше не нужен.

### Слои и маски столкновений

Для ограничения взаимодействий используются `CollisionLayer` и `CollisionMask` типа `uint`.

- `CollisionLayer` — битовая маска слоя, которому принадлежит коллайдер.
- `CollisionMask` — битовая маска слоёв, с которыми коллайдер может взаимодействовать.

Для обнаружения столкновения маски обоих коллайдеров должны разрешать взаимодействие друг с другом.

```csharp
ref var firstCollider =
    ref runtime.EcsWorld.Get<Collider2D>(firstEntity);

firstCollider.CollisionLayer = 1u << 0;
firstCollider.CollisionMask = 1u << 1;

ref var secondCollider =
    ref runtime.EcsWorld.Get<Collider2D>(secondEntity);

secondCollider.CollisionLayer = 1u << 1;
secondCollider.CollisionMask = 1u << 0;
```

В примере первый коллайдер относится к слою `0` и взаимодействует со слоем `1`. Второй настроен симметрично. Слои и маски позволяют, например, разделить взаимодействие персонажей, объектов окружения и сенсорных зон.

### Важные правила

- Для участия в физической симуляции сущности необходимы `PhysicsBody2D`, `Collider2D` и `WorldTransform2D`.
- Триггер сообщает о пересечениях, но не разрешает физическое столкновение.
- Коллайдер с `Enabled = false` исключается из обнаружения контактов.
- Даже если маска одного коллайдера разрешает взаимодействие, противоположная маска тоже должна разрешать его.

## Материалы: трение и упругость

`PhysicsMaterial2D` задаёт свойства поверхности, которые влияют на разрешение физических столкновений. Материал назначается через свойство `Material` компонента `Collider2D`.

### Настройка материала

```csharp
using Engine.Core.Math;
using Engine.Physics.Components;
using Engine.Physics.Materials;

ref var collider =
    ref runtime.EcsWorld.Get<Collider2D>(entity);

collider.Material =
    new PhysicsMaterial2D(
        Fixed32.FromFloat(0.8f), // Трение
        Fixed32.FromFloat(0.6f)  // Упругость
    );
```

Конструктор принимает два параметра:

- `Friction` — коэффициент трения. Значение должно быть неотрицательным.
- `Restitution` — коэффициент упругости при столкновении. Допустимый диапазон — от `0` до `1`.

### Как работают параметры

**Трение (`Friction`)** влияет на сопротивление относительному движению поверхностей в точке контакта. Чем выше коэффициент, тем сильнее может быть импульс трения. Это не означает, что объект обязательно остановится: результат зависит также от скоростей, масс и других параметров столкновения.

**Упругость (`Restitution`)** влияет на отскок. Значение `0` означает отсутствие упругости в расчёте столкновения, а более высокие значения позволяют получить более выраженный отскок.

### Материалы двух коллайдеров

При столкновении движок объединяет свойства материалов двух коллайдеров:

- Итоговое трение рассчитывается как геометрическое среднее коэффициентов трения.
- Итоговая упругость выбирается как меньшее из двух значений `Restitution`.

Например, если у одного коллайдера упругость `0.8`, а у другого `0.3`, в расчёте столкновения используется `0.3`.

### Материал по умолчанию

Если материал отдельно не задан, `Collider2D` использует `PhysicsMaterial2D.Default`:

- `Friction = 0.5`
- `Restitution = 0`

### Важные правила

- Материал относится к `Collider2D`, а не к `PhysicsBody2D`.
- Изменение `collider.Material` меняет параметры последующих расчётов столкновений.
- Трение и упругость влияют на физическое взаимодействие, но сами по себе не задают движение объекта или его графический вид.

## Настройки физической симуляции

Параметры физики задаются через `runtime.PhysicsSettings`. Они определяют гравитацию, точность разрешения столкновений и поведение спящих тел.

### Настройка гравитации

```csharp
using Engine.Core.Math;

runtime.PhysicsSettings.Gravity =
    new FixedVector2(
        Fixed32.Zero,
        Fixed32.FromFloat(-9.81f));
```

Гравитация задаётся в виде вектора. В этом примере она направлена вниз вдоль оси Y. По умолчанию гравитация равна нулю.

### Подшаги и итерации

```csharp
runtime.PhysicsSettings.Substeps = 4;
runtime.PhysicsSettings.VelocityIterations = 4;
runtime.PhysicsSettings.PositionIterations = 2;
```

- `Substeps` — количество подшагов физики внутри одного фиксированного шага симуляции. Значение должно быть больше нуля.
- `VelocityIterations` — количество итераций разрешения скоростей при столкновениях. Допустимо нулевое значение.
- `PositionIterations` — количество итераций коррекции взаимного проникновения тел. Допустимо нулевое значение.

Подшаги позволяют чаще пересчитывать движение и контакты внутри фиксированного шага. Дополнительные итерации могут улучшить разрешение сложных столкновений, но увеличивают вычислительную нагрузку.

### Коррекция проникновения

Также доступны параметры:

- `PenetrationSlop` — допустимая величина проникновения, которая не корректируется разрешителем столкновений. Значение не может быть отрицательным.
- `PositionCorrectionPercent` — доля коррекции проникновения в диапазоне от `0` до `1`.

Эти параметры влияют на устранение перекрытия тел после обнаружения столкновения.

### Засыпание динамических тел

Настройки засыпания позволяют уменьшить вычислительную нагрузку, когда динамические тела практически неподвижны:

- `SleepLinearVelocityThreshold` — порог линейной скорости.
- `SleepAngularVelocityThreshold` — порог угловой скорости.
- `SleepTime` — время, в течение которого тело должно оставаться достаточно спокойным для перехода в спящее состояние.

По умолчанию оба порога скорости равны `0.05`, а `SleepTime` — `0.5` секунды. Пороги скорости должны быть неотрицательными, а `SleepTime` — больше нуля.

### Важные правила

- Настройки доступны через `runtime.PhysicsSettings`; создавать отдельный `PhysicsSystem2D` для изменения параметров уже настроенного Runtime не требуется.
- Меняй параметры с учётом требуемой точности и производительности игры.
- Если важна детерминированность симуляции, настраивай параметры согласованно между участниками симуляции.
- Увеличение числа подшагов и итераций не гарантирует устранения всех проблем физики: результат также зависит от форм тел, скоростей и конфигурации столкновений.

## События столкновений и контактов

`PhysicsSystem2D` отслеживает изменения контактов между коллайдерами и публикует `PhysicsContactEvent` через `runtime.Events`.

### Жизненный цикл контакта

Каждый контакт имеет одну из трёх фаз:

- `Enter` — пара коллайдеров начала контакт.
- `Stay` — контакт сохраняется на следующем фиксированном шаге.
- `Exit` — контакт завершился.

Событие также содержит `Type`, который различает физическое столкновение (`Collision`) и пересечение триггера (`Trigger`).

### Обработка фаз контакта

Используй фазу события, чтобы выполнять игровую логику только в нужный момент:

```csharp
using Engine.Physics.Collision;

var subscription =
    runtime.Events.Subscribe<PhysicsContactEvent>(
        contact =>
        {
            var pair =
                contact.Manifold.Pair;

            switch (contact.Phase)
            {
                case PhysicsContactPhase.Enter:
                    // Контакт начался.
                    break;

                case PhysicsContactPhase.Stay:
                    // Контакт продолжается.
                    break;

                case PhysicsContactPhase.Exit:
                    // Контакт завершился.
                    break;
            }
        });
```

`Manifold.Pair.First` и `Manifold.Pair.Second` содержат идентификаторы двух сущностей. Проверяй `contact.Type`, если логика должна различать столкновения и триггеры.

### Когда вызывается обработчик

Физическая система публикует события во время `FixedUpdate`. Они помещаются в очередь `EventBus`, а затем диспетчеризуются симуляцией после выполнения систем фиксированного обновления.

Обработчик события поэтому вызывается после выполнения физической системы на данном шаге, а не непосредственно в момент обнаружения контакта.

### Доступ к текущим контактам

Для диагностики также доступны:

- `runtime.Physics.Contacts` — текущие физические контактные манifoldы; триггеры в этот список не включаются.
- `runtime.Physics.ContactEvents` — события контактов, сформированные на последнем фиксированном шаге.

Эти коллекции предназначены для получения текущего состояния, а не для долговременного хранения истории. `ContactEvents` очищается при следующем обновлении физики.

### Важные правила

- Для игровой логики обычно удобнее подписываться на `PhysicsContactEvent`, чем постоянно опрашивать коллекции контактов.
- Событие `Exit` можно использовать для завершения эффектов контакта, удаления временных связей или сброса состояния взаимодействия.
- Храни возвращённый `EventSubscription` и вызывай `Dispose()`, когда обработчик больше не нужен.
- События не заменяют проверку состояния сущностей: к моменту обработки события игровая логика должна учитывать, что сущность могла быть удалена.

## Часть II. Сервисы игры

### 9. Input
## Действия и привязки ввода

Система `Engine.Input` предоставляет интерфейс `IInput` для чтения состояния ввода. Игровая логика может использовать именованные действия (`InputAction`), которым назначаются физические источники ввода через `InputActionMap`.

### Создание действий

```csharp
using Engine.Input;

var moveLeft = new InputAction("MoveLeft");
var jump = new InputAction("Jump");
```

`InputAction` — именованное действие игры. Само по себе оно не связано с определённой клавишей: связь настраивается через `InputActionMap`.

### Привязка клавиш

В приложении, использующем `DesktopGameHostContext`, действия можно настроить через `context.InputActions`:

```csharp
context.InputActions.Bind(
    moveLeft,
    new InputBinding("Keyboard.A"));

context.InputActions.Bind(
    moveLeft,
    new InputBinding("Keyboard.Left"));

context.InputActions.Bind(
    jump,
    new InputBinding("Keyboard.Space"));
```

Теперь действие `MoveLeft` доступно при нажатии `A` или стрелки влево, а `Jump` — при нажатии пробела.

Строка `InputBinding` задаёт путь к источнику ввода. В текущем desktop-backend `SilkNetInputBackend` поддерживаются, например, пути `Keyboard.W`, `Keyboard.Space`, `Mouse.Left` и `Mouse.Scroll`. Конкретные пути интерпретируются backend, поэтому не следует считать эти строки универсальным форматом для любой будущей реализации ввода.

### Чтение состояния действий

`IInput` предоставляет четыре основных метода:

- `IsDown(action)` — действие активно в текущем кадре.
- `IsPressed(action)` — действие перешло из неактивного состояния в активное.
- `IsReleased(action)` — действие перешло из активного состояния в неактивное.
- `GetValue(action)` — числовое значение действия типа `float`.

Например, в обычном обновлении приложения:

```csharp
context.Input.Update();

if (context.Input.IsDown(moveLeft))
{
    // Действие MoveLeft активно.
}

if (context.Input.IsPressed(jump))
{
    // Обработать начало прыжка.
}

float moveValue =
    context.Input.GetValue(moveLeft);
```

`context.Input` предоставляет интерфейс `IInput`. В этом примере `context` — экземпляр `DesktopGameHostContext`, полученный при создании приложения.

### Обновление ввода

Вызывай `IInput.Update()` один раз за кадр, до чтения состояний действий. Этот вызов обновляет текущие и предыдущие значения, необходимые для определения нажатия и отпускания.

Сам `EngineRuntime` не вызывает `Services.Input.Update()` автоматически. В приложении ответственность за своевременное обновление ввода лежит на коде, который организует кадровое обновление.

### Несколько привязок к одному действию

Одному `InputAction` можно назначить несколько `InputBinding`. В текущей реализации `InputActionMap` выбирает значение с наибольшим абсолютным значением, а не суммирует значения всех привязок.

Это удобно, например, когда движение влево разрешено как клавишей `A`, так и стрелкой влево.

### Важные правила

- Настраивай привязки при подготовке приложения или изменении схемы управления.
- Используй `IsPressed()` для однократного действия при нажатии и `IsDown()` для поведения, продолжающегося, пока ввод активен.
- Чтобы `IsPressed()` и `IsReleased()` работали корректно, обновляй ввод каждый кадр.
- `InputActionMap` должен быть тем же экземпляром карты, который используется соответствующей реализацией `IInput`.
## Мышь, указатель и текстовый ввод

Помимо действий `InputAction`, desktop-приложение предоставляет отдельные интерфейсы для работы с указателем и текстовым вводом.

### Мышь и позиция указателя

В `DesktopGameHostContext` свойство `PointerInput` имеет тип `IPointerInput?`, поэтому в пользовательском коде следует учитывать nullable-контракт. Текущий стандартный `DesktopGameHost` создаёт `SilkNetInputBackend`, который реализует `IPointerInput`; отсутствие указателя относится к возможной конфигурации host без этой возможности, а не к текущей реализации стандартного desktop host.

```csharp
using Engine.Input;

var pointer = context.PointerInput;

if (pointer is not null)
{
    var position = pointer.Position;
    var scroll = pointer.ScrollDelta;

    if (pointer.IsPressed(InputMouseButton.Left))
    {
        // Обработать нажатие левой кнопки мыши.
    }

    if (pointer.IsDown(InputMouseButton.Right))
    {
        // Правая кнопка удерживается.
    }

    if (pointer.IsReleased(InputMouseButton.Middle))
    {
        // Средняя кнопка отпущена.
    }
}
```

`Position` возвращает позицию указателя в координатах, предоставляемых backend. Сам интерфейс не гарантирует, что это координаты игрового мира или координаты внутри конкретной панели UI.

`ScrollDelta` содержит значение прокрутки мыши за последнее обновление ввода.

### Текстовый ввод

Для получения введённых символов используй `ITextInput`, доступный через `context.TextInput`.

```csharp
using Engine.Input;

foreach (char character in context.TextInput.Characters)
{
    // Обработать введённый символ.
}
```

`Characters` содержит символы, полученные при обработке текущего обновления. Если символы нужно сохранить для дальнейшей работы, копируй их в собственное хранилище.

Для проверки специальных клавиш предусмотрен метод `IsPressed(TextInputKey key)`:

```csharp
if (context.TextInput.IsPressed(TextInputKey.Enter))
{
    // Обработать Enter.
}

if (context.TextInput.IsPressed(TextInputKey.Escape))
{
    // Обработать Escape.
}
```

`TextInputKey` содержит специальные клавиши, включая `Enter`, `Backspace`, `Delete`, стрелки, `Home`, `End`, `Escape` и `F1`. Этот интерфейс не заменяет получение обычных текстовых символов через `Characters`.

### Важные правила

- Перед обращением к `PointerInput` проверяй, что он не равен `null`.
- Для определения нажатия, удержания и отпускания кнопок используй `IsPressed()`, `IsDown()` и `IsReleased()` соответственно.
- `IPointerInput` и `ITextInput` — отдельные возможности host; не каждый host обязан предоставлять одинаковый набор возможностей.
- Ввод указателя и текстовый ввод сами по себе не выполняют преобразование координат, обработку фокуса UI или игровую логику.

### 10. Camera
## Camera2D: позиция, масштаб и область просмотра

`Camera2D` описывает видимую область двумерного мира. Камера предоставляет позицию, масштаб и преобразования между мировыми и экранными координатами.

В приложении на основе `DesktopGameHost` доступ к камере можно получить через `context.Camera`.

### Позиция камеры

Свойство `Position` задаёт положение центра камеры в мировых координатах.

```csharp
using Engine.Core.Math;

var camera = context.Camera;

camera.Position =
    new Vector2(100.0f, 50.0f);
```

При изменении позиции камера перемещает область просмотра относительно игрового мира.

### Масштабирование

Свойство `Zoom` управляет масштабом отображения:

```csharp
camera.Zoom = 2.0f;
```

При увеличении `Zoom` объекты занимают больше места на экране, а видимая область мира становится меньше. Значение должно быть больше нуля.

### Область просмотра

`ViewportSize` возвращает размер области просмотра в экранных единицах. Для desktop-окна начальное значение задаётся при создании камеры, а при изменении размера окна `OpenGLWindow` обновляет его автоматически.

`WorldBounds` возвращает прямоугольник мировых координат, который покрывает видимую область камеры с учётом позиции и масштаба.

### Важные правила

- `Camera2D` хранит параметры обзора, но сама не рисует игровые объекты.
- `Position` использует `Engine.Core.Math.Vector2` с типом `float`, а не фиксированную арифметику ECS.
- `Zoom` должен быть больше нуля.
- Если камера используется вне стандартного desktop-host, размер области просмотра необходимо поддерживать через `SetViewportSize()`.

## Преобразование координат и проверка видимости

`Camera2D` предоставляет методы для преобразования координат между игровым миром и экраном, а также для проверки того, попадает ли прямоугольник в область просмотра.

### Мировые координаты в экранные

Используй `WorldToScreen()`, чтобы получить экранную позицию объекта:

```csharp
using Engine.Core.Math;

Vector2 worldPosition =
    new Vector2(100.0f, 50.0f);

Vector2 screenPosition =
    context.Camera.WorldToScreen(worldPosition);
```

Метод учитывает позицию камеры, её масштаб и размер области просмотра. Центр камеры соответствует центру области просмотра.

### Экранные координаты в мировые

`ScreenToWorld()` выполняет обратное преобразование. Например, это полезно при выборе игрового объекта мышью:

```csharp
Vector2 worldPosition =
    context.Camera.ScreenToWorld(
        pointer.Position);
```

В этом примере `pointer` — доступный `IPointerInput`. Полученная мировая позиция может использоваться для поиска объектов под указателем.

**Важно:** экранные координаты должны быть относительны начала области просмотра камеры. Если камера отображает отдельную панель редактора, сначала преобразуй координаты указателя в локальные координаты этой панели.

### Проверка видимости

Метод `IsVisible()` проверяет, пересекается ли заданный `Rectangle` с видимой областью мира:

```csharp
using Engine.Core.Math;

var bounds =
    new Rectangle(
        90.0f,
        40.0f,
        20.0f,
        20.0f);

if (context.Camera.IsVisible(bounds))
{
    // Прямоугольник пересекается с областью просмотра.
}
```

Метод подходит для предварительного отсечения объектов, которые полностью находятся за пределами камеры. Он проверяет только пересечение прямоугольников и не определяет, действительно ли объект будет нарисован.

### Важные правила

- `WorldToScreen()` и `ScreenToWorld()` преобразуют позиции, а не размеры объектов.
- При преобразовании координат учитывай начало и размер конкретной области просмотра.
- `IsVisible()` принимает `Rectangle` в мировых координатах.
- Проверка видимости сама по себе не выполняет отрисовку и не меняет состояние объекта.


### 11. Graphics
## Графическое устройство

`IGraphicsDevice` — основной интерфейс взаимодействия с графической подсистемой. Он находится в пространстве имён `Engine.Graphics` и не привязан к конкретному графическому backend.

В приложении, использующем `DesktopGameHostContext`, доступ к графическому устройству предоставляется через `context.Graphics`.

```csharp
using Engine.Graphics;

IGraphicsDevice graphics =
    context.Graphics;
```

### Основные возможности

`IGraphicsDevice` предоставляет несколько менеджеров ресурсов и графических подсистем:

- `Textures` — создание и управление текстурами.
- `Fonts` — создание и управление шрифтами.
- `Buffers` — управление графическими буферами.
- `Shaders` — управление шейдерами.
- `RenderTargets` — управление целями рендеринга.
- `Pipeline` — графический конвейер, определяющий порядок проходов отрисовки.

Для отправки команд отрисовки используется метод `Submit(IRenderCommand)`.

### Жизненный цикл кадра

Графическое устройство предоставляет три метода управления кадром:

- `BeginFrame()` — начинает кадр.
- `Submit(command)` — добавляет команду отрисовки в очередь.
- `EndFrame()` — выполняет графический конвейер для накопленных команд.

При использовании стандартного desktop-host вызовы `BeginFrame()` и `EndFrame()` выполняются самим host вокруг отрисовки приложения. Игровой код обычно формирует и отправляет команды во время этапа `Render`, не управляя кадром вручную.

### Независимость от backend

Игровой код должен по возможности работать через `IGraphicsDevice` и связанные с ним интерфейсы. Например, для создания текстуры используй `graphics.Textures`, а не обращайся напрямую к объектам OpenGL.

Конкретную реализацию графического устройства выбирает приложение или host. Это позволяет сохранять игровую логику независимой от деталей графического backend.

### Важные правила

- `IGraphicsDevice` — интерфейс графической подсистемы, а не самостоятельный игровой цикл.
- При использовании `DesktopGameHost` не вызывай `BeginFrame()` и `EndFrame()` самостоятельно внутри `Render`.
- Для управления ресурсами используй соответствующие менеджеры устройства.
- Жизненный цикл самого графического устройства контролирует host или владеющее им приложение.
## Текстуры и управление ресурсами

Для создания и управления текстурами используется `ITextureManager`, доступный через `IGraphicsDevice.Textures`.

Текстура представлена дескриптором `TextureHandle`. Он позволяет обращаться к графическому ресурсу, не завися от деталей его хранения в конкретном backend.

### Создание текстуры с данными пикселей

```csharp
using Engine.Graphics.Resources;

var graphics = context.Graphics;

byte[] pixels =
[
    255, 80, 30, 255 // RGBA: один непрозрачный пиксель
];

var textureData =
    new TextureData(
        1,
        1,
        TextureFormat.Rgba8,
        pixels);

TextureHandle texture =
    graphics.Textures.Create(textureData);
```

`TextureData` содержит ширину, высоту, формат и данные пикселей. В текущей реализации поддерживается `TextureFormat.Rgba8`: четыре байта на пиксель в порядке RGBA.

Размер массива должен точно соответствовать размерам текстуры и формату: для `Rgba8` требуется `width × height × 4` байта.

### Проверка и получение описания

```csharp
if (graphics.Textures.Exists(texture))
{
    TextureDescription description =
        graphics.Textures.GetDescription(texture);

    // Использовать description.Width и description.Height.
}
```

`Exists()` проверяет, существует ли ресурс с данным дескриптором. `GetDescription()` возвращает его описание — ширину, высоту и формат. Для несуществующего ресурса `GetDescription()` выбрасывает исключение.

### Создание пустого хранилища текстуры

Если данные пикселей пока не нужны, можно создать текстуру по описанию:

```csharp
var texture =
    graphics.Textures.Create(
        new TextureDescription(
            256,
            256,
            TextureFormat.Rgba8));
```

Этот вариант выделяет текстурное хранилище без передачи исходных пикселей. Он сам по себе не загружает изображение и не задаёт содержимое текстуры.

### Освобождение ресурса

Когда текстура больше не нужна, освободи её через тот же менеджер:

```csharp
graphics.Textures.Destroy(texture);
```

После уничтожения дескриптор больше не обозначает существующий ресурс. Если передать его повторно в `Destroy()`, операция безопасно ничего не сделает, когда ресурс уже отсутствует.

### Важные правила

- Для создания и уничтожения текстур используй `graphics.Textures`, а не API конкретного графического backend.
- Сохраняй `TextureHandle`, если ресурс потребуется использовать в последующих командах отрисовки.
- Не уничтожай текстуру, пока команды или другие системы ещё используют её.
- Менеджер также освобождает принадлежащие ему текстуры при завершении работы; однако ресурсы, которые больше не нужны до завершения приложения, следует освобождать своевременно.
## Render commands и их отправка

`IRenderCommand` описывает команду отрисовки. Чтобы передать её графическому устройству, используй `IGraphicsDevice.Submit()`.

Команды не выполняются немедленно: они попадают в очередь и обрабатываются графическим конвейером при завершении кадра через `EndFrame()`.

### Пример отправки команды

Например, можно нарисовать отладочную линию:

```csharp
using Engine.Core.Math;
using Engine.Graphics.Commands;
using Engine.Graphics.DebugGraphics;

// graphics — это IGraphicsDevice.
graphics.Submit(
    new DrawDebugLineCommand(
        new Vector2(0.0f, 0.0f),
        new Vector2(100.0f, 50.0f),
        DebugColor.Green,
        DebugRenderSpace.World));
```

В этом примере создаётся зелёная линия между двумя точками мирового пространства. `DebugRenderSpace.World` означает, что координаты интерпретируются относительно игрового мира с учётом камеры.

### Слои отрисовки

Каждая команда предоставляет свойство `Layer`. Графическая очередь сортирует команды сначала по слою, а затем по порядку отправки внутри одного слоя.

Стандартные значения из `RenderLayers`:

- `World = 0` — игровой мир.
- `Ui = 1000` — пользовательский интерфейс.
- `Debug = 2000` — отладочная графика.
- `DebugText = 2001` — отладочный текст.
- `Present = 900` — вывод результата рендеринга.

Конкретный проход конвейера обрабатывает только те слои, которые входят в заданный для него диапазон.

### Где отправлять команды

В приложении, использующем стандартный `DesktopGameHost`, формируй команды во время этапа `Render`. Сам host начинает и завершает графический кадр.

```csharp
public void Render(double interpolationAlpha)
{
    _graphics.Submit(
        new DrawDebugLineCommand(
            new Vector2(0.0f, 0.0f),
            new Vector2(100.0f, 50.0f),
            DebugColor.Green));
}
```

Здесь `_graphics` — сохранённый экземпляр `IGraphicsDevice`, полученный при настройке приложения. Не вызывай `BeginFrame()` и `EndFrame()` самостоятельно внутри этого метода.

### Важные правила

- Отправка команды только ставит её в очередь; фактическая отрисовка происходит позднее.
- Порядок отправки сохраняется для команд с одинаковым `Layer`.
- Команда должна поддерживаться конкретным графическим backend и проходом конвейера.
- `DrawDebugLineCommand` предназначен для отладочной графики. Для игровых спрайтов, UI и других видов содержимого используй соответствующие команды.

## Шрифты, буферы, шейдеры и Render Targets

Помимо текстур, `IGraphicsDevice` предоставляет менеджеры для других графических ресурсов. Все они доступны через соответствующие свойства графического устройства.

### Шрифты

`graphics.Fonts` предоставляет интерфейс `IFontManager`. Он позволяет создавать шрифты из данных, получать информацию о символах и измерять текст.

Например, чтобы получить метрики текста с использованием шрифта по умолчанию:

```csharp
using Engine.Graphics.Fonts;

var font = graphics.Fonts.DefaultFont;

FontTextMetrics metrics =
    graphics.Fonts.MeasureText(
        font,
        "Hello, VibeEngine2");
```

`FontTextMetrics` содержит ширину и высоту текста, метрики восхождения и спуска символов, а также высоту строки.

Для создания собственного шрифта используется `Create()` с данными шрифта и `FontDescription`. Больше неиспользуемые шрифты следует освобождать через `Destroy()`.

### Графические буферы

`graphics.Buffers` предоставляет интерфейс `IGraphicsBufferManager` для создания и обновления графических буферов.

```csharp
using Engine.Graphics.Resources;

var buffer =
    graphics.Buffers.Create(
        new GraphicsBufferDescription(
            GraphicsBufferType.Vertex,
            256,
            GraphicsBufferUsage.Dynamic));

byte[] data = new byte[256];

graphics.Buffers.Update(buffer, data);
```

`GraphicsBufferType` определяет назначение буфера: `Vertex` или `Index`. `GraphicsBufferUsage` задаёт режим использования: `Static`, `Dynamic` или `Stream`.

Размер буфера задаётся в байтах. `Update()` записывает данные в существующий буфер с указанного смещения, которое по умолчанию равно нулю.

Когда буфер больше не нужен, освободи его через `graphics.Buffers.Destroy(buffer)`.

### Шейдеры

`graphics.Shaders` предоставляет интерфейс `IShaderManager`. Шейдер создаётся через `ShaderDescription`, содержащий исходный код вершинного и фрагментного шейдеров.

```csharp
using Engine.Graphics.Resources;

var shader =
    graphics.Shaders.Create(
        new ShaderDescription(
            vertexSource,
            fragmentSource));
```

`vertexSource` и `fragmentSource` здесь — строки с исходным кодом соответствующих шейдеров.

Менеджер также позволяет проверить ресурс через `Exists()`, получить описание через `GetDescription()` и освободить его через `Destroy()`.

Хотя сам менеджер доступен через общий интерфейс, исходный код шейдеров может зависеть от языка и требований конкретного графического backend.

### Render Targets

Render Target — цель, в которую графический конвейер может выводить результат отрисовки. Создавать и обслуживать такие ресурсы можно через `graphics.RenderTargets`.

```csharp
using Engine.Graphics.Resources;

var target =
    graphics.RenderTargets.Create(
        new RenderTargetDescription(
            512,
            512));
```

`RenderTargetDescription` задаёт ширину, высоту и формат. Если формат не указан, используется `TextureFormat.Rgba8`.

Основные операции с целью:

- `Exists()` — проверить существование ресурса.
- `GetDescription()` — получить его описание.
- `GetColorTexture()` — получить дескриптор цветовой текстуры.
- `Resize()` — изменить размеры цели.
- `Destroy()` — освободить цель.

Само создание Render Target ещё не направляет отрисовку в него. Для этого требуется настроить соответствующий проход `RenderPipeline`. Цветовую текстуру цели не следует освобождать отдельно, пока ею владеет Render Target Manager.

### Общие правила управления ресурсами

- Используй менеджер, который создал ресурс, для проверки его существования и освобождения.
- Не используй дескриптор после уничтожения ресурса.
- Освобождай ресурсы, когда игровая логика больше не нуждается в них.
- Не смешивай общие интерфейсы графики с конкретными классами backend без необходимости.

### 12. Render Pipeline и Graphics2D
## Render Pipeline и проходы рендеринга

`RenderPipeline` определяет, в какой последовательности графическое устройство обрабатывает команды отрисовки. Каждый проход (`RenderPass`) задаёт цель отрисовки, состояние графики, необходимость очистки цветового буфера и диапазон слоёв, которые нужно обработать.

### Стандартные проходы 2D

В текущей реализации `OpenGLGraphicsDevice` по умолчанию зарегистрированы три прохода из `RenderPass2D`:

- `RenderPass2D.World` — отрисовка игрового мира.
- `RenderPass2D.Ui` — отрисовка пользовательского интерфейса.
- `RenderPass2D.Debug` — отладочная графика и текст.

Все три прохода по умолчанию используют основную цель вывода и состояние `RenderState.Default2D`. Первый проход очищает цветовой буфер, последующие сохраняют результат предыдущих проходов.

### Получение конвейера

Доступ к конвейеру осуществляется через `IGraphicsDevice.Pipeline`:

```csharp
using Engine.Graphics.Rendering;

var pipeline = context.Graphics.Pipeline;

foreach (var pass in pipeline.Passes)
{
    Console.WriteLine(
        $"{pass.Name}: " +
        $"{pass.Layers.Minimum}–{pass.Layers.Maximum}");
}
```

`Passes` возвращает список зарегистрированных проходов, а `Count` — их количество. При выполнении кадра конвейер сортирует очередь команд по слоям и передаёт каждому проходу только подходящие команды.

### Собственный проход

Новый проход можно добавить через `AddPass()`:

```csharp
using Engine.Graphics.Rendering;
using Engine.Graphics.Resources;

var customPass =
    new RenderPass(
        Name: "Custom",
        Target: RenderTargetHandle.Invalid,
        State: RenderState.Default2D,
        ClearColor: false,
        Layers: new RenderPassLayerRange(
            3000,
            3099));

context.Graphics.Pipeline.AddPass(customPass);
```

В этом примере проход обрабатывает команды со слоями от `3000` до `3099` и выводит их в основную цель без очистки цветового буфера.

Добавленный проход выполняется после уже зарегистрированных проходов. Поэтому команды нового диапазона будут обработаны только в том случае, если они поддерживаются графическим backend и попадают в этот проход.

### Важные правила

- `AddPass()` добавляет проход в конец конвейера; существующие проходы автоматически не перестраиваются.
- `Clear()` удаляет все проходы, включая стандартные. Используй его только тогда, когда действительно собираешься настроить конвейер заново.
- Диапазон слоёв определяет, какие команды обрабатывает проход, но не создаёт и не отправляет команды.
- Для рисования в текстуру Render Target используй соответствующий `RenderTargetHandle` вместо `RenderTargetHandle.Invalid`.
## Слои и порядок отрисовки

Каждая команда отрисовки содержит свойство `Layer`. Оно определяет порядок команды в графической очереди и позволяет разделять игровой мир, пользовательский интерфейс и отладочную графику.

### Стандартные слои

Для распространённых случаев предусмотрены константы `RenderLayers`:

- `RenderLayers.World` (`0`) — игровой мир.
- `RenderLayers.Present` (`900`) — диапазон для команд, связанных с выводом промежуточного результата.
- `RenderLayers.Ui` (`1000`) — пользовательский интерфейс.
- `RenderLayers.Debug` (`2000`) — отладочная графика.
- `RenderLayers.DebugText` (`2001`) — отладочный текст.

Стандартные проходы `RenderPass2D` используют диапазоны слоёв: игровой мир — от `0` до `899`, UI — от `1000` до `1999`, отладочная графика — от `2000` и выше.

Диапазон `900–999` не обрабатывается этими тремя стандартными проходами. Для его использования потребуется подходящий дополнительный проход.

### Собственные слои

Если нескольким типам игровых объектов нужен определённый порядок, можно объявить собственные константы:

```csharp
using Engine.Graphics.Rendering;

public static class GameRenderLayers
{
    public const int Background = 0;
    public const int Terrain = 10;
    public const int Buildings = 20;
    public const int Characters = 30;
    public const int Effects = 40;
}
```

При отправке команды укажи нужный слой через её параметр `Layer`, если команда поддерживает такую настройку:

```csharp
using Engine.Core.Math;
using Engine.Graphics.Commands;
using Engine.Graphics.DebugGraphics;

context.Graphics.Submit(
    new DrawDebugRectangleCommand(
        new Vector2(10.0f, 10.0f),
        new Vector2(32.0f, 32.0f),
        DebugColor.Green,
        Filled: true,
        Layer: GameRenderLayers.Terrain));
```

Здесь `DrawDebugRectangleCommand` используется для демонстрации механизма слоёв. В настоящей игре для отображения тайлов или зданий следует применять соответствующие игровые команды отрисовки.

### Порядок внутри одного слоя

Очередь сначала сортирует команды по возрастанию `Layer`. Если у нескольких команд слой одинаковый, они выполняются в порядке отправки.

При стандартном альфа-смешивании более поздняя команда может оказаться визуально поверх предыдущей. Поэтому слой стоит выбирать с учётом того, какие элементы должны перекрывать другие.

### Важные правила

- Слой команды и диапазон слоя прохода — разные вещи: команда задаёт свой слой, а проход определяет диапазон допустимых слоёв.
- Команда будет обработана только проходами, в диапазон которых попадает её `Layer`.
- Если диапазоны проходов пересекаются, одна команда потенциально может быть выполнена в нескольких проходах.
- Для собственных слоёв выбирай диапазоны, согласованные с используемыми проходами, чтобы UI или игровые объекты случайно не пропускались либо не рисовались повторно.

## Graphics2D: отрисовка спрайтов

`SpriteRenderer` предоставляет удобный способ отправлять команды отрисовки спрайтов через `IGraphicsDevice`. Он находится в пространстве имён `Engine.Graphics.Sprites`.

Спрайт (`Sprite`) описывает текстуру, используемую область текстуры, размер изображения и слой отрисовки.

### Создание и отрисовка спрайта

Предположим, что `texture` — действительный `TextureHandle`, созданный ранее через менеджер текстур.

```csharp
using Engine.Core.Math;
using Engine.Graphics.Rendering;
using Engine.Graphics.Sprites;

var sprite = new Sprite(
    texture,
    new Rectangle(0.0f, 0.0f, 1.0f, 1.0f),
    new Vector2(32.0f, 32.0f),
    RenderLayers.World);

var spriteRenderer =
    new SpriteRenderer(context.Graphics);

spriteRenderer.DrawWorld(
    sprite,
    new Vector2(100.0f, 50.0f),
    context.Camera);
```

В этом примере спрайт занимает размер `32 × 32` единицы мира и размещается в позиции `(100, 50)`.

`Rectangle` для UV задаёт область текстуры в нормализованных координатах: `(0, 0, 1, 1)` означает использование всей текстуры.

### Проверка видимости

Перегрузка `DrawWorld(sprite, position, camera)` проверяет, пересекается ли прямоугольник спрайта с видимой областью камеры. Если спрайт полностью за пределами камеры, команда отрисовки не отправляется.

Также существует `DrawWorld(sprite, position)` без камеры. Эта перегрузка отправляет команду без предварительной проверки видимости.

### Важные правила

- `SpriteRenderer` использует `IGraphicsDevice` и не требует прямого обращения к OpenGL.
- Размер спрайта задаётся отдельно от размеров исходной текстуры.
- Для корректной отрисовки текстура должна существовать в момент обработки команды.
- `SpriteRenderer` отправляет команды, но не управляет жизненным циклом графического кадра.

## Texture Atlas: получение областей текстуры

`TextureAtlas` описывает сетку одинаковых ячеек внутри текстуры. Это удобно, когда одна картинка содержит множество игровых спрайтов или тайлов.

### Загрузка атласа

Для загрузки текстуры и создания атласа можно использовать `TextureResourceManager`:

```csharp
using Engine.Core.Assets;
using Engine.Graphics.Resources;

var textureResources =
    new TextureResourceManager(
        context.Content,
        context.Graphics.Textures);

var atlas =
    textureResources.LoadAtlas(
        new AssetPath("terrain.png"),
        tileWidth: 16,
        tileHeight: 16);
```

В примере предполагается, что `terrain.png` доступен через настроенный источник ресурсов. Для стандартного desktop-host путь обычно указывается относительно каталога `Assets`.

Размер ячейки задаётся в пикселях исходной текстуры. Её ширина и высота должны делиться на размеры ячейки без остатка.

### Получение спрайта из атласа

`GetRegion()` возвращает область текстуры в нормализованных UV-координатах. Ячейку можно выбрать по индексу или по столбцу и строке.

```csharp
using Engine.Core.Math;
using Engine.Graphics.Rendering;
using Engine.Graphics.Sprites;

// Вторая строка, третий столбец.
var region = atlas.GetRegion(
    column: 2,
    row: 1);

var sprite = new Sprite(
    atlas.Texture,
    region.UV,
    new Vector2(16.0f, 16.0f),
    RenderLayers.World);

var spriteRenderer =
    new SpriteRenderer(context.Graphics);

spriteRenderer.DrawWorld(
    sprite,
    new Vector2(10.0f, 5.0f),
    context.Camera);
```

Индексы строк и столбцов начинаются с нуля. Размер спрайта в мире задаётся отдельно от размера ячейки в текстуре, поэтому изображение можно масштабировать при отрисовке.

### Важные правила

- `TextureAtlas` не создаёт отдельную текстуру для каждой ячейки, а возвращает области общей текстуры.
- `Count`, `Columns` и `Rows` позволяют узнать количество ячеек и размеры сетки.
- `GetRegion()` выбрасывает исключение, если индекс, столбец или строка выходят за пределы атласа.
- Храни `TextureResourceManager` в течение нужного периода работы игры и вызывай `Dispose()`, когда его ресурсы больше не нужны. Не создавай новый менеджер каждый кадр.
- После освобождения менеджером текстуры не используй старые `TextureHandle` в новых командах отрисовки.

## TilemapRenderer: отрисовка тайловых чанков

`TilemapRenderer` предназначен для отрисовки двумерных тайловых карт через `IGraphicsDevice`. Он использует `TextureAtlas`, чтобы брать изображения тайлов из одной текстуры, и `Camera2D`, чтобы не отправлять команды для невидимой части карты.

### Создание рендерера

```csharp
using Engine.Graphics.Tilemaps;

var tilemapRenderer =
    new TilemapRenderer(
        context.Graphics,
        context.Camera,
        atlas,
        tileSize: 1.0f);
```

`atlas` — созданный ранее `TextureAtlas`. Параметр `tileSize` задаёт размер тайла в мировых единицах; значение должно быть больше нуля.

### Отрисовка чанка

Для `RenderChunk()` передаются координаты чанка, его размеры в тайлах и массив индексов:

```csharp
uint[] tiles =
[
    1, 2, 0,
    3, 4, 0,
    0, 0, 5
];

tilemapRenderer.RenderChunk(
    chunkX: 0,
    chunkY: 0,
    width: 3,
    height: 3,
    tiles: tiles);
```

В этом примере `0` обозначает пустую клетку. Остальные значения — индексы тайлов, начинающиеся с `1`: значение `1` соответствует первой области атласа, `2` — второй и так далее.

Данные хранятся построчно: сначала все клетки строки с `Y = 0`, затем следующей строки. Количество элементов должно точно равняться `width × height`.

### Отсечение невидимых тайлов

Рендерер проверяет, пересекается ли чанк с `Camera2D.WorldBounds`. Если чанк полностью находится вне области просмотра, он пропускается.

Для видимого чанка дополнительно вычисляется диапазон клеток, попадающих в область камеры. Поэтому команды отправляются только для видимых ненулевых тайлов.

Координаты чанка определяют его положение в сетке: в текущей реализации начало чанка вычисляется как `chunkX × width` и `chunkY × height` в мировых единицах карты.

### Важные правила

- `TilemapRenderer` самостоятельно не хранит карту и не загружает данные чанков из `Engine.World`. Игровой код передаёт массив тайлов при каждом вызове `RenderChunk()`.
- Все ненулевые значения должны соответствовать существующим индексам атласа.
- Размер тайла в атласе задаётся в пикселях, а `tileSize` — в мировых единицах.
- Рендерер отправляет команды в графическое устройство, но не управляет жизненным циклом кадра.



### 13. Content и Assets
## Пути к ресурсам и источники ассетов

VibeEngine2 разделяет путь к ресурсу, источник его данных и загрузку ресурса в конкретный тип.

### AssetPath

`AssetPath` из `Engine.Core.Assets` представляет путь к ассету. Он нормализует разделители каталогов, приводя обратные косые черты к `/`, и убирает разделители по краям строки.

```csharp
using Engine.Core.Assets;

var path =
    new AssetPath("Textures/terrain.png");
```

Путь указывается относительно корня используемого источника ассетов, а не обязательно относительно рабочего каталога приложения.

### Чтение исходных данных

`IAssetSource` предоставляет метод `Load(AssetPath)`, возвращающий исходные данные в виде `ReadOnlyMemory<byte>`.

В приложении на базе `DesktopGameHost` источник доступен через `context.AssetSource`:

```csharp
using Engine.Core.Assets;

var bytes =
    context.AssetSource.Load(
        new AssetPath("Textures/terrain.png"));
```

В стандартной desktop-конфигурации `FileAssetSource` читает файлы из каталога `Assets` рядом с исполняемым приложением, если каталог явно не задан через `DesktopGameHostOptions.AssetsDirectory`.

Файловый источник проверяет, что запрошенный путь не выходит за пределы корневого каталога. Если файл отсутствует, чтение завершается исключением.

### Каталог содержимого

`IContentCatalog` отвечает за сведения об ассетах, доступных для загрузки. Каталог позволяет получить список ресурсов, проверить наличие пути и найти соответствующее описание `ContentAsset`.

Стандартный `FileContentCatalog` сканирует файлы в корневом каталоге и его подкаталогах. Метод `Refresh()` обновляет список обнаруженных файлов.

Важно различать эти механизмы:

- `IAssetSource` предоставляет исходные байты.
- `IContentCatalog` сообщает, какие ассеты зарегистрированы в каталоге.
- `IContentManager` загружает ассеты в запрошенные типы через зарегистрированные загрузчики.

### Важные правила

- Используй относительные `AssetPath`, чтобы игровой код не зависел от абсолютных путей конкретной машины.
- Наличие файла в источнике данных само по себе не гарантирует, что `IContentManager` сможет загрузить его в произвольный тип.
- Если файлы добавляются после создания `FileContentCatalog`, вызови `Refresh()`, чтобы обновить каталог.
- Источник ассетов и каталог содержимого — отдельные объекты с разными обязанностями.

## IContentManager: загрузка и кэширование

`IContentManager` загружает ассеты в нужные типы через зарегистрированные загрузчики и кэширует полученные объекты. В приложении на основе `DesktopGameHost` доступ к менеджеру предоставляется через `context.Content`.

### Загрузка ресурса

Например, чтобы загрузить данные изображения:

```csharp
using Engine.Core.Assets;
using Engine.Graphics.Resources;

var path =
    new AssetPath("Textures/terrain.png");

TextureData textureData =
    context.Content.Load<TextureData>(path);
```

В стандартном desktop-host зарегистрирован `ImageTextureContentLoader`, который загружает данные изображений в `TextureData` для поддерживаемых форматов: PNG, JPEG, BMP и TGA.

Файл должен присутствовать в каталоге содержимого, а для запрошенного типа должен быть зарегистрирован подходящий загрузчик. Иначе загрузка завершится исключением.

`TextureData` содержит пиксельные данные, но ещё не является графическим ресурсом. Для создания текстуры используй `context.Graphics.Textures.Create(textureData)`.

### Проверка кэша

Метод `IsLoaded<T>()` позволяет проверить, загружен ли ресурс указанного типа по заданному пути:

```csharp
if (context.Content.IsLoaded<TextureData>(path))
{
    // Данные изображения уже находятся в кэше.
}
```

Проверка не загружает ресурс и не увеличивает количество ссылок на него.

Повторный вызов `Load<T>()` для уже загруженного ресурса возвращает закэшированный объект и увеличивает число внешних ссылок на него.

### Освобождение ресурса

Когда ресурс больше не нужен, освободи соответствующую ссылку через `Unload<T>()`:

```csharp
bool unloaded =
    context.Content.Unload<TextureData>(path);
```

Каждому внешнему вызову `Load<T>()` должна соответствовать операция освобождения. Ресурс удаляется из кэша, когда на него больше не остаётся внешних ссылок или зависимостей от других ресурсов.

Метод возвращает `false`, если для указанного типа и пути нет загруженного ресурса с доступной внешней ссылкой для освобождения.

### Повторная загрузка

`Reload<T>()` предназначен для повторной загрузки ресурса по тому же пути. Если ресурс ещё не загружен, метод загружает его обычным способом.

Повторная загрузка существующего ресурса имеет ограничения: она невозможна при нескольких внешних ссылках, активных зависимостях или параллельной асинхронной загрузке этого ресурса. В таких случаях метод выбрасывает исключение.

### Очистка кэша

`ClearCache()` очищает весь кэш и освобождает закэшированные объекты, реализующие `IDisposable`.

Используй этот метод, только когда действительно нужно очистить кэш целиком и все использующие его системы готовы к потере загруженных объектов. Для обычного освобождения одного ресурса предпочтительнее `Unload<T>()`.

### Важные правила

- Ключ кэша включает тип ресурса и `AssetPath`: один путь может использоваться для разных типов, если для них существуют подходящие загрузчики.
- Не считай `IsLoaded<T>()` подтверждением того, что ресурс пригоден для любой графической операции: проверяй, какой именно тип данных загружен.
- Не освобождай ресурс, пока его используют другие системы.
- `IContentManager` управляет объектами данных; графические ресурсы,

## Асинхронная загрузка ресурсов

`IContentManager` предоставляет `LoadAsync<T>()` для асинхронной загрузки ресурсов. Этот метод подходит для подготовки игровых данных, когда не требуется блокировать вызывающий код синхронным ожиданием результата.

### Загрузка ресурса

```csharp
using Engine.Core.Assets;
using Engine.Graphics.Resources;

var path =
    new AssetPath("Textures/terrain.png");

TextureData textureData =
    await context.Content.LoadAsync<TextureData>(
        path,
        cancellationToken);
```

В примере `cancellationToken` — токен отмены, который передаётся из вызывающего кода. Если отдельный токен не нужен, параметр можно опустить.

### Отмена загрузки

Передача `CancellationToken` позволяет запросить отмену асинхронной операции:

```csharp
using var cancellation =
    new CancellationTokenSource();

var task =
    context.Content.LoadAsync<TextureData>(
        path,
        cancellation.Token);

// Когда загрузка больше не нужна:
cancellation.Cancel();
```

Вызов `Cancel()` запрашивает отмену, но не гарантирует, что операция немедленно прекратится. При обработке отмены может быть выброшено `OperationCanceledException`.

### Важные правила

- Для получения результата необходимо дождаться завершения `LoadAsync<T>()` через `await`.
- Повторные загрузки того же типа и пути используют кэш содержимого.
- Асинхронная загрузка не означает, что полученный ресурс сразу готов к использованию графическим backend: например, `TextureData` и созданная из неё графическая текстура — разные ресурсы.
- Передавай токен отмены, если операция связана с переключением игровых экранов или другой ситуацией, в которой загрузка может потерять актуальность.

## Собственные загрузчики содержимого

Если игре нужен собственный тип ресурса, можно реализовать `IContentLoader<T>` и зарегистрировать его через `DesktopGameHostOptions.ConfigureContentLoaders`.

Загрузчик определяет, какие файлы он поддерживает, и преобразует данные ассета в объект нужного типа.

### Пример: загрузка текстового файла

Создадим тип ресурса и загрузчик для файлов `.txt`:

```csharp
using System.Text;
using Engine.Content.Assets;
using Engine.Content.Loading;
using Engine.Core.Assets;

public sealed record TextAsset(string Text);

public sealed class TextAssetLoader :
    IContentLoader<TextAsset>
{
    public Type AssetType => typeof(TextAsset);

    public bool CanLoad(ContentAsset asset)
    {
        return asset.Extension.Equals(
            ".txt",
            StringComparison.OrdinalIgnoreCase);
    }

    public TextAsset Load(
        AssetPath path,
        IContentLoadContext context)
    {
        ArgumentNullException.ThrowIfNull(context);

        var bytes = context.ReadBytes(path);

        return new TextAsset(
            Encoding.UTF8.GetString(bytes.Span));
    }

    public async ValueTask<TextAsset> LoadAsync(
        AssetPath path,
        IContentLoadContext context,
        CancellationToken cancellationToken = default)
    {
        ArgumentNullException.ThrowIfNull(context);

        var bytes = await context.ReadBytesAsync(
            path,
            cancellationToken);

        cancellationToken.ThrowIfCancellationRequested();

        return new TextAsset(
            Encoding.UTF8.GetString(bytes.Span));
    }

    object IContentLoader.Load(
        AssetPath path,
        IContentLoadContext context)
    {
        return Load(path, context);
    }
}
```

Загрузчик использует:

- `CanLoad()` — определяет, подходит ли ассет для этого загрузчика.
- `Load()` — выполняет синхронное чтение и преобразование данных.
- `LoadAsync()` — выполняет асинхронное чтение с поддержкой отмены.
- `AssetType` — сообщает менеджеру тип создаваемого ресурса.

Асинхронный метод реализован отдельно, поскольку стандартная реализация `IContentLoader<T>.LoadAsync()` по умолчанию вызывает синхронный `Load()`. Если загрузчику важно действительно асинхронное чтение, этот метод следует переопределить.

### Регистрация в DesktopGameHost

Зарегистрируй загрузчик в настройках приложения до создания `ContentManager`:

```csharp
using Engine.Hosting.Desktop;

var options = new DesktopGameHostOptions
{
    ConfigureContentLoaders = loaders =>
    {
        loaders.Register(new TextAssetLoader());
    }
};

DesktopGameHost.Run(
    context => new MyGame(context),
    options);
```

`MyGame` здесь обозначает класс приложения игры. Стандартный host регистрирует собственный загрузчик изображений, а затем вызывает `ConfigureContentLoaders`, чтобы добавить пользовательские загрузчики.

### Использование ресурса

Положим текстовый файл `intro.txt` в папку `Assets/Data` игрового проекта. Загрузить его можно через обычный `IContentManager`:

```csharp
using Engine.Core.Assets;

var intro = context.Content.Load<TextAsset>(
    new AssetPath("Data/intro.txt"));

string text = intro.Text;
```

Менеджер выберет загрузчик, подходящий запрошенному типу `TextAsset` и расширению файла.

### Важные правила

- Путь `AssetPath` указывается относительно корня ассетов.
- `CanLoad()` должен возвращать `true` только для файлов, которые загрузчик действительно способен обработать.
- Для одного ассета и запрошенного типа не должно быть нескольких подходящих загрузчиков: такая неоднозначность приводит к `InvalidOperationException`.
- Необязательно писать отдельный загрузчик для каждого расширения: один загрузчик может поддерживать несколько форматов, если умеет их корректно обрабатывать.

## Кэширование, выгрузка и время жизни ресурсов

`IContentManager` кэширует загруженные ресурсы по типу и пути ассета. Повторная загрузка одного и того же ресурса позволяет повторно использовать существующий объект, не создавая его заново.

### Повторная загрузка

```csharp
using Engine.Core.Assets;

var path = new AssetPath("Data/intro.txt");

var first = context.Content.Load<TextAsset>(path);
var second = context.Content.Load<TextAsset>(path);

bool sameObject = ReferenceEquals(first, second);
```

Если ресурс уже находится в кэше, оба вызова возвращают один и тот же объект. При этом каждый вызов `Load<T>()` увеличивает счётчик внешних ссылок менеджера.

Это означает, что каждый успешный вызов `Load<T>()` должен соответствовать освобождению полученной ссылки через `Unload<T>()`, когда ресурс больше не нужен вызывающему коду.

### Освобождение ссылки

```csharp
context.Content.Unload<TextAsset>(path);
context.Content.Unload<TextAsset>(path);
```

`Unload<T>()` уменьшает количество внешних ссылок на ресурс. Если внешних ссылок и ссылок-зависимостей больше нет, ресурс удаляется из кэша. Если на него ещё ссылаются другие ресурсы, он остаётся загруженным.

Метод возвращает `true`, если внешняя ссылка была освобождена, и `false`, если ресурс не найден в кэше или внешних ссылок для освобождения уже нет.

**Правило:** вызывай `Unload<T>()` один раз на каждый соответствующий вызов `Load<T>()`. Не используй объект после того, как его последняя ссылка была освобождена и менеджер мог уничтожить его.

### Проверка кэша

Метод `IsLoaded<T>()` позволяет проверить, есть ли ресурс в кэше:

```csharp
if (context.Content.IsLoaded<TextAsset>(path))
{
    // Ресурс сейчас находится в кэше.
}
```

Проверка не увеличивает счётчик ссылок и не загружает ресурс. Она сообщает только о его присутствии в кэше на момент проверки.

### Перезагрузка ресурса

`Reload<T>()` предназначен для повторной загрузки ресурса, например после изменения файла. Однако перезагрузить ресурс можно не во всех ситуациях.

Операция может завершиться `InvalidOperationException`, если ресурс сейчас загружается асинхронно, на него есть несколько внешних ссылок или он используется как зависимость другого ресурса.

Поэтому перезагрузку следует выполнять в контролируемый момент, когда известны владельцы ресурса и его зависимости.

### Полная очистка кэша

```csharp
context.Content.ClearCache();
```

`ClearCache()` очищает кэш целиком и вызывает `Dispose()` для закэшированных объектов, реализующих `IDisposable`.

Это не обычная замена `Unload<T>()`, а операция полного сброса кэша. Не вызывай её, пока игровой код продолжает использовать ресурсы из этого кэша.

### Важные правила

- `Load<T>()` и `LoadAsync<T>()` используются для получения ресурсов; освобождай внешние ссылки через `Unload<T>()`.
- Одинаковый путь, загруженный как разные типы, представляет разные записи кэша.
- `IsLoaded<T>()` проверяет наличие ресурса, но не получает на него ссылку.
- Используй `Reload<T>()` для контролируемой перезагрузки, а `ClearCache()` — только тогда, когда действительно нужно сбросить весь кэш.
- Не считай выгрузку безопасной, если другие части игры всё ещё используют ресурс.

### 14. Audio
## Загрузка аудиоресурсов

Для загрузки звука используется `IAudioManager`, доступный через `context.Audio` в приложении на основе `DesktopGameHost`.

Менеджер читает файл, декодирует аудиоданные и создаёт буфер, который затем можно использовать для воспроизведения.

### Загрузка звука

Положим WAV-файл `click.wav` в папку `Assets/Audio` игрового проекта:

```csharp
using Engine.Core.Assets;

var sound = context.Audio.Load(
    new AssetPath("Audio/click.wav"));
```

Метод `Load()` возвращает `IAudioBuffer` — аудиобуфер, подготовленный для использования аудиоустройством.

### Поддерживаемые форматы

В текущей реализации загрузчик поддерживает WAV с несжатым PCM-аудио. Поддерживаются моно- и стереозаписи с разрядностью 8 или 16 бит.

Другие форматы WAV, а также форматы файлов, отличные от WAV, текущим загрузчиком не поддерживаются и могут приводить к исключению.

### Кэширование

Менеджер аудиоресурсов кэширует загруженные буферы по `AssetPath`. Повторный вызов `Load()` для того же пути возвращает существующий буфер, если он уже загружен.

```csharp
var first = context.Audio.Load(
    new AssetPath("Audio/click.wav"));

var second = context.Audio.Load(
    new AssetPath("Audio/click.wav"));

bool sameBuffer =
    ReferenceEquals(first, second);
```

В стандартной реализации оба вызова используют один и тот же объект буфера.

### Время жизни буфера

В стандартном desktop-host загруженные буферы принадлежат менеджеру аудио и освобождаются при освобождении самого менеджера. Интерфейс `IAudioManager` не предоставляет отдельного метода выгрузки одного буфера.

Поэтому не вызывай `Dispose()` для буфера, полученного через `context.Audio.Load()`, пока он остаётся в кэше менеджера: повторная загрузка того же пути может вернуть уже освобождённый объект.

### Важные правила

- Используй `AssetPath` относительно корня ассетов, а не абсолютный путь к файлу.
- Загружай звук один раз и сохраняй полученный буфер для последующего использования.
- `IAudioBuffer` хранит аудиоресурс; для управления воспроизведением используется отдельный интерфейс `IAudioSource`.
- Не путай буфер аудиоданных с источником воспроизведения: один буфер может использоваться несколькими источниками.

## Воспроизведение и управление источниками

`IAudioSource` представляет источник воспроизведения аудио. Он связывает загруженный `IAudioBuffer` с управлением воспроизведением, громкостью, высотой тона и зацикливанием.

### Создание и запуск источника

```csharp
using Engine.Core.Assets;

var sound = context.Audio.Load(
    new AssetPath("Audio/click.wav"));

var source = context.Audio.CreateSource(sound);

source.SetGain(0.75f);
source.SetPitch(1.0f);
source.SetLooping(false);

source.Play();
```

В примере громкость установлена на 75% от стандартного уровня, высота тона не изменена, а зацикливание отключено.

После настройки `Play()` запускает воспроизведение. Настройки источника можно изменять и в дальнейшем.

### Управление воспроизведением

`IAudioSource` предоставляет несколько методов управления:

```csharp
source.Pause();   // Приостановить.
source.Play();    // Запустить или продолжить.
source.Stop();    // Остановить.
source.Rewind();  // Перемотать к началу.
```

Точное поведение воспроизведения после остановки может зависеть от используемого аудиобэкенда. Если нужно явно вернуться к началу, используй `Rewind()` перед повторным запуском.

### Изменение параметров

Громкость и высота тона регулируются отдельно:

```csharp
source.SetGain(0.5f);
source.SetPitch(1.2f);
source.SetLooping(true);
```

- `SetGain(float)` задаёт усиление источника. Отрицательные значения не допускаются.
- `SetPitch(float)` задаёт высоту тона и скорость воспроизведения. Значение должно быть больше нуля.
- `SetLooping(bool)` включает или отключает повторное воспроизведение.

Значения усиления и высоты тона не ограничены единицей, если соблюдаются условия валидации. Конкретный слышимый результат зависит от аудиобэкенда.

### Упрощённый запуск

Если нужно сразу начать воспроизведение, можно использовать `IAudioManager.Play()`:

```csharp
var source = context.Audio.Play(sound);
```

Метод создаёт источник, запускает воспроизведение и возвращает `IAudioSource`. Возвращённый объект позволяет управлять запущенным источником.

### Время жизни источника

Созданный источник необходимо освобождать, когда он больше не нужен:

```csharp
source.Stop();
source.Dispose();
```

Храни ссылки на используемые источники в состоянии игры и освобождай их при завершении соответствующего игрового объекта или приложения. Не вызывай `Dispose()` сразу после `Play()`, если воспроизведение должно продолжаться.

Загруженный `IAudioBuffer` имеет отдельное время жизни: в стандартной реализации desktop-host им управляет аудиоменеджер.

### Важные правила

- Один аудиобуфер можно использовать для создания нескольких источников, например для одновременного воспроизведения нескольких одинаковых звуков.
- Для одновременного независимого управления воспроизведением нужны отдельные `IAudioSource`.
- Источник и буфер — разные ресурсы; освобождение источника не означает, что игровой код должен самостоятельно освобождать буфер.
- `IAudioSource` не предоставляет универсального свойства состояния воспроизведения, поэтому автоматическое определение момента окончания звука необходимо организовать отдельно.

## Audio Listener и пространственные параметры

`IAudioListener` представляет слушателя, относительно которого воспроизводится пространственный звук. Интерфейс позволяет задавать позицию, скорость, усиление и ориентацию слушателя.

Для источника `IAudioSource` доступны позиция и скорость в трёхмерных координатах.

### Создание слушателя

```csharp
using Engine.Audio;
using Engine.Core.Math;

IAudioListener listener =
    context.Audio.CreateListener();

listener.SetPosition(
    new Vector3(0.0f, 0.0f, 0.0f));

listener.SetOrientation(
    new Vector3(0.0f, 0.0f, -1.0f),
    new Vector3(0.0f, 1.0f, 0.0f));
```

`SetOrientation()` принимает два вектора: направление взгляда (`forward`) и направление вверх (`up`). Они задают ориентацию слушателя.

В примере слушатель находится в начале координат и ориентирован вдоль отрицательной оси Z.

### Позиция и скорость источника

Положение источника можно задать через `SetPosition()`, а скорость — через `SetVelocity()`:

```csharp
source.SetPosition(
    new Vector3(5.0f, 0.0f, 0.0f));

source.SetVelocity(
    new Vector3(0.0f, 0.0f, 0.0f));
```

Эти параметры позволяют аудиобэкенду учитывать пространственное положение источника и его движение при обработке звука.

### Обновление слушателя

В игре слушатель обычно следует за игроком или игровой камерой. Например, при перемещении игрока можно обновлять позицию слушателя:

```csharp
listener.SetPosition(playerPosition);
```

Здесь `playerPosition` — позиция игрока, преобразованная в `Engine.Core.Math.Vector3`.

Для обновления скорости слушателя предусмотрен `SetVelocity()`. Позиция и скорость источника также должны обновляться игровым кодом, если звук связан с движущимся объектом.

### Усиление слушателя

`SetGain()` позволяет изменить общий уровень усиления слушателя:

```csharp
listener.SetGain(0.5f);
```

Значение должно быть неотрицательным. Усиление слушателя влияет на общий уровень воспринимаемого аудио, тогда как `IAudioSource.SetGain()` регулирует отдельный источник.

### Время жизни и ограничения

- Создавай слушателя один раз для соответствующего игрового контекста и освобождай его через `Dispose()`, когда он больше не нужен.
- `DesktopGameHostContext` не привязывает слушателя к камере автоматически. Связь с положением игрока или камеры организует игра.
- Используй согласованную систему координат для источников и слушателя. API не преобразует координаты автоматически из `Camera2D` или фиксированных ECS-компонентов.
- В текущем OpenAL-бэкенде состояние слушателя относится к аудиоустройству. Несколько объектов `IAudioListener` не представляют независимые одновременно работающие точки прослушивания.
- Конкретный эффект пространственного позиционирования зависит от аудиобэкенда и формата звукового ресурса.

### 15. UI
## Дерево UI-элементов

UI-система находится в проекте `Engine.UI`. Она предоставляет базовые элементы, контейнеры и механизм обновления, компоновки, отображения и обработки пользовательского ввода.

### Создание UI-системы

Для приложения на основе `DesktopGameHost` создай `UiSystem`, используя графическое устройство и сервисы ввода из `DesktopGameHostContext`:

```csharp
using Engine.UI.Core;

var ui = new UiSystem(
    context.Graphics,
    width,
    height,
    context.PointerInput,
    context.TextInput,
    context.Cursor);
```

`width` и `height` — размеры области отображения интерфейса.

Корневой элемент доступен через `ui.Root`. Он представляет собой `UiRoot`, производный от `UiCanvas`, к которому можно добавлять элементы интерфейса.

### Контейнеры и дочерние элементы

`UiContainer` позволяет формировать иерархию с помощью методов `AddChild()`, `RemoveChild()` и `ClearChildren()`.

Например, создадим панель с заголовком и кнопкой:

```csharp
using Engine.Graphics.Commands;
using Engine.UI.Controls;
using Engine.UI.Layout;

var panel = new UiPanel
{
    Width = 280.0f,
    Height = 140.0f,

    Padding = new UiThickness(12.0f),

    Background = new UiColor(
        24, 28, 36, 230),

    HorizontalAlignment =
        UiHorizontalAlignment.Left,

    VerticalAlignment =
        UiVerticalAlignment.Top
};

var stack = new UiStackPanel
{
    Orientation = UiOrientation.Vertical,
    Spacing = 8.0f
};

stack.AddChild(
    new UiLabel("Main Menu")
    {
        FontSize = 24.0f
    });

var startButton = new UiButton("Start");

startButton.Clicked += OnStartClicked;

stack.AddChild(startButton);
panel.AddChild(stack);
ui.Root.AddChild(panel);
```

`OnStartClicked` здесь — метод игровой логики, который необходимо реализовать в своём классе.

В этом примере используется несколько видов элементов:

- `UiPanel` — контейнер с фоном и внутренними отступами.
- `UiStackPanel` — контейнер, размещающий дочерние элементы вертикально или горизонтально.
- `UiLabel` — текстовая надпись.
- `UiButton` — интерактивная кнопка с событием `Clicked`.

Все они являются виджетами, поэтому могут входить в общее дерево интерфейса.

### Управление дочерними элементами

Добавить существующий виджет можно через `AddChild()`:

```csharp
panel.AddChild(new UiLabel("Status"));
```

Удаление выполняется через `RemoveChild()`:

```csharp
bool removed = panel.RemoveChild(startButton);
```

Метод возвращает `true`, если элемент был удалён. `ClearChildren()` удаляет всех непосредственных дочерних элементов контейнера.

Один виджет не может одновременно принадлежать двум родителям. Если элемент уже включён в дерево, сначала необходимо удалить его из прежнего контейнера.

### Обновление и отображение интерфейса

`UiSystem` не требует ручного вызова каждого виджета: система обрабатывает дерево целиком.

В обычном цикле приложения вызывай:

```csharp
ui.Update(deltaSeconds);
```

для обновления интерфейса и обработки ввода, а в фазе отображения:

```csharp
ui.Render();
```

для отправки команд отрисовки UI.

При изменении размера окна обновляй область отображения:

```csharp
ui.Resize(width, height);
```

В стандартном desktop-host графическим кадром управляет host. Поэтому не нужно вызывать `BeginFrame()` или `EndFrame()` из кода UI.

### Важные правила

- Создавай `UiSystem` один раз для соответствующего игрового контекста, а не каждый кадр.
- Дочерние элементы добавляй через контейнер, который должен ими владеть.
- Для обработки клика подписывайся на событие `UiButton.Clicked`.
- При использовании `PointerInput` учитывай, что сервис указателя может отсутствовать. Без него `UiSystem` не сможет создать свой маршрутизатор ввода.
- `UiSystem` должен обновляться и отображаться в соответствующих фазах приложения, а размер области UI необходимо синхронизировать с реальной областью отображения.

## Layout и размеры элементов

Каждый `UiWidget` имеет параметры размера, выравнивания и отступов. Они определяют, как элемент располагается внутри доступной родительской области.

### Ширина и высота

Свойства `Width` и `Height` задают размеры элемента. Если значение не задано (`null`), система рассчитывает размер на основе содержимого или доступной области — в зависимости от режима компоновки.

```csharp
var panel = new UiPanel
{
    Width = 320.0f,
    Height = 180.0f
};
```

Размеры задаются в единицах области UI, которая в стандартном desktop-приложении соответствует размеру переданного viewport.

### Выравнивание

Для обычного режима компоновки используются `HorizontalAlignment` и `VerticalAlignment`.

Горизонтальное выравнивание (`UiHorizontalAlignment`):

- `Stretch` — заполнить доступную ширину;
- `Left` — расположить слева;
- `Center` — расположить по центру;
- `Right` — расположить справа.

Вертикальное выравнивание (`UiVerticalAlignment`):

- `Stretch` — заполнить доступную высоту;
- `Top` — расположить сверху;
- `Center` — расположить по центру;
- `Bottom` — расположить снизу.

Например, закрепим небольшую панель в правом нижнем углу области родителя:

```csharp
var panel = new UiPanel
{
    Width = 240.0f,
    Height = 100.0f,

    HorizontalAlignment =
        UiHorizontalAlignment.Right,

    VerticalAlignment =
        UiVerticalAlignment.Bottom,

    Margin = new UiThickness(
        0.0f, 0.0f, 16.0f, 16.0f)
};
```

`Margin` задаёт внешние отступы элемента. В `UiThickness` значения передаются в порядке `Left`, `Top`, `Right`, `Bottom`. Также можно задать одинаковый отступ со всех сторон:

```csharp
Margin = new UiThickness(8.0f);
```

### Padding и Margin

Это два разных понятия:

- `Margin` — внешнее пространство вокруг виджета.
- `Padding` — внутренние отступы содержимого контейнера, например `UiPanel`.

```csharp
var panel = new UiPanel
{
    Padding = new UiThickness(12.0f)
};
```

Внутренние отступы панели уменьшают область, передаваемую её дочерним элементам. `Padding` предусмотрен у контейнеров, которые его поддерживают, например у `UiPanel` и `UiButton`.

### UiCanvas и позиционирование

`UiCanvas` позволяет задавать положение непосредственных дочерних элементов относительно области холста с помощью `SetPosition()`.

```csharp
using Engine.Core.Math;
using Engine.UI.Controls;
using Engine.UI.Layout;

var button = new UiButton("Start")
{
    Width = 180.0f,
    Height = 42.0f
};

ui.Root.AddChild(button);

ui.Root.SetPosition(
    button,
    new Vector2(24.0f, 24.0f));
```

Здесь элемент размещается внутри корневого холста со смещением от его верхнего левого угла. Для вложенного элемента `SetPosition()` нужно вызывать на том `UiCanvas`, которому он непосредственно принадлежит.

### Anchor — привязка к точке родителя

Для размещения относительно определённой точки родительской области предусмотрен режим `UiLayoutMode.Anchor`.

```csharp
using Engine.Core.Math;
using Engine.UI.Layout;

var button = new UiButton("Settings")
{
    Width = 160.0f,
    Height = 40.0f,

    LayoutMode = UiLayoutMode.Anchor,
    Anchor = UiAnchor.BottomRight,

    Offset = new Vector2(-16.0f, -16.0f)
};

ui.Root.AddChild(button);
```

`Anchor` задаёт точку привязки элемента и соответствующую точку родительской области. `Offset` задаёт смещение от неё. В этом примере кнопка располагается в правом нижнем углу с отступом внутрь области.

Доступны готовые значения `UiAnchor`: `TopLeft`, `TopCenter`, `TopRight`, `CenterLeft`, `Center`, `CenterRight`, `BottomLeft`, `BottomCenter` и `BottomRight`. Координаты пользовательского `UiAnchor` должны находиться в диапазоне от `0` до `1`.

### Важные правила

- Используй выравнивание, когда элемент должен занимать доступную область или располагаться у её края.
- Используй `UiCanvas.SetPosition()`, когда нужно задать смещение дочернего элемента в холсте.
- Используй `Anchor` и `Offset`, когда положение должно рассчитываться относительно точки родителя, например для кнопки в углу экрана.
- Не путай `Margin` с `Padding`: первое влияет на размещение самого элемента, второе — на внутреннюю область контейнера.
- После изменения размера окна вызывай `UiSystem.Resize()`, чтобы компоновка пересчиталась для новой области отображения.

## Обработка взаимодействия

`UiSystem` обрабатывает взаимодействие с элементами интерфейса через маршрутизатор ввода. Он определяет виджет под указателем, передаёт события по дереву элементов и управляет фокусом клавиатуры.

Маршрутизатор создаётся автоматически, если при создании `UiSystem` переданы оба сервиса: `IPointerInput` и `ITextInput`.

### Событие нажатия кнопки

У `UiButton` есть событие `Clicked`, которое вызывается при активации кнопки:

```csharp
var startButton = new UiButton("Start");

startButton.Clicked += () =>
{
    StartGame();
};

ui.Root.AddChild(startButton);
```

`StartGame()` здесь — метод игровой логики, который необходимо реализовать самостоятельно.

Кнопка обрабатывает нажатие левой кнопки мыши и активацию через клавиатурный фокус. Событие `Clicked` удобно использовать для открытия экранов, запуска игры и выполнения других действий интерфейса.

### Состояние указателя

Каждый `UiWidget` предоставляет свойства, позволяющие проверить его текущее состояние:

- `IsHovered` — указатель находится над элементом.
- `IsPressed` — элемент находится в состоянии нажатия.
- `Enabled` — элемент включён и доступен для взаимодействия.
- `Visible` — элемент отображается.
- `IsHitTestVisible` — элемент участвует в определении виджета под указателем.

Например, чтобы временно отключить кнопку:

```csharp
startButton.Enabled = false;
```

Отключённый виджет не обрабатывает обычное взаимодействие через маршрутизатор ввода. Свойство `Visible` управляет отображением элемента и также влияет на доступность взаимодействия.

### Фокус клавиатуры

Элементы, способные получать фокус, имеют свойство `Focusable`. Например, `UiButton` и `UiTextBox` включают его в своих конструкторах.

Получить текущий фокус можно через `ui.Focus.FocusedWidget`:

```csharp
var focused = ui.Focus.FocusedWidget;
```

Управлять фокусом можно через `UiFocusManager`:

```csharp
ui.Focus.SetFocus(startButton);

// Снять фокус.
ui.Focus.ClearFocus();
```

`SetFocus()` принимает только виджет, который находится в дереве соответствующего `UiSystem`, доступен для взаимодействия и имеет `Focusable = true`. Если условия не выполнены, вызов не устанавливает фокус.

`UiFocusManager` также предоставляет `MoveNext()` и `MovePrevious()` для перемещения между доступными элементами, а `Activate()` активирует элемент в фокусе через механизм `Submit`.

В стандартном маршрутизаторе стрелки вверх и вниз перемещают фокус, Enter активирует текущий элемент, а Escape может снять фокус, если событие не было обработано виджетом.

### Текстовый ввод

Для редактирования текста используй `UiTextBox`:

```csharp
var nameBox = new UiTextBox
{
    Placeholder = "Enter player name",
    MaxLength = 32
};

nameBox.TextChanged += text =>
{
    // Текст изменился.
};

nameBox.Submitted += text =>
{
    // Пользователь подтвердил ввод.
};

ui.Root.AddChild(nameBox);
```

`TextChanged` вызывается при изменении текста, а `Submitted` — при отправке значения, например через Enter, когда поле находится в фокусе.

Текст можно задавать программно через `SetText()`:

```csharp
nameBox.SetText("Player");
```

Свойство `Text` доступно для чтения, а `SetText()` позволяет изменить значение с учётом `MaxLength`. При вводе с клавиатуры поле поддерживает перемещение курсора, удаление текста и позиционирование курсора кликом мыши.

### Другие интерактивные элементы

`UiToggle` предоставляет состояние `IsOn` и событие `ValueChanged`:

```csharp
var soundToggle = new UiToggle("Sound");

soundToggle.ValueChanged += enabled =>
{
    // Включить или выключить звук в игре.
};

soundToggle.SetValue(true);
ui.Root.AddChild(soundToggle);
```

`SetValue()` вызывает `ValueChanged`, если значение действительно изменилось. Метод `Toggle()` переключает состояние на противоположное.

### Маршрутизация событий и важные правила

События указателя передаются от целевого виджета вверх по цепочке его родителей. Обработчик может установить `UiPointerEvent.Handled = true`, чтобы прекратить дальнейшую передачу события.

При создании собственных типов виджетов можно переопределять защищённые методы `OnPointerDown()`, `OnPointerUp()`, `OnPointerMove()`, `OnPointerEnter()` и `OnPointerLeave()`. Для обработки событий клавиатуры доступны `OnKeyEvent()` и `OnSubmit()`.

Основные правила:

- Подписывайся на `Clicked`, `TextChanged` и `ValueChanged`, когда достаточно стандартного поведения контролов.
- Используй `UiFocusManager`, если игровая логика должна программно устанавливать или снимать фокус.
- Для ввода текста поле должно быть доступно и находиться в фокусе.
- Вызывай `ui.Update(deltaSeconds)` каждый кадр, чтобы маршрутизатор обрабатывал ввод и обновлял состояние UI.
- Если нужно перехватить событие внутри собственного виджета, устанавливай `Handled` только тогда, когда событие действительно обработано.

## Экраны, меню и HUD

`UiScreen` представляет отдельный экран интерфейса, например главное меню, настройки или паузу. Каждый экран содержит корневой виджет `Root` и может реагировать на появление, закрытие и обновление.

### Переключение экранов

Менеджер экранов доступен через `ui.Screens`.

```csharp
using Engine.UI.Screens;

// Открыть главное меню.
ui.Screens.Replace(new MainMenuScreen());

// Открыть экран паузы поверх текущего.
ui.Screens.Push(
    new PauseMenuScreen(() =>
    {
        ui.Screens.Pop();
    }));
```

`MainMenuScreen` и `PauseMenuScreen` здесь — классы игры, унаследованные от `UiScreen`. Экран паузы принимает действие продолжения игры.

Основные операции менеджера:

- `Replace(screen)` — заменить текущий экран и очистить стек предыдущих экранов.
- `Push(screen)` — открыть новый экран поверх текущего, сохранив предыдущий в стеке.
- `Pop()` — закрыть верхний экран и вернуться к предыдущему. Возвращает `false`, если стек пуст.
- `Clear()` — очистить стек экранов.

При смене экрана вызываются `OnExit()` у предыдущего и `OnEnter()` у активируемого экрана. Экран может использовать эти методы для настройки состояния и фокуса.

### Собственный экран

Чтобы создать экран, унаследуйся от `UiScreen` и передай его корневой виджет базовому конструктору:

```csharp
using Engine.UI.Core;
using Engine.UI.Controls;
using Engine.UI.Input;
using Engine.UI.Screens;

public sealed class PauseMenuScreen : UiScreen
{
    private readonly UiButton _resumeButton;

    public PauseMenuScreen(Action onResume)
        : this(CreateRoot(onResume, out var button), button)
    {
    }

    private PauseMenuScreen(
        UiWidget root,
        UiButton resumeButton)
        : base(root)
    {
        _resumeButton = resumeButton;
    }

    private static UiWidget CreateRoot(
        Action onResume,
        out UiButton resumeButton)
    {
        var panel = new UiPanel
        {
            Width = 320.0f,
            Height = 200.0f,
            HorizontalAlignment =
                Engine.UI.Layout.UiHorizontalAlignment.Center,
            VerticalAlignment =
                Engine.UI.Layout.UiVerticalAlignment.Center
        };

        resumeButton = new UiButton("Resume");
        resumeButton.Clicked += onResume;

        panel.AddChild(resumeButton);

        return panel;
    }

    public override void OnEnter(UiFocusManager focus)
    {
        focus.SetFocus(_resumeButton);
    }
}
```

В этом примере создаётся простое меню паузы. В реальном экране можно добавить заголовок, настройки, кнопки и другие виджеты.

Корневой виджет нового экрана не должен уже принадлежать другому контейнеру: менеджер сам добавляет его в дерево UI.

### Оверлеи

Для временных элементов поверх экранов предусмотрен `UiOverlayLayer`. Он доступен через `ui.Overlays`, а также через методы `UiSystem`.

```csharp
using Engine.Core.Math;
using Engine.UI.Controls;

var popup = new UiPanel
{
    Width = 220.0f,
    Height = 100.0f
};

ui.ShowOverlay(
    popup,
    new Vector2(40.0f, 40.0f));

// Закрыть и убрать из дерева UI.
ui.HideOverlay(popup);
```

Оверлеи подходят для всплывающих окон, контекстных меню и временных подсказок. Они располагаются поверх обычного содержимого интерфейса и участвуют в обработке указателя.

`HideOverlay()` удаляет виджет из слоя оверлеев. После этого его можно добавить снова через `ShowOverlay()`.

### HUD игрового процесса

HUD — это обычная часть дерева UI, которая отображает информацию о состоянии игры: здоровье, ресурсы, координаты или подсказки управления.

Например, постоянную панель можно добавить непосредственно в `ui.Root`:

```csharp
using Engine.UI.Controls;
using Engine.UI.Layout;

var hud = new UiPanel
{
    Width = 250.0f,
    Height = 90.0f,

    Padding = new UiThickness(12.0f),

    HorizontalAlignment =
        UiHorizontalAlignment.Left,

    VerticalAlignment =
        UiVerticalAlignment.Top
};

var healthLabel = new UiLabel("HP: 100");

hud.AddChild(healthLabel);
ui.Root.AddChild(hud);
```

Ссылку на `healthLabel` можно сохранить и обновлять при изменении состояния игрока:

```csharp
healthLabel.Text = $"HP: {currentHealth}";
```

Если HUD добавлен непосредственно в `ui.Root`, он остаётся в дереве при переключении экранов через `ui.Screens`. При стандартных значениях `ZIndex` содержимое экранов будет отображаться поверх него, что удобно, например, для затемнения игрового интерфейса при открытии паузы.

Если HUD должен исчезать вместе с игровым экраном, включай его в корневое дерево соответствующего `UiScreen`.

### Важные правила

- Используй `Replace()` для полноценной замены экрана и `Push()` / `Pop()` для навигации с возвратом.
- Привязывай игровые действия к событиям UI, а само состояние игры храни отдельно от виджетов.
- Для постоянного HUD выбирай место в дереве с учётом того, должен ли он оставаться видимым при смене экранов.
- Используй оверлеи для временных окон, которым требуется приоритет над обычным интерфейсом.
- `UiScreenManager` не освобождает автоматически игровые ресурсы, принадлежащие экрану: их время жизни необходимо контролировать самостоятельно.

## Использование общих API вместо конкретного backend

VibeEngine2 разделяет пользовательский API и реализации отдельных подсистем. Игровая логика должна использовать общие интерфейсы, если ей не требуются специальные возможности конкретного backend.

Основные абстракции:

| Подсистема | Общий API |
|---|---|
| Графика | `IGraphicsDevice` из `Engine.Graphics` |
| Ввод действий | `IInput` из `Engine.Input` |
| Аудио | `IAudioManager` из `Engine.Audio` |
| Источники ассетов | `IAssetSource` из `Engine.Core.Assets` |
| Загрузка ресурсов | `IContentManager` из `Engine.Content` |
| Указатель | `IPointerInput` из `Engine.Input` |
| Текстовый ввод | `ITextInput` из `Engine.Input` |

### Использование сервисов приложения

В приложении на основе `DesktopGameHost` необходимые сервисы доступны через `DesktopGameHostContext`:

```csharp
using Engine.Core.Assets;
using Engine.Graphics;
using Engine.Input;
using Engine.Audio;

IGraphicsDevice graphics = context.Graphics;
IInput input = context.Input;
IAudioManager audio = context.Audio;

// Загрузка и запуск звука.
var sound = audio.Load(
    new AssetPath("Audio/click.wav"));

var source = audio.Play(sound);
```

Игровой код использует `IGraphicsDevice`, `IInput` и `IAudioManager`, не создавая напрямую конкретные реализации графического устройства, ввода или аудио.

### Передача зависимостей игровым системам

Если собственному классу игры нужен определённый сервис, лучше передавать его через конструктор или метод, используя подходящий интерфейс:

```csharp
using Engine.Audio;

public sealed class SoundEffects
{
    private readonly IAudioManager _audio;

    public SoundEffects(IAudioManager audio)
    {
        ArgumentNullException.ThrowIfNull(audio);
        _audio = audio;
    }

    // Методы игровой логики используют _audio.
}
```

Такой класс не обязан знать, какой конкретный аудиобэкенд создаёт буферы и воспроизводит звук. Это упрощает тестирование и снижает связанность игрового кода с инфраструктурой движка.

### Когда допустима зависимость от конкретного backend

Обращение к конкретной реализации оправдано, когда игра или инструмент намеренно использует специфическую возможность, которой нет в общем API.

Однако такую зависимость стоит локализовать в отдельном классе или адаптере, не распространяя её без необходимости на игровые системы и компоненты.

### Текущее ограничение стандартного host

Наличие общих интерфейсов не означает, что все backend уже можно свободно переключать настройкой приложения.

В текущей реализации стандартный `DesktopGameHost` самостоятельно создаёт OpenGL-окно, использует ввод на базе Silk.NET и аудиоустройство OpenAL. Публичные интерфейсы позволяют отделять игровой код от этих реализаций, но сами по себе не предоставляют готового механизма выбора альтернативных backend через настройки `DesktopGameHost`.

Поэтому важно различать два состояния:

- **Независимость игрового кода:** код использует общие API и не обращается напрямую к конкретному backend.
- **Сменяемость backend приложения:** инфраструктура умеет создать и подключить альтернативную реализацию, совместимую с необходимыми интерфейсами.

Первое уже поддерживается существующими абстракциями. Второе требует отдельной работы над инфраструктурой и остаётся самостоятельной задачей.

### Основные правила

- Предпочитай интерфейсы движка конкретным реализациям.
- Не создавай backend вручную внутри игровой логики, если сервис уже предоставлен host или Runtime.
- Изолируй зависимости от специфических возможностей конкретной реализации.
- Не считай наличие интерфейса гарантией полной совместимости всех возможных backend.

## Границы между Game, Runtime и инфраструктурой

При разработке игры важно разделять игровую логику, механизмы выполнения и платформенную инфраструктуру. Это позволяет развивать игру независимо от деталей реализации движка.

### Ответственность каждого уровня

| Уровень | Ответственность |
|---|---|
| **Game** | Игровые компоненты, правила, игровые системы, состояния игры, обработка пользовательских действий и организация игрового процесса. |
| **Engine.Runtime** | ECS-мир, планировщик систем, симуляция, фиксированные шаги, события, команды, физика и предоставляемые движком инструменты. |
| **Engine.Hosting.Desktop** | Создание окна, подключение сервисов и backend, конфигурация запуска приложения и управление жизненным циклом host. |
| **Конкретные backend** | Реализация графики, ввода и аудио с использованием соответствующих платформенных библиотек. |

Это логические границы ответственности, а не требование создавать отдельный проект для каждого игрового класса.

### Игровой проект

Игровой код определяет смысл используемых механизмов. Например, движок предоставляет ECS и физику, а игра решает, какие сущности являются персонажами, какие компоненты они имеют и как должны реагировать на столкновения.

Игровой проект может содержать собственные:

- ECS-компоненты и системы;
- состояния игры и игровые экраны;
- обработчики ввода и игровые команды;
- правила взаимодействия объектов;
- загрузку и интерпретацию игровых данных.

Не следует переносить игровую механику в `Engine.Runtime` только ради повторного использования внутри одной игры. В движок стоит выносить механизмы, имеющие самостоятельную универсальную ценность.

### Runtime и регистрация игровых систем

`EngineRuntime` предоставляет игровому коду доступ к механизмам выполнения и сервисам движка.

Если игра использует базовый класс `EngineGame`, для настройки Runtime предусмотрен метод `ConfigureRuntime()`. Он вызывается до `Runtime.Initialize()`, поэтому подходит для регистрации собственных систем и задания порядка их выполнения.

```csharp
using Engine.Runtime;
using Engine.Core.Systems;

public sealed class MyGame : EngineGame
{
    public MyGame(EngineRuntime runtime)
        : base(runtime)
    {
    }

    protected override void ConfigureRuntime()
    {
        Runtime.Scheduler.Add(
            new MyGameSystem(Runtime.EcsWorld),
            SystemPhase.Update);
    }

    protected override void OnInitialize()
    {
        // Подготовка игрового состояния.
    }

    protected override void OnUpdate(
        Engine.Core.Time.TimeSnapshot time)
    {
        // Логика уровня приложения.
    }
}
```

`MyGameSystem` здесь обозначает собственную систему игры, реализующую соответствующий интерфейс обновления.

`EngineGame` также предоставляет `OnFixedUpdate()`, `OnRender()` и `OnShutdown()` для соответствующих этапов жизненного цикла. Игровые системы следует регистрировать в подходящей фазе — `Update` или `FixedUpdate`.

### Инфраструктура запуска

Для стандартного desktop-приложения используется `DesktopGameHost`. Он создаёт окно, графическое устройство, ввод, аудиоустройство, менеджер содержимого и `EngineRuntime`, после чего запускает приложение.

Если игре нужны предоставляемые host сервисы, доступ к ним можно получить через `DesktopGameHostContext`: например, `Graphics`, `Input`, `Audio`, `Content`, `Camera` и `AssetSource`.

Инфраструктура запуска отвечает за создание и владение платформенными ресурсами. Игровой код использует предоставленные интерфейсы и не должен самостоятельно создавать второе графическое устройство или аудиоустройство для работы с уже запущенным host.

### Где размещать адаптеры

Если игре требуется связать универсальную механику движка с конкретной платформенной возможностью, зависимость следует локализовать.

Например, игровая система может сообщать о необходимости воспроизвести звук через игровой сервис, который использует `IAudioManager`. Саму реализацию OpenAL не нужно подключать к каждой системе, которой достаточно общего API аудио.

Аналогичный подход применяется к графике и вводу: игровые правила остаются в `Game`, а платформенные детали — в реализации соответствующей инфраструктуры.

### Основные правила

- Игровая семантика принадлежит игровому проекту; универсальные механизмы — движку.
- `Engine.Runtime` не должен зависеть от правил конкретной игры.
- Host отвечает за создание и подключение платформенных сервисов.
- Конкретные backend не следует использовать непосредственно в игровом коде без обоснованной необходимости.
- Наличие общей абстракции не означает, что host уже умеет переключаться между любыми реализациями: сменяемость backend требует соответствующей инфраструктуры.

## Проверка независимости игрового кода от backend

Использование общих интерфейсов — важный признак независимости, но для проверки архитектуры этого недостаточно. Нужно учитывать исходный код, зависимости проекта и способ создания сервисов.

### 1. Проверка исходного кода

При просмотре игрового проекта обрати внимание на следующие признаки прямой зависимости от конкретной реализации:

```csharp
using Engine.Graphics.OpenGL;
using Engine.Audio.OpenAL;
using Silk.NET.OpenGL;
```

Подобные пространства имён сами по себе не означают архитектурную ошибку: они допустимы в коде, который действительно реализует платформенную интеграцию или использует специфические возможности backend.

Проблема возникает, если обычная игровая логика вынуждена использовать конкретную реализацию для решения задачи, доступной через общий API.

Проверь, нет ли в игровых системах прямого создания графических устройств, аудиоустройств или backend ввода. Обычно такие действия должны выполняться инфраструктурой приложения.

### 2. Проверка зависимостей проекта

Просмотри файл игрового проекта `.csproj`. Прямые ссылки на проекты конкретных backend — сигнал для проверки:

```xml
<ProjectReference Include="..\Engine.Graphics.OpenGL\Engine.Graphics.OpenGL.csproj" />
<ProjectReference Include="..\Engine.Audio.OpenAL\Engine.Audio.OpenAL.csproj" />
```

Если игровые классы не обращаются к типам из этих проектов напрямую, возможно, ссылки можно убрать или оставить только на уровне запуска приложения. Решение принимается после проверки реальных зависимостей и необходимости этих ссылок.

При этом ссылка на `Engine.Hosting.Desktop` в точке входа приложения вполне оправдана: именно там выбирается стандартная инфраструктура запуска.

### 3. Проверка границы запуска приложения

В архитектуре должны быть ясно разделены два действия:

- **Сборка приложения:** host создаёт окно, выбирает реализации сервисов и связывает их с Runtime.
- **Выполнение игры:** игровые системы используют предоставленные механизмы и интерфейсы, не создавая платформенную инфраструктуру самостоятельно.

Такой подход позволяет в будущем менять состав сервисов на этапе запуска, не переписывая игровые правила.

### 4. Проверка тестируемости

Полезный архитектурный тест — возможность проверить игровую логику без запуска реального графического или аудиобэкенда.

Если игровая система использует интерфейсы, можно в тесте передать контролируемую реализацию зависимости. Например, игровой сервис звуков может получать `IAudioManager` извне, вместо того чтобы самостоятельно создавать `OpenALAudioDevice`.

Это не требует немедленно реализовывать полноценные альтернативные backend. Достаточно, чтобы границы зависимостей позволяли тестировать игровую логику отдельно от инфраструктуры.

### 5. Практические критерии

При проверке игрового проекта последовательно задай следующие вопросы:

- Может ли игровая система работать через публичный интерфейс движка, не зная конкретную реализацию?
- Создаются ли платформенные устройства в инфраструктуре запуска, а не внутри игровой логики?
- Нужны ли проекту прямые ссылки на конкретные backend, или их можно оставить только host?
- Можно ли тестировать игровые правила без создания настоящего графического окна и аудиоустройства?
- Если появится альтернативный backend, потребуется ли менять игровые системы или достаточно будет изменить конфигурацию и инфраструктуру?

Чем меньше изменений требуется в игровом коде при замене платформенной реализации, тем лучше соблюдается граница между механизмами движка и смыслом, который им придаёт игра.

### Текущее состояние VibeEngine2

В текущем `Game.Sandbox/Game.Sandbox.csproj` присутствуют прямые ссылки на `Engine.Graphics.OpenGL` и `Engine.Audio.OpenAL`. Это означает, что проект пока не демонстрирует полностью изолированную от backend структуру зависимостей.

Однако сами ссылки ещё не доказывают, что вся игровая логика непосредственно зависит от этих реализаций. Чтобы сделать окончательный вывод, необходимо отдельно проверить использование конкретных типов в исходном коде и выяснить, какие ссылки действительно необходимы.

Независимость игрового кода и возможность переключения backend следует оценивать отдельно: первое достигается правильными границами зависимостей, второе дополнительно требует инфраструктуры выбора и подключения реализаций.
