# Матрица поддержки и известных ограничений VibeEngine2

Документ фиксирует подтверждённые рабочие сценарии, ограничения, прямо указанные в API-документации, и области, для которых пока нельзя сделать общий вывод о готовности.

**Правило интерпретации:** наличие кода или проекта не означает, что реализованы все ожидаемые сценарии. Статус «проверено» относится только к указанному сценарию и не распространяется автоматически на всю подсистему. Неизвестное или не проверенное не следует называть ни поддерживаемым, ни неподдерживаемым без отдельной проверки.

## Значения статусов

| Статус | Что означает |
|---|---|
| **Подтверждённый сценарий** | Сценарий явно отмечен в ROADMAP как проверенный либо подтверждается названным автоматическим тестом. Это не гарантирует полноту проверки всей подсистемы. |
| **Поддерживается с ограничениями** | Документация прямо описывает условия, допустимые форматы или поведение, на которые должен рассчитывать разработчик. |
| **Требует отдельной проверки** | Реализация или API существуют, но доступных свидетельств недостаточно, чтобы объявить всю возможность готовой для произвольного производственного сценария. |
| **Не поддерживается** | Применяется только к конкретному сценарию, если он явно исключён текущей реализацией. Не выводить такой статус только из отсутствия тестов или документации. |

## Подтверждённые рабочие сценарии

| Область | Что подтверждено | Свидетельство и границы вывода |
|---|---|---|
| Сборка и повторный запуск игрового проекта | Редактор может обнаружить ошибку сборки, а после исправления исходников повторно собрать и запустить игру. | `GameProjectRunnerBuildTests.Restart_BuildsUpdatedSource_AndRecoversAfterBuildFailure`. Подтверждён этот путь восстановления, не любая возможная ошибка сборки. |
| Ошибка при выполнении игры | Исключение runtime и stack trace отображаются в диагностическом выводе; после исправления игры возможен новый запуск. | `GameProjectRunnerBuildTests.Start_RuntimeException_ReportsExceptionAndStackTrace`. |
| Восстановление сессии после runtime-сбоя | После ошибки запуска сессии можно исправить исходники и создать новую рабочую сессию. | `SessionManager_RuntimeFailure_ReportsErrorAndAllowsNewSession`. |
| Вывод сообщения с исключением | Форматирование включает сообщение и сведения об исключении; обычные сообщения остаются читаемыми. | `EditorConsoleMessageFormattingTests`; ручная проверка вывода stack trace также отмечена в работе над диагностикой. |
| Камера и эффекты частиц | Проверен игровой workflow камеры и частиц: ресурс эффекта, назначение сущности, обновление и отрисовка в runtime, сохранение и восстановление настроек. | ROADMAP, раздел 6.2 «Интеграция игрового проекта и Editor». Не означает, что проверены все виды эффектов или любой графический сценарий. |
| Hot Reload ресурсов/изменений C# | В ROADMAP зафиксированы применение поддерживаемых изменений без перезапуска, восстановление после ошибки компиляции и перезапуск при изменениях, которые нельзя применить на месте. | Это три разных поведения. Hot Reload не следует считать гарантией применения любого изменения C# без перезапуска. |
| Интеграционный путь игрового проекта | Отмечена проверка создания проекта, сборки, запуска, остановки и повторного запуска, в том числе вне репозитория исходников движка. | ROADMAP, раздел Readiness: Integration Readiness. Это подтверждение описанного сквозного пути, а не всех возможных конфигураций развёртывания. |
| Производительность проверенных подсистем | Зафиксирован Release baseline для ECS, JobScheduler, Content Pipeline и Engine.Runtime; проверены время, аллокации, GC и память при создании/освобождении ECS World. | ROADMAP, раздел production readiness. Вывод относится к измеренным сценариям и конфигурации baseline, а не ко всем нагрузкам и платформам. |

### Как трактовать покрытие тестами

В ROADMAP записан baseline покрытия **47,96% строк и 39,17% ветвей** на момент измерения. Эти проценты не являются показателем готовности каждой функции: они не говорят, какие именно пользовательские сценарии проверены, а какие нет. При повторной оценке следует обновлять показатели с датой и конфигурацией запуска.

## Документированные ограничения

| Область | Поддерживаемое поведение / ограничение | Практическое следствие |
|---|---|---|
| Платформа разработки | В README Windows названа основной средой разработки и запуска текущих Sandbox-приложений и графической подсистемы; целевой TFM основного набора проектов — .NET 8. | Не заявлять одинаковую готовность всех платформ без отдельной сборки и практической проверки на них. |
| Стандартный desktop host и графический backend | `DesktopGameHost` сам создаёт OpenGL-окно, использует ввод на базе Silk.NET и аудиоустройство OpenAL. Общие интерфейсы отделяют игровой код от конкретных реализаций, но настройка host не предоставляет готового выбора альтернативных backend. | Независимость игрового кода от backend не равна возможности переключить backend приложения без доработки host. |
| Указатель и UI | `DesktopGameHostContext.PointerInput` имеет тип `IPointerInput?` и может быть `null`, если host не поддерживает указатель. Без него UI не может создать свой маршрутизатор ввода. | Проверять наличие указателя перед использованием; не предполагать, что любой host предоставляет мышь или указатель. |
| Привязки ввода | Если одному `InputAction` назначено несколько `InputBinding`, текущий `InputActionMap` выбирает значение с максимальным абсолютным значением, а не суммирует все значения. | Не использовать несколько привязок как способ сложения осевых значений. |
| Форматы аудио | Текущий загрузчик поддерживает WAV с несжатым PCM, моно или стерео, 8 или 16 бит. Другие форматы WAV и форматы кроме WAV не поддерживаются этим загрузчиком и могут приводить к исключению. | Для документированного пути загрузки подготавливать WAV PCM указанного формата либо расширять и отдельно проверять загрузчик. |
| Время жизни аудио-буфера | В стандартном desktop host загруженные через `context.Audio.Load()` буферы принадлежат менеджеру аудио и освобождаются вместе с ним; отдельного API для выгрузки одного буфера нет. Документация предостерегает от самостоятельного `Dispose()` буфера, остающегося в кэше. | Не освобождать вручную кэшированный буфер, если он ещё может быть возвращён менеджером повторно. |
| Иерархия Transform | `TransformHierarchySystem` не регистрируется Runtime автоматически. Для вычисления мировых трансформаций с родителями её нужно зарегистрировать до `runtime.Initialize()`. | Если система не зарегистрирована, нельзя рассчитывать на автоматический пересчёт иерархии. Простое изменение Transform также не гарантирует, что соответствующая система отрисовки использует новое значение. |
| Game.Sandbox | Sandbox — интеграционная площадка и имеет прямые ссылки на многие конкретные подсистемы и backend. | Не считать его зависимости обязательным набором ссылок для пользовательской игры и не использовать один только Sandbox как шаблон архитектуры игрового проекта. |

## Области, где требуется уточнение перед заявлением о полной поддержке

Это **не список утверждённых дефектов**. Это перечень тем, по которым в рамках текущего документа нет достаточной информации, чтобы заявить полную поддержку всех сценариев.

| Область | Что необходимо уточнить |
|---|---|
| Альтернативные графические, аудио- и input-backend | Какие реализации, помимо текущей конфигурации desktop host, реально можно подключить и какие проверки интеграции для них существуют. Сейчас документированное ограничение относится именно к стандартному host. |
| Контент и сериализация | Состав поддерживаемых форматов по каждому типу ассета, правила совместимости версий и поведение при повреждённых/устаревших данных должны быть сведены в проверяемую таблицу. Не считать все форматы поддерживаемыми из-за существования общего Content Pipeline. |
| Скриптинг | Необходимо отдельно перечислить проверенные пользовательские сценарии — регистрация в игровой сборке, назначение сущности, вызовы жизненного цикла, обработка ошибок и сохранение назначений — и не расширять вывод за пределы реально проверенных тестов. |
| Networking и Replication | Наличие сетевых API и проекта репликации не доказывает готовность любой сетевой архитектуры, транспорта, восстановления соединения, авторитетности и масштабирования. Статус следует фиксировать по конкретным требованиям и интеграционным сценариям игры. |
| Кроссплатформенность и распространение | Нужны результаты сборки и запуска для каждой платформы и конфигурации поставки, которую планируется объявить поддерживаемой. Основная среда Windows сама по себе не является заявлением об исключительной поддержке Windows или о готовности других платформ. |
| Границы готовности редактора | Готовность редактора следует подтверждать отдельно для конкретных типов документов и сценариев редактирования/сохранения. Готовность одного редактора ресурса не означает, что каждый тип ресурса имеет одинаково завершённый workflow. |

## Правило фиксации нового ограничения

Когда обнаруживается ограничение, добавляйте запись по шаблону:

- **Область и сценарий:** где именно проявляется ограничение.
- **Фактическое поведение:** что происходит сейчас, без предположений о причинах.
- **Ожидаемое поведение:** только если оно определено требованиями.
- **Свидетельство:** тест, путь к исходнику, минимальный воспроизводимый пример или результат ручной проверки.
- **Статус:** подтверждённое ограничение, проверенное поведение или открытый вопрос.
- **Обходной путь:** если он существует и проверен.

Не переносите статус с одного сценария на всю подсистему. Не объявляйте функцию «готовой» только по наличию классов, наличию тестов или успешной сборке решения.
