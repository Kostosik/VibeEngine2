# Roadmap: создание и запуск игровых проектов VibeEngine2

**Обновлено:** 2026-10-21

Этот документ задаёт рабочую последовательность разработки. Выполненные пункты отражают проверенное поведение, а не только написанный код. В каждый момент есть одна текущая задача; следующие этапы не начинаются, пока её критерии не выполнены.

## Цель

Пользователь должен уметь создать игровой проект в редакторе, редактировать его код во внешней IDE, работать с ресурсами и стартовой сценой, запускать и останавливать игру из редактора, а затем собирать автономное приложение.

**Критерий готовности:** простой проект, созданный редактором, можно открыть и изменить, запустить и остановить из редактора, повторить запуск без остаточных процессов или ресурсов, а также собрать и запустить отдельно от редактора и исходников VibeEngine2.

## Принципы и границы

- **Движок предоставляет механизмы, игра определяет смысл.** Не добавлять в Engine понятия конкретной игры.
- **`Game.Sandbox` — интеграционный полигон**, а не шаблон пользовательской игры и не обязательная основа запуска. Не нужно добиваться совпадения её структуры со сгенерированным проектом.
- Повторно использовать существующие `EngineGame`, `DesktopGameHost`, `GameLoop`, `EngineRuntime`, `Engine.Content` и сборочные возможности .NET. Не вводить новые абстракции без необходимости, обнаруженной в текущей задаче.
- Различать игровой проект, открытый документ редактора, исходную сцену, runtime-состояние и сохранение игрового прогресса.
- Ресурсы игры разрешаются относительно игрового проекта/его выходного каталога, а не относительно редактора, клона репозитория или текущего рабочего каталога процесса.
- Пользовательский C#-код остаётся обычным .NET-проектом и редактируется во внешней IDE. Встроенный редактор кода не нужен.
- В текущей модели новый проект получает подготовленные библиотеки VibeEngine2 в `Engine/` и использует локальные ссылки `Reference`/`HintPath`. Не переходить на NuGet или собственный менеджер пакетов без практической причины.
- Начальный запуск из редактора может работать в отдельном процессе и окне. Встроенный Game View — отдельный будущий этап.
- Не включать в первый рабочий сценарий C# Hot Reload, сложную систему сцен, универсальную систему плагинов или независимые игровые циклы.

## Порядок работ

Работать по этапам сверху вниз. Непосредственно выполнять только текущую задачу; новые архитектурные направления не внедрять попутно.

### 1. Проектные ресурсы и рабочий процесс с проектом — ЗАВЕРШЁН

- [x] Генератор `.csproj` копирует содержимое `Assets/**/*` в build и publish output с сохранением вложенной структуры каталогов.
- [x] На свежем проекте проверено наличие тестового файла в `bin/Debug/net8.0/Assets/Probe/` и в `bin/Release/net8.0/publish/Assets/Probe/`.
- [x] Проверена загрузка PNG из выходного `Assets/` через `Runtime.Services.Content.Load<TextureData>(new AssetPath(...))`.
- [x] Добавлена команда `Open IDE`: открывает `.sln` активного проекта через системную ассоциацию, а если решения нет — `.csproj`. Проверено вручную.
- [x] Проверено создание, открытие в IDE, сборка и запуск проекта в каталоге вне клона VibeEngine2.

**Заметка о регистрах путей:** `AssetPath` нормализует разделители, но не регистр символов. `FileContentCatalog` индексирует пути по точному значению, поэтому запрос должен совпадать с регистром имени, которое обнаружено в выходном каталоге. На Windows пути файловой системы регистронезависимы, но ключи каталога контента — нет; при изменении только регистра следует очистить старые build-артефакты и пересобрать проект.

**Критерий завершения этапа выполнен:** ресурсы проекта копируются и доступны запущенной игре; открытие кода, сборка и запуск проверены без репозитория исходников движка.

### 2. Стартовая сцена и независимое runtime-состояние — ЗАВЕРШЁН

- [x] В `.vibeproject` добавлено необязательное поле `startupScene` с относительным путём; манифесты старых проектов без этого поля остаются допустимыми.
- [x] При создании проекта генерируется пустая сцена `Scenes/Main.world` существующим `WorldSaveLoadService`.
- [x] `Scenes/**/*` копируются в build/publish output.
- [x] При запуске сгенерированная игра загружает стартовую сцену в runtime-мир, используя существующую сериализацию, без отдельного формата сцены.
- [x] Runtime-мир отделён от исходного файла сцены: загрузка сцены не означает автоматического сохранения изменений runtime-миров обратно в файл.
- [x] Зафиксировано различие по назначению: файл сцены задаёт начальное состояние, runtime-мир содержит текущее состояние запущенной игры, а сохранение игрового прогресса будет отдельным сценарием и проектируется при появлении соответствующей потребности.

**Критерий завершения выполнен:** новый проект содержит стартовую сцену; игра загружает её в отдельный runtime-мир, а изменения игрового состояния не перезаписывают исходную сцену автоматически.

### 3. Запуск игры из редактора: Play / Stop / Restart — ЗАВЕРШЁН

- [x] Play запускает активный проект в отдельном процессе и окне; для запуска используется точный путь `GameProject.ProjectFilePath`.
- [x] Stop завершает игровой процесс и его дочерние процессы; при закрытии редактора runner освобождает принадлежащие ему ресурсы процесса.
- [x] Restart выполняет последовательный останов и повторный запуск.
- [x] Вывод процесса читается асинхронно через очередь и передаётся в существующую консоль редактора.
- [x] Проверены повторные Play / Stop / Restart и восстановление доступности кнопок после завершения процесса.
- [x] Подтверждено, что авария игры не закрывает и не повреждает редактор.

**Критерий завершения выполнен:** активный проект можно запускать, останавливать и повторно запускать; завершение игры не оставляет редактор в ложном состоянии «игра запущена».
### 4. Диагностика игровой сессии — ЗАВЕРШЁН

- [x] Вывод сборки, stdout и stderr игрового процесса передаются в существующую консоль редактора.
- [x] Кодировка перенаправленного вывода настроена на UTF-8; сообщения компилятора отображаются читаемо.
- [x] Проверена намеренная ошибка C#-сборки: диагностические сообщения и ненулевой код завершения видны в консоли.
- [x] Проверена runtime-авария: причина попадает в вывод процесса, редактор продолжает работать и позволяет снова запустить игру.
- [x] После неудачной сборки и аварийного завершения кнопки управления возвращаются в корректное состояние.

**Критерий завершения выполнен:** ошибки сборки и выполнения видны в существующей диагностике, а редактор восстанавливается после неудачного запуска или аварии.
### 5. Runtime-поставка и автономная сборка — ЗАВЕРШЁН

- [x] Runtime-поставка `EngineRuntime/win-x64` включается в релиз редактора существующим ручным GitHub Actions workflow через `dotnet publish`.
- [x] Поставка размещается рядом с редактором, и генератор находит её по пути `EngineRuntime/win-x64`, не полагаясь на `artifacts/` исходного репозитория.
- [x] Проверено наличие обязательных сборок runtime в собранной поставке.
- [x] Сгенерированный проект получает локальные ссылки на библиотеки движка, а необходимые native-зависимости, ресурсы и сцены копируются в build/publish output.
- [x] Проверено создание и запуск проекта вне репозитория VibeEngine2; также проверен сценарий из распакованного релиза редактора без исходников движка.

**Примечание:** дистрибутив остаётся framework-dependent и требует установленный .NET 8 Desktop Runtime x64. «Автономный» здесь означает независимость игры от редактора и исходников VibeEngine2, а не отсутствие требования к .NET Runtime.
### 6. Последующие архитектурные улучшения — не блокируют основные этапы

- [ ] Оценить границу host/platform surface для будущего выбора графического, аудио- и input-backend; текущие OpenGL, OpenAL и Silk.NET остаются стандартным рабочим вариантом.
- [ ] Спроектировать подключение пользовательских систем и фабрик `IEntityScript` из игровой сборки, когда для этого появится конкретный workflow запуска.
- [ ] Согласовать пересборку C#-проекта и перезапуск игры. Это не то же самое, что hot-reload ресурсов.
- [ ] Исследовать C# Hot Reload отдельно; не обещать горячее применение произвольных изменений кода в первой версии.
- [ ] Рассмотреть встроенный Game View, Pause и пошаговое выполнение после устойчивого сценария запуска в отдельном процессе.
- [ ] Возвращаться к плагинам и динамической загрузке модулей только при появлении конкретной необходимости.

## Сквозная проверка готовности

Когда основные этапы завершены, пройти весь сценарий подряд:

1. Создать пустой проект из редактора.
2. Закрыть и повторно открыть проект; убедиться, что состояние редактора восстановилось.
3. Добавить/изменить ресурс и стартовую сцену, открыть код во внешней IDE.
4. Собрать и запустить игру из редактора.
5. Изменить runtime-состояние, остановить игру и убедиться, что исходная сцена редактора не изменилась автоматически.
6. Несколько раз запустить и остановить игру; проверить очистку процессов и ресурсов.
7. Смоделировать ошибку сборки и ошибку запуска; убедиться, что редактор восстанавливается.
8. Собрать и запустить игру автономно, без редактора и клона репозитория VibeEngine2.

## Правила обновления ROADMAP

- Отмечать пункт выполненным только после проверки указанного результата.
- При активной разработке указывать одну текущую задачу с конкретным результатом проверки.
- Если выяснилось, что задача поставлена неверно, сначала исправить план, затем писать код.
- Не записывать исследовательскую ветку или разовое изменение `Game.Sandbox` как обязательное направление, если этого нет в согласованном плане.
- При работе над планом изменять только `docs/ROADMAP.md`; исходный код пользователь редактирует локально отдельно.
