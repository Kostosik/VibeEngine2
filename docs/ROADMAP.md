# Roadmap развития VibeEngine2

**Дата формирования:** 2026-11-27  
**Базовая ревизия:** `703dd55c9e2430a5d52251bdc11795782759d528` (`master`)  
**Основание:** завершённые архитектурные аудиты 00–08 и утверждённое направление развития в [ENGINE_DEVELOPMENT_PLAN.md](ENGINE_DEVELOPMENT_PLAN.md).  
**Статус:** сформирован; первый этап реализации ещё не начат.

---

## 1. Цель

Развивать VibeEngine2 в универсальный игровой движок, на котором можно создавать игры разных жанров и масштабов, не привязывая Engine к правилам конкретной игры.

Результат должен определяться не количеством подсистем и классов, а возможностью пройти полный рабочий цикл:

1. Создать игровой проект.
2. Импортировать и организовать ресурсы.
3. Создавать и редактировать сцены и игровые объекты.
4. Настраивать компоненты и ресурсы в Editor.
5. Писать игровую логику на C# и подключать собственные системы.
6. Запускать, отлаживать и профилировать игру.
7. Собирать и распространять готовое приложение на заявленных платформах.

Главный принцип остаётся прежним: **движок предоставляет механизмы, игра определяет смысл**. ECS, Runtime, World, Content и текущие границы проектов сохраняются как основа. Полная замена архитектуры или копирование внутреннего устройства другого движка не является целью.

## 2. Как пользоваться Roadmap

Это приоритетный план реализации, а не обещание реализовать каждую существующую подсистему одновременно.

- Этапы идут в порядке зависимостей. Следующий крупный этап начинается после достижения критериев предыдущего либо после отдельного согласования изменения порядка.
- Внутри этапа работа делится на небольшие задачи. За один проход выполняется одна согласованная задача.
- Наличие реализации в репозитории не означает, что её нужно переписывать. Сначала проверяются потребители, интеграция и фактический сценарий.
- Если возможность нужна только отдельному жанру или игре, её можно вынести в специализированное направление и не задерживать базовый workflow.
- Поддержка платформы, формата или backend объявляется только после сборки и проверки реального сценария.
- Тесты, сборка и ручная проверка должны подтверждать именно критерии текущей задачи. Наличие тестового файла само по себе не считается результатом запуска.

### Приоритеты

| Приоритет | Значение |
|---|---|
| P0 — блокирующий | Не позволяет надёжно создавать, открывать, собирать, запускать или сохранять игровой проект |
| P1 — основной | Необходим для законченного общего Editor workflow, 2D или 3D вертикального сценария |
| P2 — расширение | Повышает качество, производительность, удобство распространения или расширяет специализированные возможности |
| По потребности | Развивается, когда существует конкретный игровой сценарий, который требует этой возможности |

## 3. Текущее исходное состояние

Аудит 00–08 завершён и зафиксирован в `docs/audits/`. Ключевые выводы, влияющие на порядок работ:

### Уже существующая основа

- Разделение Core, ECS, World, Runtime, Hosting, Editor, Backend и Game сформировано. Существующую архитектуру можно развивать без общего переписывания.
- Editor уже содержит документы, Hierarchy, Inspector, 2D Viewport, Asset Browser, операции сохранения и отдельные редакторские представления ресурсов.
- ContentManager поддерживает кэширование, зависимости, владение ссылками и синхронную/асинхронную загрузку.
- Есть сохранение World, Prefab-механизм, 2D Transform hierarchy и отдельные API runtime SceneManager.
- Runtime имеет игровой цикл, fixed update, SystemScheduler, команды, события, регистрацию пользовательских компонентов и систем.
- 2D-основа включает спрайты, тайлмапы, Camera2D, физику, частицы, аудио, UI, навигацию и освещение.
- 3D-основа содержит mesh rendering, Camera3D, Transform 3D, базовые материалы и ограниченный collision detection.
- Есть диагностика, Console, CPU profiling, validation, debug visualization и standalone benchmarks.
- Создание игрового проекта и запуск через отдельный .NET процесс уже реализованы; есть тесты ряда сценариев восстановления после ошибок.

### Основные незавершённые сквозные сценарии

1. Startup Scene сохраняется в manifest, но стандартный Play и сгенерированный Program не загружают эту сцену автоматически.
2. Workspace и Editor Session persistence API существуют, но не подключены к стандартному запуску Editor; session capture охватывает только World documents.
3. Undo/Redo работает не для всех видов документов.
4. Asset Browser остаётся в основном файловым представлением; нет полноценного общего import database с устойчивыми идентификаторами, import settings и артефактами.
5. Content Hot Reload не подключён к стандартному Host workflow и не обновляет автоматически все зависимые ресурсы.
6. Некоторые loaders не регистрируются стандартным Desktop Host; Animation, UI и другие ресурсы требуют дальнейшего завершения runtime-интеграции.
7. Tilemap не связана автоматически с chunk storage/streaming Engine.World; ChunkStreamingService не включён в стандартный Runtime.
8. 3D не образует полного Editor → Content → Serialization → Runtime workflow; в частности, нет модельного importer, полноценного Physics 3D и 3D authoring в Editor.
9. Developer Tools не имеют полного diagnostic/visualization workflow; отсутствуют Frame Debugger и GPU timing.
10. Основная конфигурация поставки — Windows x64 + .NET 8. Runtime Builder использует win-x64, а Editor использует Windows Forms.
11. Последний успешный distribution workflow, найденный аудитом, был собран не на текущем commit. Текущий master требует актуальной проверки CI и установленного дистрибутива.

Подробные основания и пути к коду находятся в отчётах аудита и [матрице поддержки](SUPPORT_MATRIX.md).

## 4. Последовательность реализации

## Этап 0. Надёжный базовый цикл проекта

**Приоритет:** P0  
**Статус:** запланирован  
**Цель:** подтвердить и завершить путь от пустого проекта до запускаемой игры на текущей целевой конфигурации Windows x64.

### Задачи

0.1. **Проверить текущий master.** Выполнить Release build и полный набор тестов на актуальной ревизии. Запустить distribution workflow на той же ревизии. Исправлять только реально воспроизводимые проблемы, не переносить в код исторические CI-таймауты без подтверждения причины.

0.2. **Проверить распакованную поставку.** Добавить smoke-сценарий, который использует именно ZIP из distribution workflow: запускает Editor, создаёт проект, собирает/запускает его, проверяет доступность Assets, выполняет Stop/Restart и проверяет запуск опубликованного приложения вне каталога исходников.

0.3. **Согласовать требования к среде.** В README дистрибутива явно указать, что Desktop Runtime нужен для запуска Editor, а .NET SDK — для Play/Hot Reload и сборки пользовательского проекта. Проверить, что сообщения об отсутствии SDK или Runtime понятны.

0.4. **Завершить Startup Scene workflow.** Новый проект должен получать корректную стартовую сцену; настройка должна сохраняться в manifest; стандартный запуск игры должен загружать именно её через существующие механизмы World/Serialization. Не вводить второй параллельный механизм загрузки сцен.

0.5. **Проверить выходные файлы проекта.** Подтвердить копирование Assets, manifest, managed и native зависимостей в build/publish output и загрузку ресурсов по проектным относительным путям.

### Критерии завершения

- На актуальном commit проходят Release build и тесты; distribution pipeline проходит на том же commit.
- ZIP распаковывается и запускает Editor без доступа к исходному репозиторию.
- Из поставки создаётся новый проект; он успешно собирается, запускается и останавливается.
- Startup Scene создаётся/назначается, сохраняется, загружается при Play и восстанавливается после повторного открытия проекта.
- Игровые Assets доступны и в обычном запуске, и в проверенном publish output.
- Требования к SDK/Runtime соответствуют реальному сценарию.

**Результат этапа:** надёжная Windows x64 база, на которой можно безопасно развивать пользовательский workflow.

## Этап 1. Основной Editor и Content workflow

**Приоритет:** P1  
**Зависимость:** этап 0  
**Статус:** запланирован  
**Цель:** дать разработчику возможность создавать и изменять основные данные игры через Editor, сохранять проект и возвращаться к работе без ручного редактирования внутренних файлов.

### Задачи

1.1. **Документы и история изменений.** Определить единый ожидаемый контракт Undo/Redo и распространить его на основные типы редактируемого содержимого. Начать с World/Scene и Prefab, затем включать Tilemap, UI и другие документы по фактической потребности. Не добавлять историю для файлов, которые не имеют осмысленных атомарных операций.

1.2. **Workspace и Editor Session.** Подключить существующие механизмы сохранения workspace и session в стандартный Editor. Согласовать восстановление активного проекта, открытых документов, выбранного документа и layout панелей. Расширять session persistence за пределы World документов по мере появления стабильного контракта соответствующих документов.

1.3. **Объекты и компоненты.** Уточнить основной набор операций Hierarchy/Inspector: создание, удаление, изменение Transform, добавление и настройка зарегистрированных компонентов. Поддержать необходимые сценарии нескольких выделенных объектов только там, где они реально используются. Сохранить явную регистрацию типов и редакторов, пока не доказана необходимость автоматического discovery.

1.4. **Asset Browser и импорт.** Развить файловую модель до управляемого import workflow: тип ресурса, importer, настройки импорта, диагностика, повторный импорт и preview результата. Устойчивые asset IDs, hashes и dependency metadata добавлять в объёме, необходимом для переименований, ссылок и корректного reimport, а не ради создания отдельной базы данных как самоцели.

1.5. **Зависимости и Hot Reload.** Уточнить ownership и dependency lifecycle для ресурсов, подключить безопасное обновление импортированных ресурсов и связанных зависимостей. Не считать простой polling изменения файла полноценным Hot Reload, пока ресурс и его зависимые GPU/runtime объекты не обновляются согласованно.

1.6. **Регистрация loaders и диагностика Content.** Составить понятный перечень стандартных loaders и тех, которые регистрирует игра. Подключить Content validation к доступному catalog/loader registry и выводить конкретные ошибки, а не только их количество.

### Критерии завершения

- Основную сцену можно открыть, редактировать, сохранить, закрыть и восстановить после перезапуска Editor.
- Основные поддерживаемые документы имеют предсказуемую историю Undo/Redo либо явно документированное ограничение.
- Объекты и компоненты можно настраивать через Hierarchy/Inspector без ручного редактирования сериализованного файла.
- Ресурсы можно импортировать, просматривать, повторно импортировать и диагностировать через единый понятный workflow.
- Ссылки между сценами и ресурсами переживают сохранение, переименование и повторную загрузку в пределах поддерживаемых форматов.
- Ошибки загрузки/импорта содержат asset path, тип ресурса и конкретную причину.

**Результат этапа:** пригодная основа редакторской работы над проектом и ресурсами.

## Этап 2. Законченный 2D workflow

**Приоритет:** P1  
**Зависимость:** этапы 0 и 1  
**Статус:** запланирован  
**Цель:** довести существующие 2D-механизмы до согласованного цикла authoring → serialization → runtime → debugging → publish.

### Задачи

2.1. **Сцены и 2D-объекты.** Завершить редактирование сущностей, 2D Transform hierarchy, спрайтов, камер и связанного содержимого сцены. Подтвердить round-trip сохранения и повторной загрузки для поддерживаемых компонентов.

2.2. **TileSet и Tilemap.** Согласовать Tilemap authoring/runtime с World и chunk storage. Определить границы между обычной Tilemap, большими картами и chunk streaming; подключать ChunkStreamingService в стандартный runtime workflow только после определения жизненного цикла и сериализации данных.

2.3. **Анимация.** Подключить AnimationPlayer/SpriteAnimation к предсказуемому runtime lifecycle: update, назначение сущности/спрайта, загрузка ресурсов, serialization и редакторская настройка. Не оставлять обязательное обновление базовой анимации только на ручной реализации в пользовательском коде, если система является штатной возможностью движка.

2.4. **UI.** Завершить путь UiAsset → загрузка → создание/обновление UI runtime → input/actions. Определить удобную точку интеграции с EngineGame/Desktop Host и сохранить возможность настройки UI игровым кодом.

2.5. **2D Lighting и rendering.** Использовать результаты отдельного аудита графики и 2D Lighting. Не повторять уже пройденные проверки и не переписывать работающий RenderPipeline/RenderGraph без конкретного сценария. Новые задачи формулировать по реальным требованиям: ресурсы материалов, normal/emission workflow, корректное сохранение и интеграция с Editor.

2.6. **Physics, Particles, Audio и Camera.** Не переписывать существующие системы, уже включённые в Runtime. Проверить их совместное использование в одной сцене: порядок обновления, ownership ресурсов, сериализация настроек, runtime поведение и диагностические инструменты.

2.7. **Navigation.** Согласовать grid/chunk navigation с World/Tilemap только при определённом контракте карты и обновления геометрии. Связь AI с Navigation планировать в специализированном направлении.

### Критерии завершения

- Небольшую законченную 2D-игру можно собрать преимущественно через Editor и обычный C# проект.
- Сцена и ресурсы сохраняются и восстанавливаются без ручного исправления внутренних данных.
- Спрайты, камера, Transform, Tilemap, анимация, физика, частицы, UI и аудио совместно работают в одном проверенном runtime сценарии.
- Игровой проект можно запустить через Play/Stop/Restart и опубликовать на текущей поддерживаемой платформе.
- Основные сбои сцены, ресурсов и физики обнаруживаются существующими или дополненными диагностическими средствами.

**Результат этапа:** первый законченный жанрово-независимый игровой workflow, ориентированный на 2D.

## Этап 3. Полноценный 3D workflow

**Приоритет:** P1, большой самостоятельный этап  
**Зависимость:** этапы 0 и 1; базовые инструменты диагностики развиваются параллельно  
**Статус:** запланирован  
**Цель:** превратить существующие 3D-прототипы в полный пользовательский путь Editor → Content → World/ECS → Runtime → Publish.

### Задачи

3.1. **3D Runtime Foundation.** Подключить 3D Transform hierarchy и необходимые компоненты к стандартному Runtime. Добавить стандартные serializers для поддерживаемых 3D-компонентов, определить Camera3D service/active camera workflow и согласовать их с World/Scene.

3.2. **Model Content Pipeline.** Выбрать и реализовать основной формат импорта моделей (кандидат для оценки — glTF). Определить импорт геометрии, mesh/material references, textures, coordinate conventions, resource ownership и reimport. Сначала поддержать ограниченный проверенный набор features, а не заявлять универсальную поддержку формата без тестов.

3.3. **Mesh и Materials.** Завершить runtime регистрацию/отрисовку MeshRenderer3D. Развить Material3D до обоснованного базового material workflow: shader parameters, texture maps, PBR properties и совместимость ресурсов. Подключить нормальное управление ресурсами и serialization.

3.4. **Lighting и Shadows.** Выбрать реалистичный первый набор 3D lights и shadow technique. Подтвердить корректность в RenderGraph/RenderPipeline и на целевых backend. Не вводить множество типов освещения до появления соответствующего workflow.

3.5. **Physics 3D.** Спроектировать и реализовать полный минимальный 3D physics step: broad phase, поддерживаемые narrow-phase shape pairs, contact generation, solver/response, queries и FixedUpdate integration. Joints и дополнительные shape types добавлять после проверки базовой модели. Существующий CollisionDetector3D не считать полноценной физической системой.

3.6. **3D Animation.** Добавить skeleton/bones, skinning, inverse bind matrices, model import bindings и runtime animation update. Связать импортированную анимацию с сущностью/моделью и сохранением authoring data.

3.7. **3D Editor workflow.** Создать 3D Scene View с камерой редактирования, selection, transform gizmos, Hierarchy и Inspector для 3D компонентов и ресурсов. Отделить camera/navigation Scene View от игрового Camera3D.

3.8. **3D Debug и validation.** Подключить отображение bounds, colliders, contacts и другой необходимой физической информации. Добавить проверку ссылок на модели, материалы, камеры и физические компоненты.

### Критерии завершения

- 3D модель импортируется в проект через Content Pipeline и отображается в Editor.
- Scene View позволяет размещать, выбирать и трансформировать 3D объекты.
- 3D сцена сохраняется и загружается с Transform, mesh, material и camera данными.
- Игра использует ту же сцену в стандартном Runtime без ручного запуска демонстрационных render systems.
- Проверены освещение, текстуры, физические столкновения и базовая анимация на реальном игровом сценарии.
- 3D workflow имеет тесты сериализации, runtime интеграции и графического backend.

**Результат этапа:** основа для создания законченных 3D-игр, а не только демонстрации отдельных mesh/render API.

## Этап 4. Developer Tools, диагностика и производительность

**Приоритет:** P2; базовая диагностика развивается в этапах 0–3  
**Зависимость:** базовые Runtime и 2D/3D workflow  
**Статус:** запланирован  
**Цель:** сделать ошибки, графические проблемы и узкие места понятными и воспроизводимыми.

### Задачи

4.1. **Validation workflow.** Показывать конкретные ValidationIssue: severity, code, entity/asset path и описание. Подключать validators в тех слоях, где доступны необходимые каталоги и runtime data. Сохранить возможность получать результаты программно.

4.2. **Debug Visualization.** Завершить жизненный цикл вызова debug rendering, чтобы включённая визуализация действительно появлялась в кадре через понятную точку интеграции. Не делать её обязательной для всех игр; оставить контролируемой и отключаемой.

4.3. **CPU profiling и benchmark baseline.** Сохранить существующий FrameTimingProfiler и scheduler profiling. Определить повторяемые Release workloads, зафиксировать условия запуска и сохранять baseline для сравнения. Добавлять 3D benchmarks после появления полноценного 3D runtime path.

4.4. **Frame Debugger.** Реализовать захват одного кадра с последовательностью RenderPass/RenderGraph, commands, targets и существенным состоянием ресурсов. Сначала создать backend-neutral представление снимка кадра, затем UI для навигации и анализа.

4.5. **GPU timings.** Только после появления устойчивого Frame Debugger добавить backend-specific timestamp queries и асинхронное чтение результатов. Не смешивать GPU time с CPU временем вызова EndFrame.

4.6. **Job System и параллельное исполнение.** Не переводить стандартный Runtime на параллельное выполнение только из-за наличия JobSystemExecutionStrategy. Сначала определить workload и baseline, затем проверить независимость систем, владение данными, детерминизм и воспроизводимость. Включать в стандартный Runtime только при подтверждённой выгоде.

### Критерии завершения

- Пользователь видит конкретную причину ошибок validation и может найти соответствующую сущность или ресурс.
- Debug Visualization включается предсказуемо и не требует скрытых ручных обходных вызовов.
- CPU performance baseline воспроизводим и сравним между версиями.
- Frame Debugger позволяет объяснить состав кадра и состояние основных render resources.
- GPU metrics отдельно показывают GPU и CPU время.
- Параллельное исполнение включается только при измеримой пользе и наличии тестов корректности.

**Результат этапа:** практичная диагностика и управляемое развитие производительности без преждевременной оптимизации.

## Этап 5. Build, Publish и платформы

**Приоритет:** P1 для надёжной публикации Windows; P2 для расширения платформ  
**Зависимость:** этап 0; расширенная публикация зависит от завершения соответствующих runtime workflows  
**Статус:** запланирован  
**Цель:** обеспечить воспроизводимую сборку и поставку игрового проекта, отделив требования Editor от требований запуска готовой игры.

### Задачи

5.1. **Windows distribution.** Поддерживать build/test/distribution проверки на одном и том же commit для релизных кандидатов. Проверять не только ZIP состав, но и запуск распакованного Editor и пользовательского проекта.

5.2. **Publish workflow пользователя.** Определить удобный способ сборки игры из Editor/BuildTools: configuration, RID, framework-dependent или self-contained режим, assets, native libraries и результат публикации. Не добавлять сложный Export Manager, пока не определены реальные параметры и UX.

5.3. **Версия Engine в игровом проекте.** Определить, как созданный проект узнаёт версию скопированных Engine DLL, как проверяется совместимость и как обновляются библиотеки. Формат manifest должен иметь понятную стратегию версионирования и миграций.

5.4. **Платформенная стратегия Runtime.** Перед расширением выбрать конкретные платформы, которые действительно нужны для игр. Разделить совместимость библиотек Engine, Host/backend, native dependencies, packaging и пользовательский publish. Для каждой платформы завести отдельные сборки и smoke tests.

5.5. **Linux/macOS.** Проверять отдельно Runtime игры и Editor. Runtime может иметь иной путь к кроссплатформенности, чем текущий Windows Forms Editor. До решения о поддержке этих ОС не считать перенос RID в Runtime Builder достаточной реализацией.

5.6. **ARM64 и другие классы устройств.** Рассматривать после фиксации целевых платформ и проверки всех native dependencies, input, graphics, audio и package workflows. Мобильные и консольные платформы не включены в обязательный объём без отдельного согласования.

### Критерии завершения

- Публикация игры выполняется воспроизводимо из пользовательского проекта и имеет проверяемый output.
- В поставке присутствуют все требуемые managed/native зависимости и ресурсы.
- Игра запускается на чистой целевой машине по документированным требованиям.
- Каждая заявленная платформа имеет CI build, тесты и runtime smoke test.
- Ограничения Editor, Runtime и отдельных backend описаны раздельно.

**Результат этапа:** понятная и проверенная поставка игр на выбранных платформах.

## Этап 6. Специализированные игровые системы и экосистема

**Приоритет:** по потребности конкретных игр  
**Зависимость:** соответствующие базовые Runtime, Content, World и Editor workflows  
**Статус:** запланирован как набор независимых направлений  
**Цель:** довести уже существующие расширяемые подсистемы до конкретных полноценных игровых сценариев, не превращая их в искусственный блокирующий этап.

### Направления

6.1. **AI и Navigation.** Подключить AISystem и scheduler к стандартному Runtime при определённом контракте жизненного цикла. Согласовать navigation grids/chunks с World/Tilemap. Проверить path queries, perception, memory, Behavior Trees и Utility AI на реальном игровом сценарии. Оценивать алгоритмы по назначению и производительности, а не только по названиям API.

6.2. **Scripting.** Завершить пользовательский путь от script definition/asset до назначения объекту, вызова lifecycle, сохранения назначения и runtime fault diagnostics. Явно документировать границы безопасности и то, какие языки/модели исполнения поддерживаются.

6.3. **Networking и Replication.** Зафиксировать модель авторитетности, транспорт, жизненный цикл соединения, сериализацию и recovery. Развивать replication только на основе выбранной сетевой модели и интеграционных сценариев двух или более игровых экземпляров.

6.4. **Localization.** Связать существующие localization API с Content, проектными ресурсами и Editor workflow. Проверить fallback, pluralization/formatting и runtime switching в рамках определённых требований.

6.5. **Расширяемость.** Развивать регистрацию пользовательских компонентов, систем, importer-ов и editor extensions через реальные точки расширения. Не создавать общий plugin/package manager без конкретных требований к загрузке, версиям и изоляции расширений.

### Критерии завершения

Для каждого направления отдельно определяются поддерживаемый сценарий, API, редакторская настройка, сериализация, runtime lifecycle, тесты и ограничения. Отдельная подсистема считается готовой только в границах проверенного сценария.

## 5. Зависимости и порядок работ

Основной маршрут:

```text
Этап 0. Базовый цикл проекта
        |
        v
Этап 1. Editor и Content workflow
        |
        v
Этап 2. Законченный 2D workflow
        |
        v
Этап 3. Полноценный 3D workflow
        |
        v
Этап 4. Developer Tools и performance
        |
        v
Этап 5. Build, Publish и платформы
```

Этап 6 (AI, Scripting, Networking, Localization и расширения) развивается параллельно только тогда, когда для него готовы необходимые базовые механизмы и есть реальный игровой сценарий.

Зависимости не запрещают локальные улучшения: например, validation, debug visualization и тесты могут добавляться раньше большого этапа Developer Tools, если они непосредственно помогают текущей задаче.

## 6. Общие критерии готовности каждой задачи

Перед завершением задачи должны быть выполнены подходящие для неё пункты:

1. **Поведение:** описан и проверен пользовательский или runtime сценарий, ради которого делалось изменение.
2. **Интеграция:** изменение работает через стандартные точки входа Engine/Editor/Host, если возможность заявлена как стандартная.
3. **Тесты:** есть unit tests для логики и integration tests для пересечения модулей, где это оправдано.
4. **Реальный запуск:** Editor/Game.Sandbox или отдельный игровой проект проверен, если тесты не могут полностью подтвердить пользовательский путь.
5. **Данные:** serialization, format version и обратная совместимость учтены, если затронуты файлы проекта или игровые данные.
6. **Производительность:** измерения добавляются при наличии конкретного требования; оптимизация без измеримой проблемы не становится отдельной целью.
7. **Документация:** обновляются API, SUPPORT_MATRIX и соответствующий отчёт, если изменились подтверждённые возможности или ограничения.

После этапа фиксируются результат, тестовые свидетельства, ограничения и следующий приоритет.

## 7. Что намеренно не входит в обязательный ближайший объём

Следующие задачи не нужно начинать автоматически:

- переписывание ECS, World, Runtime или RenderGraph целиком;
- копирование архитектуры Godot или другого движка без конкретной выгоды;
- поддержка всех платформ одновременно;
- автоматический discovery всех пользовательских компонентов до появления проблемы явной регистрации;
- общий asset database с избыточной метаинформацией, если текущему workflow достаточно более простого каталога;
- Frame Debugger, GPU profiling и широкая система benchmark regression до появления измеримых задач, которые они должны решать;
- универсальный Export Manager до выбора реальных publish profiles и целевых платформ;
- полная реализация всех AI, networking и scripting возможностей до появления проверяемых игровых требований.

Это не запрет на развитие перечисленных направлений. Это правило удержания фокуса на завершённых пользовательских сценариях и фактических зависимостях.

## 8. Первый рабочий этап

Первой задачей реализации назначается **Этап 0 — надёжный базовый цикл проекта**.

Рекомендуемая последовательность внутри него:

1. Проверить Release build/tests на актуальном master.
2. Проверить distribution на том же commit.
3. Добавить/выполнить smoke test распакованного дистрибутива.
4. Закончить Startup Scene workflow от создания проекта до загрузки в игре.
5. Проверить Assets и publish output.

После завершения этапа 0 перейти к этапу 1. Каждую конкретную задачу предварительно уточнять через `/plan`, затем выполнять по `/next`.
