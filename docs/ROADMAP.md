# Roadmap: создание и запуск игровых проектов VibeEngine2

**Обновлено:** 2026-10-22

Этот документ задаёт рабочую последовательность разработки. Выполненные пункты отражают проверенное поведение, а не только написанный код. В каждый момент есть одна текущая задача; следующие этапы не начинаются, пока её критерии не выполнены.

## Цель

Пользователь должен уметь создать игровой проект в редакторе, редактировать его код во внешней IDE, работать с ресурсами и стартовой сценой, запускать и останавливать игру из редактора, а затем собирать автономное приложение.

**Критерий готовности:** простой проект, созданный редактором, можно открыть и изменить, запустить и остановить из редактора, повторить запуск без остаточных процессов или ресурсов, а также собрать и запустить отдельно от редактора и исходников VibeEngine2.

## Принципы и границы

- **Движок предоставляет механизмы, игра определяет смысл.** Не добавлять в Engine понятия конкретной игры.
- **`Game.Sandbox` — интеграционный полигон**, а не шаблон пользовательской игры и не обязательная основа запуска. Не нужно добиваться совпадения её структуры со сгенерированным проектом.
- Повторно использовать существующие `EngineGame`, `DesktopGameHost`, `GameLoop`, `EngineRuntime`, `Engine.Content` и сборочные возможности .NET. Не вводить новые абстракции без необходимости, обнаруженной в текущей задаче.
- Различать игровой проект, открытый документ редактора, исходную сцену, runtime-состояние и сохранение игрового прогресса.
- Ресурсы игры разрешаются относительно игрового проекта/его выходного каталога, а не относительно редактора, клона репозитория или текущего рабочего каталога процесса.
- Пользовательский C#-код остаётся обычным .NET-проектом и редактируется во внешней IDE. Встроенный редактор кода не нужен.
- В текущей модели новый проект получает подготовленные библиотеки VibeEngine2 в `Engine/` и использует локальные ссылки `Reference`/`HintPath`. Не переходить на NuGet или собственный менеджер пакетов без практической причины.
- Начальный запуск из редактора может работать в отдельном процессе и окне. Встроенный Game View — отдельный будущий этап.
- Не включать в первый рабочий сценарий C# Hot Reload, сложную систему сцен, универсальную систему плагинов или независимые игровые циклы.

## Порядок работ

Работать по этапам сверху вниз. Непосредственно выполнять только текущую задачу; новые архитектурные направления не внедрять попутно.

### 1. Проектные ресурсы и рабочий процесс с проектом — ЗАВЕРШЁН

- [x] Генератор `.csproj` копирует содержимое `Assets/**/*` в build и publish output с сохранением вложенной структуры каталогов.
- [x] На свежем проекте проверено наличие тестового файла в `bin/Debug/net8.0/Assets/Probe/` и в `bin/Release/net8.0/publish/Assets/Probe/`.
- [x] Проверена загрузка PNG из выходного `Assets/` через `Runtime.Services.Content.Load<TextureData>(new AssetPath(...))`.
- [x] Добавлена команда `Open IDE`: открывает `.sln` активного проекта через системную ассоциацию, а если решения нет — `.csproj`. Проверено вручную.
- [x] Проверено создание, открытие в IDE, сборка и запуск проекта в каталоге вне клона VibeEngine2.

**Заметка о регистрах путей:** `AssetPath` нормализует разделители, но не регистр символов. `FileContentCatalog` индексирует пути по точному значению, поэтому запрос должен совпадать с регистром имени, которое обнаружено в выходном каталоге. На Windows пути файловой системы регистронезависимы, но ключи каталога контента — нет; при изменении только регистра следует очистить старые build-артефакты и пересобрать проект.

**Критерий завершения этапа выполнен:** ресурсы проекта копируются и доступны запущенной игре; открытие кода, сборка и запуск проверены без репозитория исходников движка.

- [x] При создании проекта генерируется пустая сцена `Scenes/Main.world` существующим `WorldSaveLoadService`.

**Критерий завершения выполнен:** новый проект содержит стартовую сцену; игра загружает её в отдельный runtime-мир, а изменения игрового состояния не перезаписывают исходную сцену автоматически.

- [x] Вывод процесса читается асинхронно через очередь и передаётся в существующую консоль редактора.
- [x] Проверены повторные Play / Stop / Restart и восстановление доступности кнопок после завершения процесса.
- [x] Подтверждено, что авария игры не закрывает и не повреждает редактор.

**Критерий завершения выполнен:** активный проект можно запускать, останавливать и повторно запускать; завершение игры не оставляет редактор в ложном состоянии «игра запущена».

### 6. Последующие архитектурные улучшения — не блокируют основные этапы

Раздел объединяет проверку полноты Engine Runtime, интеграцию игрового проекта с движком и развитие Editor. Исследование само по себе не означает, что требуется новая подсистема: сначала проверить существующие API и зафиксировать конкретный пробел.

#### 6.1. Проверка полноты Engine Runtime

- [x] Проверить путь создания и регистрации пользовательских компонентов и систем из игровой сборки; определить минимально необходимый workflow без преждевременного универсального plugin framework. Базовый механизм `EngineGame.ConfigureRuntime()` покрыт тестом `ConfigureRuntime_RegistersGameSystemThatUsesCustomComponent`; сквозной сценарий подтверждён тестом `SeparateGameAssembly_CanRegisterAndExecuteCustomSystem`, который собирает и запускает отдельный временный C#-проект с собственными ECS-компонентом и системой. Универсальный plugin framework не требуется для этого workflow.
- [x] Проверить согласованность ECS, Physics и сцен: можно добавлять необходимые компоненты сущностям через команды редактора, сохранять поддерживаемое физическое состояние и восстанавливать его при загрузке сцены. Проверено интеграционным тестом `BinaryPersistence_RoundTripsPhysicsComponentsAddedThroughEditorCommands`.
- [x] Проверить согласованность регистрации компонентов и сериализации: сохранение ECS-компонента без зарегистрированного сериализатора завершается понятной ошибкой с типом компонента и не создаёт файл сохранения. Проверено тестом `Save_RejectsRuntimeComponentWithoutRegisteredSerializer`.
- [x] Проверить освобождение runtime-ресурсов, подписок и состояния при остановке и повторном запуске. Тестами проверены идемпотентность `Dispose`, очистка команд и событий, отключение систем, скриптов, debug-консоли и контроллера игрового цикла, освобождение спрайтовых ресурсов после предварительного `Shutdown`, а также корректная очистка при ошибках инициализации и остановки.
- [x] Оценить границы host/platform для графики, аудио и ввода. Подтверждено разделение владения: `EngineRuntime` освобождает собственные ресурсы, но не освобождает внедрённый `IAudioManager`, принадлежащий host. OpenGL, OpenAL и Silk.NET остаются стандартными вариантами; смена backend не требуется без конкретной потребности.
- [x] Проверить использование пользовательских сборок, зависимостей, ресурсов и сцен в игровом проекте вне репозитория движка. Интеграционный тест публикует и запускает временный игровой проект с пользовательской ECS-системой, отдельной библиотекой через `ProjectReference`, ресурсом из `Assets/` и стартовой сценой. Текущая модель локальных `Reference`/`HintPath` сохранена.

#### 6.2. Интеграция игрового проекта и Editor

- [x] **Текущее покрытие:** `Add Component` поддерживает `LocalTransform2D`, `WorldTransform2D`, `PhysicsBody2D`, `Collider2D`; Inspector редактирует параметры физического тела, форму коллайдера и материал, а зависимости защищены при добавлении и удалении. Проверено тестами `InspectorComponentPickerTests` и `EcsComponentPropertyProviderTests`.
- [x] **Rendering:** добавлены сериализуемый `SpriteComponent` и runtime-отрисовка ECS-спрайтов; проверены регистрация, сериализация и `SpriteRenderSystemTests`.
- [x] **Audio:** добавлены `AudioSourceComponent`/`AudioListenerComponent` и runtime-управление ресурсами; проверено тестами `AudioEcsSystemTests`.
- [x] **Существующий ECS:** добавлено назначение `DistanceJoint2D` (две сущности и длина) и управление `TransformParent2D` через Hierarchy; проверено тестами `DistanceJointEditorCommandTests` и `TransformParentEditorCommandTests`.
- [x] **Первичный аудит Camera/Particles:** `Camera2D` уже доступна runtime через `EngineRuntimeServices` и используется при отрисовке спрайтов; `ParticleEmitter`, `ParticleEmitterRuntime` и `ParticleSystem` работают отдельно от ECS/runtime. Сам факт наличия этих API не даёт игровому разработчику законченного workflow настройки камеры и размещения/настройки/отрисовки эмиттеров.
- [ ] **Camera и Particles — workflow разработчика игры:** определить и обеспечить понятный путь создания и настройки камеры (позиция, zoom, viewport, активная камера и управление ею из игрового кода/runtime) и создания/конфигурирования эмиттеров (частота/burst, параметры частиц, фабрика инициализации/модификаторы), их размещения/привязки к миру, runtime-обновления и отрисовки. Определить, какие настройки принадлежат документу мира/сцене или ресурсам, а какие остаются игровым кодом, и обеспечить нужное сохранение/восстановление. Выбрать подходящую точку интеграции после проектирования: ECS-компонент — один из вариантов, но не обязательное требование.
- [x] Проверена пересборка C#-проекта и повторный запуск после изменения кода; `GameProjectRunnerBuildTests.Restart_BuildsUpdatedSource_AndRecoversAfterBuildFailure` подтверждает запуск обновлённого кода, диагностику ошибки компиляции и успешный повторный запуск после исправления. Это отдельный сценарий, не связанный с hot-reload ресурсов.
- [ ] Рассмотреть встроенный Game View, Pause и пошаговое выполнение после устойчивой работы текущего запуска в отдельном процессе. Это задачи интеграции Editor/runtime, а не обязательные условия базовой готовности Engine Runtime.

#### 6.3. Scripting, Networking и отложенные архитектурные направления

- [ ] **Scripting — минимальный workflow:** проверить и довести до понятного использования существующие `ScriptRegistry`, `ScriptRuntime` и `ScriptAssignmentsComponent`: регистрация скриптов из игровой сборки, назначение объекту мира/сущности, настройка параметров, вызовы в update/fixed update, обработка ошибок и жизненного цикла, сохранение и восстановление назначений. Предусмотреть работу из игрового кода и определить нужную поддержку в Editor; не требовать C# Hot Reload или универсальный plugin framework.
- [ ] **Networking — аудит реализуемого минимального сценария:** изучить существующие `Engine.Networking` и `Engine.Networking.Replication` (transport, connections/sessions, topologies, authority, entity mapping и replication) и определить, чего не хватает для сквозного сценария двух игровых узлов: соединение, обмен данными/командами, идентификация и синхронизация выбранного состояния, отключение и очистка. Проверить реальную реализуемость интеграционным тестом/прототипом, зафиксировать ограничения и предложить минимальный scope до расширения функциональности. Не считать `NetworkIdentity` обязательным ECS-компонентом заранее — способ идентификации выбрать по итогам аудита.
- [ ] Исследовать C# Hot Reload отдельно; не обещать горячее применение произвольных изменений кода в первой версии.
- [ ] Возвращаться к плагинам и динамической загрузке модулей только при появлении конкретного workflow, который нельзя разумно покрыть обычными игровыми сборками.
- [ ] Не вводить отдельные GameLoop, универсальный менеджер расширений или другие новые абстракции без подтверждённой необходимости.

**Правило этапа:** сначала исследовать текущую реализацию и описать выявленный пробел, затем согласовать конкретную задачу и критерий проверки. Не превращать все исследовательские пункты автоматически в обязательную разработку.

## Сквозная проверка готовности

Когда основные этапы завершены, пройти весь сценарий подряд:

1. Создать пустой проект из редактора.
2. Закрыть и повторно открыть проект; убедиться, что состояние редактора восстановилось.
3. Добавить/изменить ресурс и стартовую сцену, открыть код во внешней IDE.
4. Собрать и запустить игру из редактора.
5. Изменить runtime-состояние, остановить игру и убедиться, что исходная сцена редактора не изменилась автоматически.
6. Несколько раз запустить и остановить игру; проверить очистку процессов и ресурсов.
7. Смоделировать ошибку сборки и ошибку запуска; убедиться, что редактор восстанавливается.
8. Собрать и запустить игру автономно, без редактора и клона репозитория VibeEngine2.

## Правила обновления ROADMAP

- Отмечать пункт выполненным только после проверки указанного результата.
- При активной разработке указывать одну текущую задачу с конкретным результатом проверки.
- Если выяснилось, что задача поставлена неверно, сначала исправить план, затем писать код.
- Не записывать исследовательскую ветку или разовое изменение `Game.Sandbox` как обязательное направление, если этого нет в согласованном плане.
- При работе над планом изменять только `docs/ROADMAP.md`; исходный код пользователь редактирует локально отдельно.

## Readiness: Editor, Game.Sandbox и Engine

Этот этап проводится после выполнения необходимых рабочих этапов ROADMAP. Его цель — отдельно оценить готовность редактора, тестового полигона и движка, не подменяя проверку одного компонента результатами другого.

- [ ] **Editor Readiness:** проверить основные рабочие сценарии редактора, состояние и восстановление проекта, работу Asset Browser и инспектирования/редактирования поддерживаемых данных, диагностику ошибок, запуск и остановку игры, а также корректное освобождение ресурсов.
- [x] **Game.Sandbox Readiness:** готово.
- [ ] **Engine Readiness:** проверить ключевые runtime-механизмы и их взаимодействие — жизненный цикл, ECS, сцены и сериализацию, контент/ресурсы, графику, ввод, аудио, физику и обработку ошибок — с учётом фактически поддерживаемых возможностей проекта.
- [ ] **Integration Readiness:** проверить сквозные сценарии Editor → игровой проект → Engine Runtime, включая создание проекта, сборку, запуск, остановку, повторный запуск и работу вне репозитория исходников движка.
- [ ] Для каждой найденной проблемы определить воспроизводимый сценарий, ожидаемое поведение, критерий завершения и подходящий уровень проверки: unit, integration или ручной smoke test.
- [ ] Разделить подтверждённые дефекты, отсутствующие необходимые возможности и необязательные улучшения. Не объявлять readiness пройденным только по зелёным тестам или успешному запуску Sandbox.

## Проверка готовности к production

Провести отдельную оценку production readiness перед объявлением движка и редактора готовыми для стабильного использования в реальных игровых проектах. Это контрольный этап, а не обещание соответствия конкретному сертификационному стандарту.

- [ ] **Надёжность:** проверить обработку ошибок, повторный запуск после сбоев, очистку процессов и ресурсов, а также отсутствие критических зависаний и повреждения состояния проекта.
- [ ] **Тестирование:** определить критичные сценарии и покрытие автоматическими unit/integration-тестами; добавить воспроизводимые smoke tests для сборки, запуска и поставки.
- [ ] **Сборка и распространение:** проверить чистую сборку и публикацию из релизных артефактов, состав поставки, native-зависимости, целевые платформы и документированные требования к .NET Runtime.
- [ ] **Безопасность и целостность данных:** проверить валидацию путей проекта и ресурсов, корректную обработку отсутствующих/повреждённых файлов и сохранение обратной совместимости форматов там, где она заявлена.
- [x] **Производительность и ресурсы:** снят и повторно проверен Release baseline для ECS, JobScheduler, Content Pipeline и Engine.Runtime; проверены время выполнения, аллокации, GC и память при создании и освобождении ECS World. Явных регрессий в проверенных сценариях не обнаружено.
- [ ] **Диагностика и сопровождение:** убедиться, что ошибки сборки и runtime понятны разработчику, а важные ограничения, зависимости и процедуры восстановления задокументированы.
- [ ] **Документация и ограничения:** описать поддерживаемые функции, неподдерживаемые сценарии и известные ограничения; не заявлять готовность функций, которые не прошли проверку.
- [ ] Зафиксировать итог по Editor, Game.Sandbox и Engine отдельно: **готово**, **готово с известными ограничениями** или **не готово**, со списком блокирующих проблем и доказательствами проверок.

**Критерий завершения:** production readiness подтверждён результатами проверок и документированными ограничениями, а не только субъективной оценкой или фактом успешной сборки.
