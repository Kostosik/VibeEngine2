## 1. Итог

В репозитории есть workflow создания C#-проекта, подготовки локального набора библиотек движка, сборки и запуска игры из Editor, остановки процесса и повторного запуска после исправления ошибок компиляции.

Первая поставляемая конфигурация ориентирована на **Windows x64 и .NET 8**. В текущем виде это не кроссплатформенный build pipeline: Runtime Builder жёстко использует RID `win-x64`, Editor основан на Windows Forms и `net8.0-windows`, а CI и distribution workflow выполняются на Windows.

### Сводная оценка

| Область | Статус | Основание и границы |
|---|---|---|
| Создание проекта | Подтверждено с ограничениями | Создаётся обычный C#/.NET проект с локальными ссылками на библиотеки Engine. Поддерживается только шаблон `empty`. |
| Runtime Builder | Подтверждено с ограничениями | Сборщик публикует набор библиотек под `win-x64`, проверяет обязательные сборки и устанавливает каталог через staging/backup. Набор целевых проектов и обязательных DLL задан вручную. |
| Play / Stop / Restart | Подтверждено тестами для отдельных сценариев | Editor использует отдельный процесс `dotnet run`; тесты проверяют сборку, ошибки компиляции, восстановление после исправления, Hot Reload и остановку дерева процессов. |
| Assets в output / publish | Реализовано в шаблоне проекта | Файлы `Assets/**/*`, manifest и native DLL получают правила копирования в output и publish. Полный runtime smoke test на распакованном ZIP в workflow не выполняется. |
| Публикация пользовательской игры | Возможна стандартными средствами .NET | Игровой проект — обычный `.csproj`; отдельный пользовательский Export/Publish workflow в Editor не обнаружен. |
| Windows x64 | Основная целевая конфигурация | Для неё есть CI и workflow сборки дистрибутива. Последние найденные успешные запуски относятся не к текущему исходному commit аудита. |
| Linux / macOS / ARM64 | Не проверено | Нет соответствующих CI jobs и distribution targets; наличие отдельных проектов с TFM `net8.0` само по себе не подтверждает платформенную поддержку. |
| Self-contained publish | Не подтверждено как штатный сценарий | Runtime Builder и distribution workflow используют `--self-contained false`. |

Главные вопросы для дальнейшего развития — актуальная проверка CI на текущем коде, точное описание требований к .NET SDK для Play/Hot Reload, пакетный end-to-end smoke test и отдельный план многоплатформенности. Связанный вопрос загрузки Startup Scene уже описан в [аудите Scene и World](03-SCENE-AND-WORLD.md).

## 2. Создание игрового проекта

Основная реализация находится в `Engine.Editor/Projects/ProjectCreationService.cs`.

### 2.1. Что создаётся

На текущий момент сервис принимает только template ID `empty`. Остальные значения завершаются `NotSupportedException`.

Новый проект создаётся во временном staging-каталоге и затем перемещается в целевой каталог. Сервис проверяет имя и пути проекта, существование корня диска, отсутствие уже существующего целевого файла/каталога и наличие полного набора runtime DLL до создания содержимого проекта.

Структура нового проекта включает:

- каталог `Engine/` с копией DLL из подготовленного Runtime;
- пустой каталог `Assets/`;
- `.csproj` проекта;
- `.vibeproject` manifest;
- `Program.cs` и `GameMain.cs`;
- `.sln`, если пользователь запросил создание solution.

Это обычный C# проект, а не проект, который требует собирать VibeEngine2 из исходников при каждом запуске. Managed-сборки подключаются через локальные `Reference` и `HintPath` в `Engine/`.

### 2.2. Конфигурация шаблона

Генерируемый проект задаёт:

- `TargetFramework = net8.0`;
- `PlatformTarget = x64`;
- Nullable и implicit usings;
- локальные ссылки на managed DLL движка;
- копирование native DLL из `Engine/` в output и publish;
- копирование `Assets/**/*` в output и publish;
- копирование `.vibeproject` рядом с приложением.

В результате игровой проект использует конкретную копию библиотек Engine, расположенную внутри самого проекта. Это позволяет собирать его отдельно от репозитория VibeEngine2. Вместе с тем manifest содержит версию формата проекта, но не отдельную версию Engine или сведения о происхождении набора DLL. Обновление скопированных библиотек в проекте остаётся отдельной операцией.

### 2.3. Startup Scene

В `ProjectCreationService` присутствует закрытый метод `CreateEmptyStartupScene`, однако в текущем коде он только объявлен и не вызывается. При создании проекта каталог `Assets/` создаётся пустым, а поле `startupScene` в manifest не задаётся.

Сам manifest поддерживает относительный путь `startupScene`, а `GameProject` проверяет формат и безопасность пути. Но в стандартном Play workflow `EditorApplication.StartGame` передаёт Runner только проект и режим запуска. Сгенерированный `Program.cs` также не загружает `.world` сцену.

Итог: хранение настройки Startup Scene существует, но автоматический путь от создания/настройки сцены до её загрузки запущенной игрой не завершён. Это сквозной вопрос Scene/World, а не Runtime Builder; подробности зафиксированы в отчёте 03.

## 3. Engine Runtime Builder

Основная реализация: `BuildTools/BuildTools.Core/Runtime/EngineRuntimeBuilder.cs`. CLI: `BuildTools/BuildTools.CLI/Program.cs`.

### 3.1. Состав и процесс сборки

Сборщик хранит фиксированные списки:

- `SourceProjectPaths` — проекты, которые нужно опубликовать для формирования Runtime;
- `RequiredAssemblies` — DLL, обязательные для признания результата полным.

Для каждого проекта выполняется отдельный `dotnet publish` со следующими параметрами:

- конфигурация Debug или Release;
- RID `win-x64`;
- `--self-contained false`;
- `CopyLocalLockFileAssemblies=true`.

DLL из корневого каталога каждого publish output объединяются в общий runtime-каталог. После этого сборщик проверяет наличие всех элементов `RequiredAssemblies`.

Каталог Runtime — это подготовленный набор managed/native библиотек для ссылки из игрового проекта. Это не самостоятельная self-contained публикация игры: исполняемый проект и его runtimeconfig/deps формируются уже при сборке пользовательского `.csproj`.

### 3.2. Надёжность установки

Сборка выполняется под общим semaphore lock. Временная рабочая директория создаётся рядом с целевым output, а итоговый runtime сначала полностью собирается отдельно.

При установке старый output переименовывается в backup, новый каталог переносится на его место, а при ошибке выполняется попытка восстановить предыдущий каталог. Временная рабочая директория удаляется после сборки.

Тесты проверяют, что при отмене публикации и при ошибке публикации ранее существовавший Runtime сохраняется. Это важная гарантия для повторного обновления библиотек.

### 3.3. Ограничения проверки Runtime

Проверка `runtime verify` контролирует существование обязательных DLL. Она не проверяет:

- архитектуру и ABI каждой native-библиотеки;
- версию или целостность DLL;
- согласованность версий всех зависимых сборок;
- полноту произвольных дополнительных файлов, которые пользовательский проект может ожидать рядом с Engine.

Проверка OpenAL native DLL дополнительно выполняется в distribution workflow, но не является частью общей проверки `EngineRuntimeBuilder.ContainsRequiredAssemblies`.

Списки исходных проектов и обязательных сборок поддерживаются вручную. При добавлении новой зависимости Engine необходимо поддерживать их в согласованном состоянии. Сейчас тесты проверяют определение source root и полноту списка DLL, но не содержат отдельного успешного интеграционного теста полного BuildAsync на свежем checkout. Успешная сборка Runtime подтверждалась distribution workflow.

## 4. Play / Stop / Restart и запуск вне репозитория

Основные файлы:

- `Engine.Editor/Projects/GameProjectRunner.cs`;
- `Engine.Editor/Projects/GameProjectSessionManager.cs`;
- `Engine.Editor.UI/EditorApplication.cs`.

### 4.1. Как Editor запускает игру

Стандартный Play запускает отдельный процесс `dotnet` с рабочим каталогом проекта:

- `dotnet run --project <project.csproj> --configuration Debug --no-launch-profile`.

Hot Reload использует `dotnet watch` с тем же проектом. Стандартный запуск не зависит от того, находится ли исходный код игры внутри репозитория движка: проект содержит локальные библиотеки в `Engine/`.

Вывод stdout/stderr асинхронно считывается Runner и помещается в очередь сообщений редактора. Ошибки компилятора и runtime-исключения могут отображаться в консоли. Runner поддерживает передачу аргументов приложения через разделитель `--`, а Session Manager может управлять несколькими независимыми игровыми процессами.

### 4.2. Остановка и повторный запуск

Stop завершает дерево процессов, а не только непосредственный процесс `dotnet`. Runner ограничивает ожидание завершения процесса пятью секундами и ожидание дочитывания stdout/stderr одной секундой. Restart останавливает прежний процесс и запускает проект заново в прежнем режиме.

В тестах присутствуют сценарии:

- сборка и запуск временного проекта;
- отображение ошибок компиляции;
- повторный запуск после исправления исходника;
- Hot Reload и продолжение наблюдения после ошибок;
- передача аргументов;
- несколько независимых сессий;
- остановка дочерних процессов и ограниченное ожидание завершения.

### 4.3. Требование .NET SDK

Это важное различие в требованиях к среде:

- Для запуска самого framework-dependent Editor достаточно соответствующего .NET 8 Desktop Runtime.
- Для Play и Hot Reload редактор вызывает `dotnet run` / `dotnet watch`, которые выполняют сборку пользовательского проекта. Для этого на машине разработчика нужен **.NET 8 SDK**, а не только Runtime.
- При отсутствии готового Runtime Editor может попытаться собрать Engine Runtime из исходников; этот fallback также требует установленного .NET SDK и доступного репозитория движка.

README и README.txt, формируемый distribution workflow, сейчас сообщают требование .NET 8 Desktop Runtime, но не объясняют отдельное требование SDK для сценария разработки и запуска пользовательских проектов. Это несоответствие пользовательской инструкции реальному workflow.

## 5. Build и Publish пользовательской игры

Пользовательский проект является обычным SDK-style `.csproj`. Поэтому доступны стандартные команды .NET, в частности `dotnet build`, `dotnet run` и `dotnet publish`.

Шаблон явно включает в output/publish каталоги Assets, manifest и native DLL, находящиеся в Engine. Это создаёт основу для публикации игры без исходного репозитория движка.

При этом в Editor не обнаружен отдельный пользовательский Publish/Export workflow с профилями конфигурации, RID, self-contained/framework-dependent выбором и проверкой итоговой поставки игры. Текущий workflow `build-distribution.yml` собирает сам Editor, Runtime и Game.Sandbox; он не является pipeline публикации произвольного проекта пользователя.

Практический путь публикации пользовательской игры сейчас остаётся обычным .NET publish из внешней IDE или терминала. Для готовности распространения игры отдельно требуется проверять итоговую папку и запуск приложения вне каталога разработки.

## 6. Платформы и конфигурации

| Слой | Текущая конфигурация | Фактический вывод |
|---|---|---|
| Editor | `net8.0-windows`, WinForms | Приложение редактора явно Windows-ориентировано. |
| Generated game project | `net8.0`, `PlatformTarget=x64` | Целевая архитектура проекта — x64; ссылки и native DLL берутся из Windows Runtime bundle. |
| Engine Runtime Builder | RID `win-x64`, framework-dependent | Другие RID через текущий API сборщика не задаются. |
| Game.Sandbox distribution | `dotnet publish --runtime win-x64 --self-contained false` | Опубликованная демонстрационная игра в workflow — Windows x64. |
| Editor distribution | `net8.0-windows`, `win-x64`, framework-dependent | Для запуска требуется Windows Desktop Runtime соответствующей архитектуры. |
| CI build/test | `windows-latest`, .NET 8 SDK | Нет матрицы Linux/macOS/ARM64. |
| Self-contained | Не используется в штатном pipeline | Отдельного подтверждённого self-contained сценария в CI не найдено. |

Нельзя делать вывод, что каждая библиотека Engine технически не способна работать на иной ОС: многие проекты используют общий TFM `net8.0`. Однако готовый пользовательский workflow Editor → Runtime Builder → native dependencies → запуск игры на иных ОС не реализован и проверками не подтверждён.

**Подтверждённая конфигурация текущей поставки: Windows x64 + .NET 8.** Linux, macOS, ARM64 и self-contained deployment остаются непроверенными направлениями.

## 8. Рекомендации и приоритеты

### Приоритет 1 — надёжность текущего Windows workflow

1. Уточнить требования в документации и в README внутри ZIP: .NET 8 Desktop Runtime запускает Editor, но для Play/Hot Reload пользовательских проектов нужен .NET 8 SDK.
2. Выполнить build/test и distribution workflow на актуальном master и зафиксировать проверенный commit.
3. Добавить end-to-end smoke test распакованной поставки: запуск Editor, создание проекта, сборка/Play, проверка чтения Assets, Stop и запуск опубликованного приложения из отдельного каталога. Не ограничиваться проверкой наличия DLL.
4. Добавить успешный интеграционный тест Runtime Builder либо сохранить текущую проверку через distribution workflow, но запускать её на каждом релизном кандидате.

### Приоритет 2 — завершённость проектного workflow

1. Завершить сквозное использование Startup Scene: создание сцены для нового проекта, сохранение manifest и загрузка сцены сгенерированной игрой. Не дублировать механизмы World/Scene — использовать уже существующие сервисы и согласовать с выводами аудита 03.
2. Определить понятную процедуру обновления скопированных Engine DLL в уже созданном проекте и при необходимости сохранять версию Engine в manifest.
3. При появлении реальной потребности в распространении пользовательских игр добавить в Editor или BuildTools отдельный Publish workflow с явной конфигурацией и проверкой результата.

### Долгосрочно — новые платформы

Переходить к Linux/macOS/ARM64 следует отдельным согласованным этапом. Он потребует не только добавить RID в Runtime Builder, но и подтвердить соответствующие native dependencies, desktop host/backend, Editor UI, упаковку и запуск на целевой ОС. Простого изменения `win-x64` на другой RID недостаточно.
